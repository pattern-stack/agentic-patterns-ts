# Spec — Approval gates on native SDK toolApproval

All repo line numbers cite `main` @ `0551140` (post-#386/#388: ai@7.0.37,
runtime 0.34.0). All SDK line numbers cite the installed `ai@7.0.37`
`dist/index.d.ts` / `dist/index.js`, byte-verified on that commit.

## Goal

Bridge our approval-gate layer (layer 6) to v7's native `toolApproval` loop on
the paths where the SDK drives multi-step execution, so that:

- the **gate chain stays the single policy brain** — every decision still flows
  through `AgentEventBus.evaluateIntent()` (SAFETY → RATE_LIMIT → APPROVAL →
  guaranteed AUDIT, `agent-event-bus.ts:96-161`);
- a **denial becomes a first-class SDK denial** (`tool-output-denied` sent to
  the model) instead of today's fake tool-error (`ToolCallBlocked` thrown from
  inside `execute`, `agent-runner.ts:989-991`);
- the new SDK approval artifacts are **surfaced as `agent.*` events → SSE →
  dashboard**;
- **zero behavior change** on `run()` / `stream()` / the 2-tier fallback — the
  GATE-CHAIN INVARIANT (`agent-runner.ts:13-19`) stays intact there.

This spec's Gate-1 question — who owns the loop — is presented as **Decision D0**
below with a recommendation. Everything after D0 assumes the recommended option;
if the human picks differently, the spec must be revised, not patched.

## Verified v7 toolApproval mechanics (byte-checked, not docs-checked)

The facts the design stands on, from `ai@7.0.37`:

1. **`toolApproval` is a generateText/streamText setting** (`dist/index.d.ts:3429`
   and `:4753`): either a per-tool map or a single generic callback
   `GenericToolApprovalFunction` receiving `{toolCall, tools, messages, …}`
   (`d.ts:2968-2990`). It returns `MaybePromiseLike<ToolApprovalStatus>` — **the
   callback may be async and take arbitrarily long**. Statuses:
   `'not-applicable' | 'approved' | 'denied' | 'user-approval'`, each also as
   `{type, reason?}` objects (`d.ts:2941-2953`).
2. **Per-status runtime behavior** (generateText loop, `dist/index.js:5491-5556`):
   - `approved` → SDK synthesizes a `tool-approval-request` output part with
     `isAutomatic: true` **plus** a matching `tool-approval-response
     {approved: true, reason}`, then executes the tool **in the same step**.
     No pause.
   - `denied` → same synthesized request/response pair (`approved: false`),
     tool never executes, a **`tool-output-denied`** part is produced, and —
     critically — **the loop continues** (denials count as satisfied outputs in
     the continue condition, `index.js:5717-5723`), so the model sees the
     denial and can adjust.
   - `user-approval` → a `tool-approval-request` part is emitted, the call
     lands in `blockedToolCallIds`, and the **loop stops** (pending approvals
     fail the continue condition). Resume = append a `tool` message carrying a
     `ToolApprovalResponse {approvalId, approved, reason}`
     (`provider-utils/dist/index.d.ts:1444-1481`) and call generateText again.
3. **HMAC signing applies ONLY to the pause/resume path.**
   `experimental_toolApprovalSecret` (`d.ts:3435`) signs each request at
   issuance (`maybeSignApproval`, `index.js:4913-4923`); verification happens
   exclusively in `validateApprovedToolApprovals` when a replayed approval
   response re-enters a later call (`index.js:4930-5005`, signature check at
   `:4946-4970`) — which **also re-resolves `toolApproval` a second time**
   (revalidation, `:4983-4997`). If the callback never returns
   `'user-approval'`, this code path is never entered.
4. **Loop-stop conditions are unchanged for execute-less tools**: "A tool
   without an execute function is called" still ends the loop (`d.ts:1747-1756`)
   — v7 did not break the single-step behavior `run()`/`stream()` rely on.
5. **Stream parts**: `tool-approval-request` / `tool-approval-response` /
   `tool-output-denied` are `TextStreamPart` members (`d.ts:2887-2891, 2927`)
   and appear in `result.content` / `steps[].content` on the generateText path
   (`ToolApprovalRequestOutput` `d.ts:1168-1189`, carrying `approvalId`,
   `toolCall`, `isAutomatic`, `signature?`).

## Current approval architecture (what exists today)

- **Gate chain**: `HumanApprovalGate` (`gates/approval.ts:28-102`) is APPROVAL
  category; its `ApprovalCallback` (`approval.ts:23-26`) may be async and
  already returns rich `HarnessDecision`s (deny/cancel/rewriteInput/allow*).
  The bus runs the chain per intent and **guarantees the audit phase and an
  `agent.gate.decision` event on every evaluation, allow or block**
  (`agent-event-bus.ts:96-186`); blocks additionally emit `agent.tool.rejected`
  (`:152, :190`).
- **In-process human await already exists**: `createHumanInputApprovalGate`
  (`interaction/approval-gate.ts:52-91`) publishes `agent.input.request` on the
  bus, parks the decision in `PendingInputRegistry`
  (`interaction/pending-input-registry.ts`), and the server resolves it via
  `POST /conversations/:id/input` (`agent-server/src/routes/conversations.ts:684`;
  live delivery via the `agent.input.request` subscription at `:465-494`;
  config seam `agent-server/src/config.ts:214-220`). The dashboard renders the
  approval card and answers it (`agent-dashboard/src/chat/input-responder.ts`,
  `api/sse-events.ts:46-49`). **The run blocks in-process while the human
  decides; nothing round-trips through the client but `{correlation_id,
  decision}`.**
- **Three gate-interception sites in the runner**:
  1. `run()` — execute-less tools, single-step, intents evaluated between
     steps (`agent-runner.ts:472-479` no-stopWhen call; `:630-632` block →
     `ToolCallBlocked` throw).
  2. `stream()` — same invariant (`:1450` comment); block → `agent.error` +
     `conversation.end{reason:"error"}` (`:1779-1800`).
  3. `runStructured()` **capable path** — the one place the SDK already drives
     a multi-step loop (`stopWhen: isStepCount(...)`, `:1164`) with
     execute-bearing tools; the gate check lives INSIDE each `execute`
     (`convertExecutableTools`, `:958-1050`; `emitIntent` at `:989`;
     block → `throw ToolCallBlocked` at `:991`, which ai@7 converts to a
     `tool-error` content part — the model sees a generic execution error,
     not a denial).

## D0 — The Gate-1 decision: who owns the loop?

### Option A — approval interop only on SDK-driven paths; invariant untouched

Scope native `toolApproval` to the paths where the SDK already drives the loop
(today: the `runStructured()` capable path). `run()`/`stream()` keep the
invariant and their existing gate interception unchanged.

- **+** Blast radius ≈ one private method + event plumbing. All 1,899 lines of
  `agent-runner.test.ts` gate/terminal/abort semantics stay valid.
- **+** No event-ordering changes for exporters/collector/dashboard on the two
  primary paths.
- **−** Approval events only exist on the capable path; `run()`/`stream()`
  approvals continue to surface via the existing (already-working)
  `input.request`/`gate.decision`/`tool.rejected` vocabulary.

### Option B — relax the invariant; SDK drives every loop

Give `run()`/`stream()` execute-bearing tools + `stopWhen:
isStepCount(maxIterations)` and make the gate chain the `toolApproval`
callback everywhere; single unified approval story.

- **+** One code path; unlocks per-step SDK features (timeouts, `prepareStep`,
  drift detection) as a side effect.
- **−** This is a **runner rewrite, not an approval port**. `run()`'s
  per-iteration event scaffolding (iteration.start/end, llm.start/end,
  verbatim message append `:831`, terminal-tool exit `:705-766`, bounded
  completion `:768-820`, cancel-and-return `#341` semantics) would need
  faithful reconstruction from `onStepEnd`/steps — every exporter, the
  collector, and the dashboard trace view consume that event ordering today.
- **−** The T0-1 gate-allow regression test (`agent-runner.test.ts:638-686`)
  and the gate-integration suite (`:608-698`) exist precisely because SDK
  auto-looping once bypassed gates. Rewriting them alongside the mechanism
  they guard destroys their regression value.
- **−** Nothing in #389's acceptance requires it.

### Option C (recommended) — Option A's scope + a real mechanism upgrade on the capable path

Same scope as A, but on the capable path **move the gate evaluation out of
`execute` and into the `toolApproval` callback**:

```
toolApproval: async ({ toolCall }) => {
  const evaluation = await bus.evaluateIntent(intentFrom(toolCall));
  return evaluation.outcome === "allow"
    ? { type: "approved", ... }
    : { type: "denied", reason: evaluation.reason };
}
```

- The callback **awaits the gate chain in-process** — including a live human
  via the existing `PendingInputRegistry` round-trip — and returns
  `approved`/`denied`. It **never returns `'user-approval'`**, so the SDK loop
  never pauses, no approval ever round-trips through a client, and the
  HMAC/revalidation machinery is (correctly) unused.
- Denials become native: the model receives `tool-output-denied` with the
  gate's reason and the loop continues (verified `index.js:5717-5723`) —
  strictly better than today's `ToolCallBlocked`-throw-as-tool-error.
- The gate chain still runs **exactly once per tool call, before execution**;
  the bus still emits `gate.decision` / `tool.rejected` / `input.request`
  exactly as before, because `evaluateIntent` is the same entry point.
- `run()`/`stream()` untouched; the invariant comment gets a scope note.

**Why not A-as-written?** A would leave the capable path's gate check inside
`execute` and bolt `toolApproval` on top — the chain would then run **twice**
per call (once in the callback, once in `execute`), double-prompting humans
and double-counting audit. Moving the evaluation is the *minimal correct*
integration, not an embellishment.

**Recommendation: C.** B is real and desirable but is its own epic (an ADR +
staged rewrite), not a rider on an approval port. C delivers the issue's
acceptance criteria with a test-preserving blast radius.

## Approach (assumes C)

1. **Bridge** (`agent-runtime/src/runner/tool-approval-bridge.ts`, new): a
   factory `createGateToolApproval(ctx)` returning a
   `GenericToolApprovalFunction` that
   - builds a `ToolCallIntent` from the SDK's `toolCall` — **using the SDK's
     own `toolCallId`** (today `convertExecutableTools` generates a fresh id at
     `:986`, orphaning correlation; the SDK id is what appears in
     approval parts and `ToolExecutionOptions`);
   - emits `agent.tool.approval.request` (new event) before evaluating;
   - awaits `bus.evaluateIntent(intent)` (human-capable via the approval
     gate's own `approvalFn`);
   - emits `agent.tool.approval.response` with
     `{approved, reason?, settledBy, decisionKind?}` from the `GateEvaluation`;
   - returns `{type: "approved"|"denied", reason?}`.
   Note: the bus's own `gate.decision`/`tool.rejected`/`input.request`
   emissions continue unchanged — the new pair adds the *SDK-approval* framing
   (requested/granted/denied) the issue asks for, keyed by `toolCallId`.
2. **Capable path rewiring** (`agent-runner.ts`):
   - pass `toolApproval: createGateToolApproval(...)` to the capable-path
     `generateText` call (`:1155-1165`);
   - delete the `emitIntent` + `ToolCallBlocked` throw from
     `convertExecutableTools.execute` (`:979-991`) **on this path only** —
     `execute` keeps `tool.start`/`tool.end` emission and executor dispatch;
     take `ToolExecutionOptions` as `execute`'s 2nd arg to reuse the SDK
     `toolCallId` for span anchoring (preserving the #102 `spanId ===
     toolCallId` invariant, `:965-978`);
   - a **modify** gate result (`rewriteInput`) cannot rewrite the call through
     `toolApproval` (the SDK API has no rewrite affordance) — the bridge maps
     `modify` to `approved` and passes the rewritten args to `execute` via a
     per-`toolCallId` overlay map owned by the bridge (checked in `execute`
     before dispatch). Trail/audit already record the modification.
3. **Events** (`agent-runtime/src/events/types.ts`): two new event interfaces,
   `ToolApprovalRequestEvent` (`agent.tool.approval.request`: toolCallId,
   toolName, arguments) and `ToolApprovalResponseEvent`
   (`agent.tool.approval.response`: toolCallId, toolName, approved, reason?,
   settledBy, decisionKind?). Register in the `AgentEvent` union (`:530-560`)
   and `event-profiles.ts` (alongside `input.request`/`gate.decision`,
   `:36-108`).
4. **SSE** (`transport/sse-formatter.ts`): wire names
   `tool.approval.request` / `tool.approval.response` — add to the
   `SSEEventName` union (`:116-125`), `SSE_WIRE_EVENT_NAMES` (`:166-183`,
   compile-time exhaustiveness enforced), the format switch (pattern:
   `input.request` case `:295-305`), and the name map (`:597-605`).
5. **Dashboard** (`agent-dashboard/src`): mirror the two names in
   `api/sse-events.ts` (union + names array `:292-301`), add `TYPE_TONES`
   entries in `EventStream.tsx` (`:16-39`; request → `warn`, response →
   `ok`/`err` by payload). The interactive approval card needs **no change**
   — it already rides `input.request` (kind `approval`) + `input-responder.ts`.
6. **`tool-output-denied` / `tool-approval-request` stream parts in
   `stream()`'s drain switch** (`agent-runner.ts:1474+`): add explicit cases
   that map to the new events *defensively*. Under C they are unreachable
   today (stream() passes no `toolApproval`) but they future-proof any
   SDK-driven streaming path and satisfy the acceptance wording; a one-line
   comment marks them as such.
7. **Server**: no route changes. `experimental_toolApprovalSecret` is **not
   adopted** (see HMAC verdict). `ServerConfig` untouched.

## HMAC verdict (issue: "Evaluate HMAC-signed approvals for the server path")

**Not applicable under C — do not adopt.** The signature exists to
authenticate an approval response that leaves the trust boundary between two
SDK calls (`'user-approval'` pause → untrusted client → resume). Under C the
decision authority is the in-process `PendingInputRegistry` promise; the
client transmits only `{correlation_id, decision}` to an authenticated route,
and no `ToolApprovalResponse` message is ever constructed from client data.
Verified: signing/verification code (`index.js:4913-5005`) is unreachable when
the callback never returns `'user-approval'`. Adopt the secret if and when a
pause/resume shape ships (Option B follow-up, or a serverless deployment where
the run cannot stay resident). Record this in the code comment on the bridge.

## Behavior-regression guarantees

- `run()`/`stream()`/tier-1+2 `runStructured()`: **byte-identical code paths**.
  Guarded by: gate integration suite (`agent-runner.test.ts:608-698`, incl.
  the T0-1 gate-allow regression `:638`), gates unit suite
  (`gates/__tests__/gates.test.ts`, 313 lines), stream suite
  (`agent-runner-stream.test.ts`) — all must pass unmodified.
- Capable path invariants preserved: gate runs once per call, before
  execution, via `evaluateIntent` (audit phase + `gate.decision` +
  `tool.rejected` semantics unchanged, `agent-event-bus.ts:96-186`).
- Capable path deliberate change (call out in PR): a denied call now yields
  `tool-output-denied` to the model and the loop continues, instead of a
  `tool-error` part from the `ToolCallBlocked` throw. No existing test asserts
  the old shape (verified: no capable-path block test exists); the new tests
  pin the new shape.

## Tests / Acceptance

1. Bridge: allow → `approved` + response event `{approved: true}`; block →
   `denied` with gate reason; modify → `approved` + overlay delivers rewritten
   args to `execute`; human-gate path → `input.request` still published once
   (dedupe by SDK `toolCallId` — the double-check memo in
   `interaction/approval-gate.ts:56-61` keys on it).
2. Capable path (MockLanguageModelV4, gpt-4o id): denied tool → model receives
   denial, loop continues, run completes; approval events appear in order
   `approval.request → gate.decision → approval.response → (tool.start …)`.
3. Event → SSE: formatter round-trips both new events (name + payload).
4. Regression: full existing suite green with zero test-file edits outside
   the new blocks.

## Open questions

1. Should the response event carry the SDK `approvalId`/`signature`? Under C
   they are synthesized after the callback resolves, so the bridge can't know
   them in real time; recovering them requires a post-call scan of
   `steps[].content`. Proposed: omit in v1, correlate by `toolCallId`.
2. Should `HumanApprovalGate`'s `allowSession` decision kind auto-approve
   subsequent calls of the same tool on the capable path (session grant)? The
   bridge sees `decisionKind` and could memoize. Proposed: out of scope for
   #389; file as follow-up.
3. Option B (SDK owns all loops) — file as an ADR candidate post-#390 rather
   than a tracker issue now?
