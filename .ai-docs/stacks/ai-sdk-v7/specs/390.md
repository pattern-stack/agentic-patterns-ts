# Spec — Model capability map: Zod-schema'd per-provider/model capabilities with verified provenance

All line numbers cite `origin/main` @ `0551140` (post-#386/#387/#388: `ai@7.0.0^`,
lockstep 0.34.0). Branch off `origin/main` — the full v7 stack is the base.

## Goal

Today the runtime's only model-capability knowledge is one hardcoded boolean
function: `modelSupportsToolsWithStructuredOutput()`
(`packages/agent-runtime/src/runner/agent-runner.ts:123-136`) — three prefix
checks (`gpt-4o*`, `gpt-5*`, `gemini-3.5-flash`), "conservative, additive,
empirically seeded", answering exactly one question (single-call tools +
`Output.object`). Everything else the runtime might want to know — does this
model accept `strict` json-schema mode, native structured output at all, tool
`inputExamples`, which reasoning-effort levels — is unrepresented, and the one
adjacent knob that exists (`GatewayConfig.supportsStructuredOutputs`,
`src/providers/model-resolver.ts:192`, consumed at `:434`) is a property of a
gateway, not a model.

Replace that scattered knowledge with **one Zod-schema'd capability map exported
from the providers layer** (`src/providers/capabilities.ts`), consulted by
`runStructured()` for path selection and advisory warnings. The map's defining
property, per the issue: **every capability value carries provenance** —
`verifiedBy: docs | probe | unverified` — so an unknown is an explicit
`"unknown"`, never a guess. Correctness must continue to never depend on the map
(the 2-tier fallback at `agent-runner.ts:1196-1274` stays the always-correct
path); the map only saves round-trips and warns early.

## Current state, traced

1. **Path selection** — `runStructured()` (`agent-runner.ts:1064`) branches
   three ways at `:1136-1197`: no-tools → single `Output.object`; tools +
   `modelSupportsToolsWithStructuredOutput(modelName)` → single-call SDK loop;
   otherwise → 2-tier fallback. The capability check is called at `:1149` with
   the *resolved* model id (`model.modelId`), after gateway-prefix stripping
   inside the function (`:129`, split on `/` only, NOT `:` — a load-bearing
   subtlety to preserve).
2. **Public surface** — the function is exported from `runner/index.ts:4`;
   removing it is a breaking change. Extend-and-delegate, don't delete.
3. **Warning precedent** — `schema-guard.ts` (`guardOpenObjectSchemas`, called
   at `agent-runner.ts:1075`) establishes the advisory idiom: fail-loud error
   by default where silence would corrupt, `console.warn` **once per schema**
   via a `WeakSet` (`schema-guard.ts:206-222`) when downgraded. The capability
   advisories reuse this once-per-key `console.warn` idiom — no new event type
   (rationale in Design §D4).
4. **Provider registry** — nine adapters, each a `ProviderProtocol`
   (`providers/types.ts:41-56`) with `tiers` + `envVars` + `load()`; registry
   `PROVIDERS` at `providers/index.ts:48`. The map keys off these nine plus the
   family-rule patterns already proven in `model-resolver.ts:206-212`
   (`FAMILY_RULES` / `inferProvider`).
5. **Reasoning-effort vocabulary** — V4 CallOptions define
   `reasoning?: 'provider-default'|'none'|'minimal'|'low'|'medium'|'high'|'xhigh'`
   (understanding.md §"Provider spec V2→V4", verified against published d.ts).
   Tool `strict` / `inputExamples` are likewise V4-era inputs (understanding.md
   fact 1). The map's enums mirror these SDK vocabularies exactly — we advise on
   SDK-level knobs, not provider-native spellings.

## Design

### D1 — Schema shape (`src/providers/capabilities.ts`, new)

Zod-first per repo convention (schema, then `z.infer<>`), `Object.freeze` on the
exported const. Sketch of the shape (signatures, not code):

```
VerificationSchema   = z.enum(["docs", "probe", "unverified"])
SupportSchema        = z.enum(["yes", "no", "unknown"])
ReasoningEffortSchema = z.enum(["none","minimal","low","medium","high","xhigh"])   // V4 vocabulary minus 'provider-default' (that's a request, not a capability)

CapabilityValueSchema = z.object({
  support:      SupportSchema,
  verifiedBy:   VerificationSchema,
  lastVerified: z.string().optional(),          // ISO date; required when verifiedBy !== "unverified" (refine)
  note:         z.string().optional(),
}).strict()
  .refine(v => (v.support === "unknown") === (v.verifiedBy === "unverified"))
  // ^ the honesty invariant: a claimed yes/no MUST name its evidence + date;
  //   an unverified entry MUST say "unknown". No guessed booleans can typecheck past parse.

ModelCapabilitiesSchema = z.object({
  provider: z.enum(PROFILE_PROVIDERS),          // reuse model-resolver.ts:84
  match:    z.string(),                          // bare-id prefix, matched longest-first (e.g. "gpt-4o", "claude-", "gemini-2.5-")
  structuredOutput:          CapabilityValueSchema,   // native json-schema response_format / Output.object without tools
  strictSchemaMode:          CapabilityValueSchema,   // `strict` json-schema enforcement (tool + response_format)
  toolsWithStructuredOutput: CapabilityValueSchema,   // single-call tools + Output.object (subsumes today's table)
  inputExamples:             CapabilityValueSchema,   // tool inputExamples honored (not stripped)
  reasoningEffort: z.object({
    levels:     z.array(ReasoningEffortSchema),       // [] = none supported
    verifiedBy: VerificationSchema,
    lastVerified: z.string().optional(),
  }).strict(),
}).strict()

MODEL_CAPABILITIES: readonly ModelCapabilities[]     // frozen, parsed at module load (dev-time self-validation)
```

Lookup:

```
getModelCapabilities(modelId: string): ModelCapabilities | undefined
```

- Normalizes exactly as `agent-runner.ts:124-129` does today (lowercase; strip
  gateway prefix by splitting on `/` only — move that logic here as a shared
  `bareModelId()` helper so there is one copy).
- Longest-`match`-prefix wins (so `gpt-4o` beats a hypothetical `gpt-` entry).
- No match → `undefined`. Callers treat `undefined` as "unknown model — take the
  conservative path, optionally warn". **No default entry, no guessing.**

Per-family granularity (matching `FAMILY_RULES` philosophy at
`model-resolver.ts:199-212`): entries are model-*family* rows (e.g. `gpt-4o`,
`gpt-5`, `o4-`, `claude-`, `gemini-2.5-`, `gemini-3.5-flash`, `grok-4`,
`deepseek-reasoner`, `mistral-large`, tier defaults for groq/ollama/openrouter),
seeded from each adapter's `tiers` map (nine adapters, e.g. `openai.ts:5-9`,
`anthropic.ts:5-9`) — those are the ids the runtime actually dispatches by
default, so they are the verification targets that matter first.

### D2 — Consultation: `runStructured()` and the legacy function

- `modelSupportsToolsWithStructuredOutput()` (`agent-runner.ts:123`) becomes a
  one-line delegate: `getModelCapabilities(id)?.toolsWithStructuredOutput.support === "yes"`.
  Semantics preserved exactly: unknown/`undefined`/`"no"` → `false` → 2-tier
  model-safe path. Export kept (`runner/index.ts:4`), JSDoc-deprecated pointing
  at the map. The three families currently returning `true` seed the map as
  `{support: "yes", verifiedBy: "probe"}` with the original DESIGN §9.5
  empirical date — no behavior change on day one.
- New advisory hook in `runStructured()` immediately after model resolution
  (`agent-runner.ts:1099`, next to the `guardOpenObjectSchemas` precedent at
  `:1075`): call a new `adviseStructuredRun(modelId)` (lives in
  `capabilities.ts`) that warns when:
  - `structuredOutput.support === "no"` — "model <id> is marked as not
    supporting native structured output (verified <how>, <date>); expect the
    2-tier fallback / possible 'No object generated'";
  - entry is `undefined` or relevant value `"unknown"` — one-line "capabilities
    unverified for <id>; taking conservative path" (helps the human know the map
    wants extending — this is the anti-staleness feedback loop, D5).
- **Gateway interplay unchanged**: `GatewayConfig.supportsStructuredOutputs`
  (`model-resolver.ts:192`) remains a (gateway × upstream) property and still
  gates whether the SDK *sends* the schema (`:434`). The map speaks about the
  *model*; the gateway flag about the *pipe*. `adviseStructuredRun` needs no
  gateway awareness because it already sees the bare id post-strip.
- **model-resolver stays pure** — it builds models, it doesn't judge them. The
  map lives beside it in `providers/` and is exported through
  `providers/index.ts`; the runner (layer 7) already imports from providers, so
  no layer-rule violation. Core untouched.

### D3 — What this issue does NOT do

- No automatic path *promotion* from the map beyond what the boolean already
  does (i.e. we don't start sending `strict`/`inputExamples`/`reasoning` based
  on map entries — that's the V4-inputs adoption work, coupled to #387's
  follow-ups). This issue is the *advisory substrate*: shape, data, warnings,
  and the one existing selection point rewired.
- No new event type for advisories (D4). No dashboard surface.
- No capability claims for the `ClaudeCodeLanguageModel` path (`claude-code.ts`)
  beyond an `unverified` row — its capabilities are harness-mediated, a
  different axis.

### D4 — Advisory mechanism: `console.warn`, once per (model × capability)

Follows `schema-guard.ts:206-222` exactly (module-level `Set<string>` keyed
`"<bareId>:<capability>"`, `[agentic-patterns]` prefix). Rationale for not
minting an `agent.warning` event: the event vocabulary change would ripple
through SSE/exporters/dashboard (cf. #388's five-file fan-out) for a message
whose audience is the developer at the console, and the acceptance bar is
"clear advisory warning, not silent failure" — which `console.warn` meets with
zero surface growth. If a structured-events need emerges, that's a follow-up.

## Verification methodology (the research deliverable)

Two evidence classes, honestly separated:

**Docs/typings-verifiable (`verifiedBy: "docs"`)** — properties of the SDK
adapter or officially documented model behavior:
- Whether each `@ai-sdk/*` provider package *sends* json-schema
  `response_format` / supports `strict` provider options / exposes
  reasoning-effort options — readable from the published d.ts + provider README
  (same method understanding.md used; cite package@version + docs URL in the
  entry's `note`).
- OpenAI structured-outputs + strict model list, Google `responseSchema`
  support, Anthropic (no native json-schema response format; ai-sdk emulates
  via forced tool), DeepSeek/Groq/Mistral/xAI json-mode docs.
- Reasoning: OpenAI o-/gpt-5-series effort levels, Anthropic extended thinking,
  DeepSeek reasoner, Gemini thinking — docs give the supported-level sets.

**Probe-required (`verifiedBy: "probe"`)** — server-side behaviors invisible to
typings; docs are frequently stale or aspirational here:
- Single-call **tools + `Output.object`** round-trip (the existing table was
  empirically seeded for exactly this reason — `agent-runner.ts:115-118`
  "empirically seeded (DESIGN §9.5)").
- **strict mode actually accepted** (servers 400 on unsupported models).
- **`inputExamples` honored vs silently stripped** (pure probe; no doc source
  is trustworthy).
- Open-object silent-`{}` decode class of bugs (schema-guard's origin story).

**Probe harness**: `scripts/probe-capabilities.mjs` (sibling of
`scripts/runner-side-by-side.mjs`). Per provider whose env key is set, run a
minimal matrix against that provider's `tiers` defaults (cheapest first): (a)
no-tools `Output.object` closed schema; (b) tools + `Output.object` single
call; (c) same with `strict`; (d) `reasoning` effort ladder probe. Output: a
table of `{provider, model, capability, outcome, date}` for transcription into
`MODEL_CAPABILITIES` (the map stays code — reviewable, typed, frozen — the
probe output is evidence, not a generated artifact). Budget: haiku-tier models,
tiny schemas; single-digit cents per full run.

**Keys per probe** (catalogued in `.env.example` "#390 live capability probes"
section): `OPENAI_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`,
`OPENROUTER_API_KEY`, `XAI_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY`,
`DEEPSEEK_API_KEY`; `ANTHROPIC_API_KEY` direct (note the CC-billing caveat in
`.env.example`); `OLLAMA_HOST` (keyless, local — probe only if reachable);
gateway probes via `AP_GATEWAY_BASE_URL` are **out of scope** (gateway capability
is a pipe property, D2). The script skips-and-reports providers without keys —
their entries ship `verifiedBy: "unverified", support: "unknown"` and the
runtime says so at use time. **OpenRouter special case**: capabilities are
(route × upstream)-dependent; probe only the pinned tier defaults
(`openrouter.ts:5-9`, all `anthropic/claude-*`) and mark everything else
unknown.

## Maintenance story (how the map stays honest)

A stale map is worse than none, so staleness is made *visible* at three layers:

1. **Provenance in the data** — every value carries `verifiedBy` +
   `lastVerified` (schema-enforced, D1 refine). Reviewing a map PR means
   reviewing evidence, not vibes.
2. **Re-runnable probe with drift detection** — `probe-capabilities.mjs
   --check` compares live outcomes against the current map and exits non-zero
   on drift, printing the delta row-by-row. Also warns on any entry whose
   `lastVerified` is >180 days old. New-model onboarding = add the id to the
   matrix, run, transcribe.
3. **CI-optional job** — `.github/workflows/probe-capabilities.yml`:
   `workflow_dispatch` + monthly `schedule` cron, runs `--check` with whichever
   provider secrets the repo has, `continue-on-error` and **not** part of the
   required `check` status (external API flakiness must never block merges).
   On drift it fails visibly in the Actions tab; wiring "auto-open an issue on
   drift" is a nice-to-have the implementer may include if trivial.
4. **Runtime feedback loop** — the `"unknown"` advisory (D2) means every run on
   an unmapped model nudges toward extending the map, instead of silently
   taking the slow path forever.

## Open questions (for Gate 1 review)

1. **Advisory channel** — is `console.warn` (schema-guard precedent, D4)
   acceptable, or does the human want an `agent.warning` event now despite the
   SSE/exporter/dashboard fan-out cost?
2. **Probe spend approval** — live probes hit seven paid APIs (cents, not
   dollars). Run them during implementation for full `verifiedBy: "probe"`
   coverage, or ship docs-verified + unverified rows first and probe in a
   follow-up pass?
3. **Reasoning-levels granularity** — per-family level *sets* (D1) vs a simpler
   `supportsReasoningEffort: yes/no/unknown`. Sets are more useful for the
   eventual V4-inputs adoption but cost more verification; the spec proposes
   sets with most rows starting `unverified`.
