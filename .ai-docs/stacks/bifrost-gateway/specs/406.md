# Spec — Bifrost gateway injection: virtual keys, guardrail selection, run correlation

## Goal

Extend the gateway path so a governed Bifrost instance is usable end-to-end:

1. **Virtual key** — `AP_GATEWAY_VIRTUAL_KEY` / `GatewayConfig.virtualKey` →
   `x-bf-vk` header on every gateway request. A governed Bifrost 401s
   (`{"type":"virtual_key_required"}`) on ALL endpoints without it — this is the
   entry ticket, not an option.
2. **Guardrail selection** — `AP_GATEWAY_GUARDRAIL_IDS` /
   `GatewayConfig.guardrailIds` → `x-bf-guardrail-ids` header (comma list),
   with a per-run override seam ("which Presidio profile applies to this run").
3. **Run correlation** — runId / agent name / traceId propagated as
   `x-request-id` + `x-bf-dim-*` headers per request, so the gateway's
   /workspace/logs UI is filterable by our runs (also where Bifrost keeps
   redaction mappings for reveal — #407's raw material).

Hard invariant: **non-Bifrost gateways are byte-for-byte unaffected when the new
config is unset.** The current no-headers construction path must not change shape
when nothing new is configured.

## Approach

Two mechanisms, split by lifetime:

**A. Static injection (vk + default guardrails) — provider-creation time.**
`buildFromGateway` (`packages/agent-runtime/src/providers/model-resolver.ts:410-433`)
already passes `gw.headers` into `createOpenAICompatible` (`:426`). Derive
`x-bf-vk` and `x-bf-guardrail-ids` from the new `GatewayConfig` fields and merge
them UNDER the user's explicit `gw.headers` (explicit wins). These values are
per-gateway constants, so static provider headers are the right home. Models are
memoised per id (`model-resolver.ts:243-244, 278-287`) — static headers ride the
cache correctly.

**B. Per-request injection (correlation dims + per-run guardrail override) —
call time.** Verified on main's actual dependency graph
(`@ai-sdk/openai-compatible@3.0.14`, `ai@7.0.37`, `bun.lock:172`):

- `ai@7`'s `generateText`/`streamText` accept a per-call `headers` option
  ("Additional HTTP headers to be sent with the request") that flows into
  `LanguageModelV4CallOptions.headers`.
- `@ai-sdk/openai-compatible@3` merges them per request:
  `combineHeaders(this.config.headers?.(), options.headers)` (dist/index.js:625
  chat doGenerate, :710 doStream) — **per-call wins over provider-static on key
  collision**. This is the precedence backbone: RunOptions override > runner
  factory > static gateway config.

So per-request dims are fully achievable — no "static-only" limitation to flag.
`AgentRunner` currently passes no `headers` at any of its 5 provider call sites
(`agent-runner.ts:500, 1180, 1214, 1326, 1521`); we thread them through:

- A generic, gateway-agnostic seam on the runner: an optional
  `requestHeaders` **factory** (3rd constructor arg, backwards-compatible with
  `constructor(model, eventBus?)` at `agent-runner.ts:190`) receiving per-run
  context `{ runId, traceId, agentName, modelId, modelProvider }` — because
  `runId` is minted INSIDE `run()` (`generateId()` at `agent-runner.ts:385`)
  and is unknowable to the caller.
- A generic per-run seam on `RunOptions`: `requestHeaders?: Readonly<Record<string,
  string>>` (merged over the factory's output) — this is the per-run guardrail
  override: pass `{ "x-bf-guardrail-ids": "pii-strict" }` for one run and
  combineHeaders makes it beat the gateway-level default.
- All Bifrost naming lives in a new small module
  `packages/agent-runtime/src/providers/bifrost.ts` (header-name constants, the
  correlation factory, a caller-facing `bifrostRunHeaders()` helper). The runner
  and `GatewayConfig` stay vendor-generic; #407's response-side helpers get a
  natural home.
- `createRunner` wires the factory automatically whenever a gateway is
  configured (`create-runner.ts:221-237` builds `new AgentRunner(resolver,
  opts.eventBus)` at `:229` today). The factory **self-gates on
  `ctx.modelProvider`**: gateway-built models carry provider `"gateway.chat"`
  (from `name: "gateway"` at `model-resolver.ts:423`), so profile-pinned ids
  that escape-hatch to a direct provider (`model-resolver.ts:289-292`) never
  receive `x-bf-*` headers.

**Auth precedence (vk vs Basic/bearer).** They are orthogonal layers, not
alternatives: `Authorization` (Basic per `create-runner.ts:163-170`, or Bearer
via `apiKey`) is transport/proxy auth; `x-bf-vk` is Bifrost governance. When both
are configured, both are sent — a Basic-fronted Bifrost needs exactly that. For a
vk-only governed Bifrost, `x-bf-vk` alone suffices (no `apiKey` needed;
`buildFromGateway:418` already omits `Authorization` when unset). Bifrost also
accepts `Authorization: Bearer vk-*`, but we do NOT auto-map `virtualKey` into
`Authorization` — the `x-bf-vk` header is canonical and keeps `Authorization`
free for a fronting proxy. Document this in the `virtualKey` JSDoc and
`.env.example`; no mapping code.

**#407 anticipation (design-only, no code here).** Keep `buildFromGateway`'s
provider-settings object a single literal so #407 can add
`metadataExtractor` (a first-class `createOpenAICompatible` setting in v3) as a
one-key change; response-side helpers land in `bifrost.ts`. Nothing else.

## File-level plan

### 1. `packages/agent-runtime/src/providers/bifrost.ts` — NEW (~90 lines + docs)

All Bifrost-specific naming, in one place:

- `BIFROST_VK_HEADER = "x-bf-vk"`, `BIFROST_GUARDRAILS_HEADER =
  "x-bf-guardrail-ids"`, `BIFROST_DIM_PREFIX = "x-bf-dim-"`,
  `REQUEST_ID_HEADER = "x-request-id"`.
- `sanitizeHeaderValue(v: string): string` — header values must be ASCII-safe
  (agent role names are arbitrary strings, `AgentLike.role.name` at
  `runner/types.ts:28`): replace chars outside printable ASCII (0x20–0x7E) with
  `-`, collapse runs, trim, cap at 128 chars.
- `bifrostCorrelationHeaders(ctx: RunHeadersContext): Record<string, string>` —
  the factory `createRunner` wires. Returns `{}` unless
  `ctx.modelProvider?.startsWith("gateway")`. Otherwise:
  `x-request-id: runId`, `x-bf-dim-agent: sanitize(agentName)`,
  `x-bf-dim-run: runId`, plus `x-bf-dim-trace: traceId` only when
  `traceId !== runId` (`effectiveTraceId` defaults to runId at
  `agent-runner.ts:386` — omit the redundant dim).
- `bifrostRunHeaders(opts: { guardrailIds?: readonly string[]; dims?:
  Readonly<Record<string, string>> }): Record<string, string>` — caller-facing
  composer for `RunOptions.requestHeaders` (joins guardrail ids with `,`;
  prefixes each `dims` key with `x-bf-dim-` and sanitizes values). Callers use
  this for per-run guardrail overrides without memorizing header names.

### 2. `packages/agent-runtime/src/providers/model-resolver.ts` — modify

- `GatewayConfig` (`:128-192`): add three readonly optional fields after
  `apiKeyEnv`/`headers` (`:130-136`):
  - `virtualKey?: string` — inline vk. JSDoc: what it is, 401 behavior of a
    governed Bifrost, canonical-header-vs-`Bearer vk-*` note, orthogonality to
    `Authorization`. Env: `AP_GATEWAY_VIRTUAL_KEY`.
  - `virtualKeyEnv?: string` — mirror of `apiKeyEnv` (`:134`), read at resolve
    time; the vk is a secret and belongs out of config files.
  - `guardrailIds?: readonly string[]` — default guardrail profile ids sent as
    `x-bf-guardrail-ids` on every request through this gateway; per-run
    override via `RunOptions.requestHeaders` / `bifrostRunHeaders`. Env:
    `AP_GATEWAY_GUARDRAIL_IDS` (comma list).
- `buildFromGateway` (`:410-433`): resolve
  `const vk = gw.virtualKey ?? (gw.virtualKeyEnv ? process.env[gw.virtualKeyEnv] : undefined)`
  (same pattern as `apiKey` at `:417`); build a `derived` headers object (vk +
  joined guardrails, each key only when configured); pass
  `headers: { ...derived, ...gw.headers }` and keep the existing conditional
  spread shape so **no `headers` key is passed at all when neither derived nor
  `gw.headers` exist** (preserves today's construction byte-for-byte for
  non-Bifrost gateways). Explicit `gw.headers` spread LAST — a user's literal
  `x-bf-vk` wins over the derived one.

### 3. `packages/agent-runtime/src/runner/types.ts` — modify

- `RunOptions` (`:125-236`): add
  `requestHeaders?: Readonly<Record<string, string | undefined>>` — per-run HTTP
  headers forwarded to every provider call this run makes; merged over any
  runner-level `requestHeaders` factory output; per-call headers beat
  provider-static headers downstream (openai-compatible `combineHeaders`), so
  this is the per-run override seam for e.g. `x-bf-guardrail-ids`. Inert for
  non-HTTP providers (SDK contract).

### 4. `packages/agent-runtime/src/runner/agent-runner.ts` — modify

- New exported types near the top:
  `RunHeadersContext = { runId: string; traceId: string; agentName: string;
  modelId: string | undefined; modelProvider: string }` and
  `AgentRunnerOptions = { requestHeaders?: (ctx: RunHeadersContext) =>

- Constructor (`:190`): add optional 3rd param `opts?: AgentRunnerOptions`;

- Private helper `_callHeaders(ctx, options)`: returns
  `{ ...this._requestHeaders?.(ctx), ...options?.requestHeaders }`, or

## Explicitly out of scope — do not touch

- **#407's response side**: no `metadataExtractor`, no response-header/body
  capture, no redaction-reveal, no event-bus surfacing of gateway metadata.
- **Model discovery**: `/v1/models` returns `{"data":[]}` on governed instances
  even with a valid vk + `x-bf-list-models-provider` — build nothing on it.
- **Auto-mapping vk → `Authorization: Bearer vk-*`**: documented, not coded.
- **`AP_GATEWAY_MODEL_PREFIX` machinery**: bare ids not auto-resolving on
  governed Bifrost is already served by existing prefix/`auto` support
  (`toGatewayModelId`, `model-resolver.ts:364-379`) — no changes.
- **CLI interactive gateway wizard** (`agent-cli/src/services/execution-service.ts:244-283`):
  prompting for vk there is a nice-to-have; the `config.ts` key list is enough
  for this PR.
- Honoring `RunOptions.runId` in `AgentRunner` (it mints its own; see Open
  questions).

```ts

export const BIFROST_VK_HEADER = "x-bf-vk";
export const BIFROST_GUARDRAILS_HEADER = "x-bf-guardrail-ids";

  guardrailIds?: readonly string[];
  dims?: Readonly<Record<string, string>>;

// runner/agent-runner.ts
export interface RunHeadersContext {
  runId: string; traceId: string; agentName: string;
  modelId: string | undefined; modelProvider: string;
}
export interface AgentRunnerOptions {
  requestHeaders?: (ctx: RunHeadersContext) => Record<string, string | undefined>;
}
// constructor(model, eventBus?, opts?: AgentRunnerOptions)

// runner/types.ts — RunOptions addition
requestHeaders?: Readonly<Record<string, string | undefined>>;
```

Merge precedence (highest wins): `RunOptions.requestHeaders` → runner factory
(`bifrostCorrelationHeaders`) → explicit `GatewayConfig.headers` → derived
vk/guardrail headers → `apiKey` Bearer. (First two merge at the call site; last
three at provider creation; per-call beats static via openai-compatible
`combineHeaders`.)

## Open questions

1. **Dims on non-Bifrost gateways.** The correlation factory fires for any
   gateway-built model (it gates on provider `"gateway.chat"`, not on
   Bifrost-ness). `x-bf-dim-*` on LiteLLM/OpenRouter is inert but visible.
   Gating on `virtualKey` instead was rejected: a Basic-fronted ungoverned
   Bifrost (the pre-vk deployment shape) would silently lose correlation.
   Accepting inert headers is the lesser evil; revisit if a gateway ever
   rejects unknown `x-*` headers.
2. **`RunOptions.runId` vs minted runId.** `AgentRunner` mints its own runId
   (`agent-runner.ts:385`; the `RunOptions.runId` JSDoc at `types.ts:137-141`
   documents this asymmetry from #226). Correlation headers use the minted id —
   consistent with what events carry. Honoring `options.runId` would align
   NodeBackedRunner and AgentRunner but touches event identity; deferred,
   possibly to #407 where cross-referencing gateway logs against event streams
   makes it matter.
3. **Sanitization policy** (proposed: printable-ASCII, `-` replacement, 128-char
   cap) — implementer may adjust the cap; keep it deterministic and tested.
