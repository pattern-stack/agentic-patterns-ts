# Spec — capture-from-session (#140, E5d)

## Goal

ADK's lowest-friction way to grow a gold set: "Add current conversation as an
eval case." `POST /eval/cases/from-session {conversationId, setId, …}` reads
one exchange out of a **live** server-side conversation (the in-process
registry `conversationRoutes` already uses), maps it to a `StoredEvalCase` —
`input` = that exchange's user message, `expected` = seeded from the actual
assistant answer, client-editable before submit (§9) — and lands it in the
chosen set via `EvalStore.upsertEvalCase`, `split` defaulting `train`.
Capturing the same exchange twice is **idempotent by construction**: the
server derives a deterministic `caseId` from the session, so the second
capture updates the same `(set_id, case_id)` row (201 vs 200 makes it
visible). The dashboard grows a "Capture as eval case" affordance on the live
chat (set picker: existing set or create-new), and the captured case is
immediately browsable via the existing `GET /eval/sets/:id/cases` and runnable
by #139's `POST /eval/runs` — locked by a capture → run round-trip test.

## Approach

### Verified against the branch tip (2026-07-04, `dug/140-capture-session` @ `16263fd`, forked from `dug/139-run-from-ui` — Epic 1 + #138 compare + #139 POST/SSE present)

1. **What a session IS server-side — and an anchor drift that decides the UI
   placement.** The only conversation state this server holds is the
   per-`createServer` in-process registry `Map<string, ConversationEntry>`
   (`app.ts:26`), `ConversationEntry = { conversation: Conversation; agentId:
   string }` (`routes/conversations.ts:13-16`), today handed only to
   `conversationRoutes` (`app.ts:36`). The issue's stated dashboard anchor —
   `ConversationDetailPage.tsx` — exists but is **dormant in the playground**:
   it fetches `GET /conversations/:id`, `GET /conversations/:id/messages`,
   `GET /messages/:id/parts` (`ConversationDetailPage.tsx:64-72`), none of
   which any server route serves (grep across `agent-server/src/routes/` = 0
   hits; the `api/types.ts:74-78` comment attributes them to "Team 2's"
   Drizzle server). Likewise `ConversationsPage` reads `/admin/conversations`,
   which `routes/admin.ts` does not mount. The **functioning** live-session
   surface is `ChatPage` → `useChat`, which holds the registry key: `useChat`
   creates the conversation once per thread and exposes `conversationId`
   (`chat/useChat.ts:24-25, 67-74`, set from `POST /conversations`' `{id}`
   response, `conversations.ts:43`). See Decision 1.
2. **The real Exchange shape (the mapping source).** `Conversation.history:
   Exchange[]` (`conversation/conversation.ts:112-114`) where `Exchange =
   { number, invocationId, user: string, assistant: string, toolCalls,
   inputTokens, outputTokens, timestamp }` (`conversation.ts:33-42`),
   `number` 1-based in send order. Both `send()` (`:164-175`) and `stream()`
   (`:246-257`) append the exchange only **after** the turn completes —
   capture mid-stream simply doesn't see the in-flight turn. The constructor
   accepts injected `history` (`conversation.ts:78-99`) — the test fixture
   seam.
3. **The eval engine dictates the mapping.** `runEval` executes a case as ONE
   `node.run(evalCase.input, nodeCtx)` (`eval/run-eval.ts:250`) — no
   multi-turn replay exists — and the agent-target adapter **fails loud on
   non-string input** (`eval/target.ts:86-92`: "Eval agent target requires
   string input"). So a captured case must be a single-turn
   `{ input: string, expected: string }` pair — exactly one exchange. See
   Decision 2.
4. **The store surface is already idempotent — and has one clobber trap.**
   `upsertEvalCase` is `INSERT … ON CONFLICT(set_id, case_id) DO UPDATE`
   (`storage/eval-store.ts:205-213`) — a deterministic `caseId` gives us
   no-silent-dup for free (Decision 3). `upsertEvalSet` is `ON CONFLICT(id)
   DO UPDATE SET name = excluded.name, description = excluded.description`
   (`eval-store.ts:197-203`) — calling it on an **existing** set overwrites
   name/description (with `null` when omitted). The route must therefore only
   create, never re-upsert, set metadata (Decision 4). Browse/runnability both
   require the `eval_set` meta row to exist: `listEvalSets` selects FROM
   `eval_set` (`eval-store.ts:215-219`) and #139's `POST /eval/runs` 404s any
   `setId` not in that list (`routes/eval.ts:229-232`).
5. **#139's route conventions to match.** Ordered validation ladder — parse
   400s first, then 503s (`notConfigured`, `eval.ts:412-420`), then 404s with
   `hint` fields; `parseSplit` on `EvalSplitSchema` (`eval.ts:438-447`); the
   explicit-body-opt-in precedent for guarded operations (`allowTest: true`,
   hint `retry with "allowTest": true`, `eval.ts:204`). The dashboard client
   precedent is `lib/evalApi.ts`'s 503-aware `EvalFetch<T>` union
   (`evalApi.ts:1-22`), and the UI idiom is `RunLauncher`'s
   button-expands-a-form-Card, page-scoped component (`pages/eval/
   RunLauncher.tsx:1-10`).
6. **No CLI change needed.** `/eval` is already in the SPA fallback's
   `API_PREFIXES` (`agent-cli/src/commands/playground.ts:214-222`), and the
   fallback only intercepts GETs anyway (`playground.ts:239-241`). Verified —
   nothing to do.

### Decision 1 — session source: the live in-process registry; affordance on ChatPage

`evalRoutes` gains `conversations: Map<string, ConversationEntry>` in
`EvalRoutesOptions`; `app.ts` passes the same Map it already hands to
`conversationRoutes` (one line, and the Map is created two lines above the
route mounts — no ordering hazard). The capture route resolves
`conversations.get(body.conversationId)` and reads
`entry.conversation.history`.

Consequences, stated plainly:

- **Capture works for conversations live in THIS server process.** That is
  the playground's reality — the registry is in-process and conversations do
  not survive restart. An unknown id → 404 with a hint saying exactly that.
- **The dashboard affordance lands on ChatPage, not ConversationDetailPage**
  (fact 1: the detail page's data source does not exist in this server, and
  its `:id` — a Drizzle store id — would not key the live registry even if it
  loaded). ChatPage is the one view that has the live `conversationId` in
  hand. This is the ADK model too: "add **current** conversation."
  Reviving the dormant conversations read-API is out of scope (Non-goals).

### Decision 2 — mapping: one exchange per case; `input` = user message, `expected` seeded from the answer

Locked by facts 2 + 3: the engine runs a case as one string-in call, so a
capture is one `Exchange`:

| EvalCase field | Source | Notes |
|---|---|---|
| `caseId` | `session-<conversationId>-<exchange.number>` | deterministic — Decision 3; client `caseId` override is the versioning escape hatch |
| `input` | `exchange.user` (string) | **not** client-overridable — capture means the session is the source of truth for input; a different input is hand-authoring, not capture |
| `expected` | body `expected` if present, else `exchange.assistant` | §9's "seeded from the actual answer, **editable** by the client before submit" |
| `split` | body `split` if present, else `"train"` | issue acceptance + §8 |
| `tags` | body `tags` if present, else `["captured", "agent:<entry.agentId>"]` | provenance: which agent produced the seed answer; filterable in the bank |

Which exchange: **default = the first** (`history[0]`) — the doc's "input =
first user message" (§8). Body `exchange?: number` selects another by
`Exchange.number` (the class's 1-based numbering, `conversation.ts:37`). The
dashboard passes it explicitly when the user picks a turn.

Dropped by design: `toolCalls`, token counts, timestamps, the original
trace — `StoredEvalCase` (`eval-store.ts:75-81`) has no slot for them and the
eval run will produce its own fresh `runs` row + trace when executed (#139).

### Decision 3 — idempotence: deterministic `caseId` ⇒ upsert semantics; 201/200 makes re-capture visible

The `eval_case` PK is `(set_id, case_id)` and `upsertEvalCase` is a full-row
`ON CONFLICT DO UPDATE` (fact 4). The server derives
`caseId = session-<conversationId>-<exchangeNumber>` — so capturing the same
exchange into the same set twice targets the **same row**: the second capture
updates in place (typically refreshing an edited `expected`). No silent dup —
and no read-modify-write logic to get wrong.

- The response distinguishes the two: **201** when the row is new, **200**
  when it overwrote (checked via `listEvalCases(setId)` before the upsert —
  sets are UI-browse-sized; no new store method needed).
- **Rejected: `-v2` suffixing.** Auto-versioning recreates the silent-dup
  problem in a different suit — two near-identical cases silently both run in
  every subsequent suite and skew aggregates — and needs a scan-before-write.
  Deliberate versioning stays available: the client MAY pass an explicit
  `caseId` (e.g. `…-tightened`) to fork a variant on purpose.
- Same exchange into a **different set** is a different row by PK — correct
  (sets are independent banks).

### Decision 4 — set creation: explicit `createSet` opt-in; bare unknown set 404s (the #139 error-semantics style)

`POST /eval/runs` 404s an unknown set — right for *running*. Capture is an
*authoring* write and the UX explicitly wants "existing set or create-new",
so the route follows #139's **explicit-body-opt-in** precedent (`allowTest`):

- `setId` unknown + no `createSet` → **404**
  `{ error: 'eval set "<id>" not found', hint: 'retry with "createSet": {"name": …} to create it' }`.
  A typo'd `setId` never silently creates a stray set.
- `setId` unknown + `createSet: { name?, description? }` present →
  `upsertEvalSet({ id: setId, name, description })`, then proceed. The meta
  row is mandatory for browse + runnability (fact 4), so creation always
  writes it — never a bare `eval_case` row.
- `setId` **known** → `createSet` is **ignored** (never re-upserted): fact
  4's clobber trap means re-upserting an existing set would overwrite its
  name/description with this request's values (or `null`). Renaming sets is
  not capture's job.

### Decision 5 — split: default `train`; any valid split accepted on write

`split` is validated with the existing `parseSplit`/`EvalSplitSchema` helper
and defaults `"train"` (issue acceptance). No held-out guard on the write
path: §7's guard protects *selecting test cases for a run* (enforced by #139
at `POST /eval/runs`), not authoring into the bank — writing a fresh case to
`test` is legitimate curation.

### POST /eval/cases/from-session — request pipeline (ordered, the #139 ladder)

1. JSON parse failure → 400 `invalid JSON body`.
2. `conversationId` missing/empty → 400 `conversationId is required`.
3. `setId` missing/empty → 400 `setId is required`.
4. `exchange` present but not a positive integer → 400
   `invalid exchange — expected a 1-based exchange number`.
5. `expected` present but not a string → 400 `expected must be a string`.
6. `tags` present but not `string[]` → 400 `tags must be an array of strings`.
7. `split` invalid → 400 (the `parseSplit` message shape).
8. `caseId` present but not a non-empty string → 400.
9. No `evalStore` → 503 `notConfigured` (existing helper).
10. `conversations.get(conversationId)` miss → 404
    `{ error: 'conversation "<id>" not found', hint: "capture reads live conversations in this server process — start one in Chat" }`.
11. `history.length === 0` → 400 `conversation has no completed exchanges yet`
    (the #139 empty-cases 400 style; also the mid-first-stream case, fact 2).
12. Requested `exchange` number not in history → 404
    `exchange <n> not found in conversation "<id>" (has <count>)`.
13. Set existence via `listEvalSets()`: unknown → Decision 4 (404 or create).
14. `created = !listEvalCases(setId).some(r => r.caseId === caseId)`;
    `upsertEvalCase(setId, storedCase)`; respond **201/200** with
    `{ setId, caseId, created, input, expected, tags, split }` — echoing the
    stored row so the client renders exactly what the server captured (this
    echo is also the visibility mitigation for a client/server transcript
    desync — see Failure modes).

Handler stays synchronous end-to-end (better-sqlite3 is sync; no detach —
nothing long-running here).

### Dashboard — capture affordance on the live chat

New page-scoped component `pages/eval/CaptureCasePanel.tsx` (eval-domain
components stay together; the `RunLauncher` expanding-form-Card idiom, fact 5),
mounted from `ChatPage`'s `Header` next to "New Chat"
(`ChatPage.tsx:193-195`):

- **Button** "Capture eval case" — enabled when `conversationId != null &&
  exchangeCount > 0 && !streaming` (all three already computed in ChatPage,
  `ChatPage.tsx:48-52, 72-74`). Disabled tooltip explains why.
- **Form Card** (opens on click):
  - *Exchange picker* — shown only when `exchangeCount > 1`; options
    `exchange N — "<first ~48 chars of user msg>"`, default 1 (Decision 2).
    Pairs derived client-side from `chat.messages`: the Nth `role: "user"`
    message and its following assistant message's concatenated `text` parts
    (`chat/model.ts:23, 37`).
  - *Expected textarea* — seeded from the selected pair's assistant text;
    the client always sends its (possibly edited) value as `expected` (§9).
  - *Set picker* — `<select>` fed by `fetchEvalSets()` (503-aware
    `EvalFetch`, fact 5) plus a "new set…" option that reveals id + name
    inputs and sends `createSet`.
  - *Split select* — train/dev/test, default `train`.
  - Submit → new `captureFromSession(body)` in `lib/evalApi.ts` (POST,
    503-discriminated like `launchEvalRun`). Success → inline confirmation
    Card showing the echoed `caseId` + captured `input` preview and
    `created ? "created" : "updated existing case"`, with a link to `/eval`.
- Form state resets when `conversationId` changes (New Chat / agent switch).
- Lean by intent: no case-browser embed, no tag editor, no input editing.

## Interfaces

```typescript
// routes/eval.ts — options grow the registry (app.ts threads the existing Map)
export interface EvalRoutesOptions {
  readonly evalStore: EvalStore | undefined;
  readonly agents: AgentRegistration[];
  readonly eventBus: AgentEventBus;
  readonly evalExecution?: EvalExecutionConfig;
  readonly conversations?: ReadonlyMap<string, ConversationEntry>; // NEW — absent (older embedders) -> 404 on capture
}

// POST /eval/cases/from-session — request body
interface CaptureFromSessionBody {
  conversationId: string;                 // live registry key (useChat's conversationId)
  setId: string;                          // target bank
  exchange?: number;                      // Exchange.number, 1-based; default: first
  expected?: string;                      // client-edited; default: exchange.assistant
  split?: "train" | "dev" | "test";       // default "train"
  tags?: string[];                        // default ["captured", "agent:<agentId>"]
  caseId?: string;                        // explicit override — deliberate versioning
  createSet?: { name?: string; description?: string }; // opt-in auto-create (Decision 4)
}

// 201 (created) / 200 (updated existing row) — echoes the stored row
interface CaptureFromSessionResponse {
  setId: string;
  caseId: string;                         // default: `session-<conversationId>-<n>`
  created: boolean;
  input: string;                          // = exchange.user, always server-derived
  expected: string;
  tags: string[];
  split: "train" | "dev" | "test";
}
```

## Failure modes

- **Conversation restarted away / wrong id** → 404 + hint (ladder 10). The
  registry is in-process; this is the designed boundary, not a bug.
- **Aborted / partial turn as seed.** `stream()` pushes the exchange even
  when the turn errored (partial `assistant`, `conversation.ts:242-257`), and
  a client-side abort can leave the client transcript and server history
  disagreeing (the server may not have appended the aborted turn). Two
  mitigations: `expected` is human-reviewed in the textarea before submit,
  and the response echoes the server-derived `input` so any desync is visible
  immediately in the confirmation Card. Accepted residual risk for v1.
- **Set meta clobber** — prevented structurally: `upsertEvalSet` is only ever
  called when the set does not exist (Decision 4).
- **`expected: ""`** (empty answer captured) — allowed; #139's default scorer
  gates on `expected === undefined`, not `""` (`eval.ts:521-523`), so an
  empty-string expected is an intentional, editable value. The UI seeds the
  textarea so the human sees it.
- **Concurrent capture of the same exchange** — both upserts target the same
  row; last write wins; `created` may race to both-false/one-true. Harmless
  (better-sqlite3 serializes writes).

## Tests

`packages/agent-server/src/__tests__/eval-capture.test.ts` — real in-memory
SQLite `EvalStore` (the `eval-run.test.ts` harness), fixture conversations
built via `new Conversation(agent, runner, { history: [...] })` with a stub
agent/runner (never invoked — history is injected), registered in a
`Map<string, ConversationEntry>` handed to `evalRoutes`.

1. **T1 — happy path (defaults).** 2-exchange conversation; POST
   `{conversationId, setId}` (set pre-seeded) → 201; body echoes
   `caseId = session-<id>-1`, `input` = exchange 1's `user`, `expected` =
   exchange 1's `assistant`, `split: "train"`, tags
   `["captured", "agent:<agentId>"]`. Row visible via
   `GET /eval/sets/:id/cases` (route-level, not store-level).
2. **T2 — exchange selection + expected override.** `{exchange: 2, expected:
   "edited"}` → `caseId` suffix `-2`, `input` = exchange 2's user,
   `expected: "edited"`.
3. **T3 — idempotence (acceptance 3).** Same capture twice, second with
   edited `expected` → first 201 `created: true`, second 200
   `created: false`; `listEvalCases` shows exactly ONE row carrying the
   second `expected`. Explicit `caseId` override → a second, distinct row
   (deliberate versioning).
4. **T4 — set creation (Decision 4).** Unknown set, no `createSet` → 404 with
   the `createSet` hint, and NO set/case rows written. With
   `createSet: {name}` → 201; `GET /eval/sets` now lists the set with
   `caseCount: 1`. Existing set + `createSet` → set name/description
   unchanged (clobber guard).
5. **T5 — capture → run round-trip (acceptance 2).** Capture from a fixture
   conversation into a fresh set, then #139's
   `POST /eval/runs {setId, targetId}` against the echo promoted target
   (`eval-run.test.ts` fixture); await completion → `GET /eval/runs/:id`
   results contain the captured `caseId` with a scored row — the stored-set
   discipline makes runnability free, this test locks it.
6. **T6 — the ladder.** Missing `conversationId`/`setId` → 400s; invalid
   `exchange` (0, 1.5, "x") → 400; out-of-range exchange → 404 with count;
   empty conversation (fresh `Conversation`, no history) → 400; unknown
   conversation → 404 + hint; invalid split → 400 (parseSplit shape); no
   `evalStore` → 503; options without `conversations` Map → 404 path.
7. **Dashboard (vitest, jsdom-free logic level).** `captureFromSession`
   discriminates 503 → `unconfigured`, 201/200 → `ok` with `created` intact;
   pair-derivation helper (user/assistant text extraction from
   `ChatMessage[]`) unit-tested if extracted into `model.ts`-adjacent pure
   function.

## Non-goals (scope fences)

- **No LLM judge** (E6/#141) and **no A/B-compare changes** (#138).
- **No multi-turn case capture / history replay** — the engine runs
  single-shot string input (fact 3); capturing a whole dialogue as one case
  has no executor. One exchange per case.
- **No revival of the dormant conversations read-API**
  (`GET /conversations/:id` etc.) or the Drizzle-flavored
  ConversationDetail/Conversations pages — separate concern, separate issue.
- **No case editing/deleting endpoints** — re-capture (upsert) covers the
  edit-the-seed loop; full bank CRUD is future authoring surface.
- **No file-first (jsonl) export of captured cases** — §16.4 keeps files as
  the authoring source of truth; captured cases live in the DB mirror. An
  `ap eval export` is future work if wanted.
- **No capture from persisted/historic conversations** — live registry only
  (Decision 1).

## Open questions

1. **Should the capture button also surface per-message?** (A small "capture
   this turn" icon on each assistant message instead of/in addition to the
   header button + picker.) Deferred — header affordance satisfies the
   acceptance; per-message placement is a UX refinement once the panel is in
   use.
2. **Client/server transcript desync after aborts** (Failure modes) — if it
   bites in practice, the fix is a tiny `GET /eval/cases/from-session/preview
   ?conversationId=` returning the server-side exchange list; deliberately
   not built in v1.
