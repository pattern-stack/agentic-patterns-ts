# Spec — Run evals from the playground (#139, E5c)

## Goal

Close the loop in the UI. `POST /eval/runs {setId, targetId, variant?, split?,
allowTest?}` resolves the target from the server's registered agents (the
`conversationRoutes` seam), starts the suite **asynchronously** server-side via
`runEval` with the exact `EvalStore` persistence the CLI writes (#135's
`onResult` seam, extracted into a shared runtime recorder so parity holds by
construction), and returns the `eval_run` id immediately (202). `GET
/eval/runs/:id/stream` is an SSE feed of per-case completion (the
`conversations.ts` `streamSSE` pattern) that any client can attach to at any
time — page reload mid-run recovers by re-hydrating persisted partial state
from the existing `GET /eval/runs/:id` and re-attaching the stream. The
held-out `test` split is refused server-side (403) without an explicit
`allowTest: true` body field — the §7 guard, not just UI chrome. The dashboard
grows a run launcher on `/eval` (set / target / variant / split picker) and
live progress on `/eval/runs/:id`.

Acceptance headline: **a UI-launched run persists the same rows as `ap eval`**
— same `eval_run` columns, same per-case `runs` rows (metadata incl.
`variant`/`split`, traceIds `${evalRunId}:${caseId}`), same `eval_result`
annotations — locked by a two-path parity test.

## Approach

### Verified against the branch tip (2026-07-04, `dug/139-run-from-ui` @ `1872a1b`, forked from `dug/138-ab-compare` — Epic 1 merged + #138's compare/aggregates present)

1. **The write seam is prepared but empty.** `routes/eval.ts:17` is
   `evalRoutes(evalStore: EvalStore | undefined)` serving five read GETs
   (`:20 /eval/sets`, `:27 /eval/sets/:id/cases`, `:46 /eval/runs`,
   `:65 /eval/runs/:id`, `:78 /eval/aggregates/splits`); its module doc (`:9`)
   names this issue: "Write routes (`POST /eval/runs`, …) and the SSE stream
   are epic 2 — not here." Helpers to reuse: `notConfigured` (`:98`),
   `parseSplit` (`:113`, built on `EvalSplitSchema`), `summarize` (`:143`).
2. **The streamSSE pattern anchor is exact.** `conversations.ts:79` (no drift
   from the issue) — `return streamSSE(c, async (stream) => { … await
   stream.writeSSE(msg); … await stream.writeSSE({ event: "done", data: "{}"
   }) })`, with `agentEventToSSE` (`sse.ts:40`) as the event formatter
   precedent. The eval stream defines its own 4-event vocabulary (below)
   rather than reusing the 20-event agent mapping — per-case progress is an
   eval-domain fact, not an agent event.
3. **Target resolution seam confirmed — with a trap.** `conversationRoutes`
   receives `config.agents` (`app.ts:36`; issue said `:35` — one-line drift)
   and resolves `agents.find(a => a.id === agentId)`
   (`conversations.ts:30`). Eval routes need the same list for
   `targetId → reg.agent`. **But `reg.runner` must NOT be handed to
   `runEval`:** the playground wraps promoted registrations in
   `NodeBackedRunner` (`playground.ts:110`), and `NodeBackedRunner.run()`
   **throws** on any non-promoted agent (`workflows/as-agent.ts:171-176`) —
   a nested `AgentStep` inside a promoted pipeline would call it with a bare
   inner agent and crash. `runEval` needs the **raw LLM runner** (what
   `resolveEvalTarget` + `withEvalBus` expect, and exactly what `ap eval`
   passes — `commands/eval.ts:225` calls `createRunner()` fresh). The raw
   runner exists in the playground (`playground.ts:95` `llmRunner`) but is not
   on `ServerConfig` — Decision 3 threads it through.
4. **The engine already does everything the async run needs.**
   `runEval(spec, ctx)` (`eval/run-eval.ts:213`) is sequential,
   never-throws-per-case, calls `await spec.onResult(result)` after each case
   (`:283-285`), and — given `ctx.eventBus` + `ctx.traceId = evalRunId` —
   mints per-case traceIds `${evalRunId}:${caseId}` and delivers bus + trace
   into every LLM leaf via the `withEvalBus` wrapper (`:236-246`, #133). The
   server's shared bus (`config.eventBus`) is the right bus: the playground's
   runner is already bound to it and `SQLiteExporter` is already attached
   (`playground.ts:71-95, 389-391`), so per-case traces land in `events.db`
   with zero new plumbing.
5. **Persisted-partial-state recovery is already built.**
   `startEvalRun` opens the suite row with `status: 'running'`
   (`storage/eval-store.ts:385`), `recordEvalResult` lands per-case rows as
   the run progresses, and `finishEvalRun` stamps the terminal status
   first-finalize-wins (`:401`, `WHERE status = 'running'`). So `GET
   /eval/runs/:id` mid-run already returns the run + completed cases — the
   dashboard's `statusTone` even handles `"running"` already
   (`EvalRunsPage.tsx:41-52`, `EvalRunDetailPage.tsx:43`). Reload recovery =
   that GET + stream re-attach; nothing new to persist.
6. **The CLI persistence block to replicate** is `commands/eval.ts:272-305`
   (onResult: `startRun` with `metadata {evalRunId, caseId, variant?, split?}`
   where split is `r.case.split ?? runSplit` — case-level wins; `finishRun`
   with `finalAnswer: JSON.stringify(r.output)`, tokens, `finishReason`/`
   status` from `r.succeeded`; `recordEvalResult` with `derivePass(r.scores)`),
   plus the expected-gated default scorer (`:264-266`) and the ctx shape
   (`:309-311`: `{runner, eventBus: bus, traceId: evalRunId}`). `derivePass`
   lives in **storage** (`eval-store.ts:536`), not `eval/` — so the extracted
   recorder (Decision 4) can live in `storage/` without breaking the store
   family's "zero coupling to `eval/`" invariant (structural `EvalScoreLike`
   precedent, `eval-store.ts:52-59`).
7. **The split guard is importable and free.**
   `assertSplitSelectable(split, {allowTest})` throws `HeldOutSplitError`
   iff `split === "test"` without opt-in (`eval/case-bank.ts:247`), and
   `filterBySplit` (`:254`) filters to exact split (untagged excluded). The
   CLI calls the guard before any store/file work (`commands/eval.ts:100-109`)
   — the route mirrors that ordering (guards before side effects).
8. **Stored-set loading is proven in store-mode `ap eval`.**
   `store.listEvalSets()` / `store.listEvalCases(setId)` +
   `storedCaseToEvalCase` null→undefined normalization
   (`commands/eval.ts:163-174, 387-395` — the normalization is load-bearing:
   an un-normalized `expected: null` would make the default scorer gate an
   expected-less case).
9. **Issue key-file drift (expected, same as #138 noted):** the issue names
   `pages/EvalPage.tsx`; the shipped surface is
   `pages/eval/{EvalRunsPage,EvalRunDetailPage,EvalComparePage,CaseDetail,
   SplitAggregatesPanel}.tsx` with routes `/eval`, `/eval/runs/:id`,
   `/eval/compare/:aId/:bId` (`App.tsx:43-45`). The doc §8 gotcha (SPA
   `API_PREFIXES` allowlist) is **already fixed** — `/eval` is present at
   `playground.ts:219` (#136). No CLI SPA change.
10. **Test substrate:** server route tests use a real in-memory-SQLite
    `EvalStore` + `evalRoutes`-only Hono app + `app.request()`
    (`agent-server/src/__tests__/eval.test.ts:21-24`); CLI eval tests have the
    injected-runner seam + promoted-echo / AgentLike+stub-runner fixtures
    (`agent-cli/src/commands/__tests__/eval.test.ts`); `MockRunner` is a
    runtime export (`runner/index.ts:33`). Dashboard pages test with jsdom +
    `vi.stubGlobal("fetch")` (`EvalRunsPage.test.tsx`); the SSE hook precedent
    is `hooks/useEventStream.ts` (EventSource + exponential backoff).

### Decision 1 — case source: stored sets only (`setId` → `eval_case` rows)

The POST has no file path and must not accept one (a server that opens
arbitrary client-supplied paths is a footgun, and the playground's DB-side
case bank is exactly the read `GET /eval/sets/:id/cases` already serves).
**`POST /eval/runs` runs against a stored set:** `setId` →
`store.listEvalCases(setId)` → the CLI's null→undefined normalization →
`EvalCase[]`. File-based jsonl/gold sets remain **CLI-only** — and the CLI's
file mode already mirrors every loaded bank into `eval_case`
(`commands/eval.ts:182-193`), so any set that has been run once via `ap eval`
is UI-launchable. Sets born in the UI arrive with #140 (capture-from-session).
The normalization helper is duplicated route-locally (8 lines) per the route
file's own stated precedent ("small helpers are deliberately not shared
across route files", `routes/eval.ts:94-95`), with a comment pointing at
`commands/eval.ts:387`.

### Decision 2 — async model: fire-and-poll, with an attachable SSE feed

`runEval` is sequential and a real suite takes minutes; holding the POST open
is not an option, and making the run's lifetime depend on an open HTTP stream
(stream-attached execution) would mean closing the tab kills the run.
**Chosen: fire-and-poll with an attachable stream.**

- The POST handler does all validation + `startEvalRun` **synchronously**
  (better-sqlite3 is sync), registers an in-process live-run handle, kicks off
  the suite as a detached promise (`void run().catch(…)` — errors terminate
  the run row, never the process), and returns `202 {runId, total}`.
- The **persisted rows are the source of truth** for progress (fact 5):
  clients that never attach the stream can poll `GET /eval/runs/:id`.
- `GET /eval/runs/:id/stream` is a **view** over the live handle: attach any
  time, from any number of tabs; detach freely. Disconnecting never affects
  the run.
- Reload-mid-run recovery: `EvalRunDetailPage` hydrates from
  `GET /eval/runs/:id` (partial results + `status:"running"`), then attaches
  the stream. The stream's first event is a `run.snapshot` read from the
  store **after** subscribing (subscribe-then-read is atomic — both are
  synchronous in one JS tick, and `recordEvalResult` is written *before* the
  case is broadcast), so no case can fall in a gap; the client dedupes by
  `caseId` anyway.

### Decision 3 — runner seam: `ServerConfig.evalExecution` (per fact 3, `reg.runner` is a trap)

New optional group on `ServerConfig` (the `eventStore`/`evalStore` idiom,
`config.ts:96-98`):

```ts
/** Server-launched eval execution. Absent → POST /eval/runs returns 503. */
readonly evalExecution?: {
  /** RAW LLM runner (createRunner's) — NOT a registration's possibly
   *  NodeBackedRunner-wrapped one (as-agent.ts:171 throws on nested
   *  AgentSteps). resolveEvalTarget handles promoted targets itself. */
  readonly runner: RunnerProtocol;
  /** Provenance stamped onto eval_run rows (CLI formula: AGENT_MODEL ?? tier). */
  readonly model?: string;
  readonly gitSha?: string;
};
```

The playground passes `{ runner: llmRunner, model: process.env.AGENT_MODEL ??
tier, gitSha }` (it already has `llmRunner` and `tier` in scope,
`playground.ts:90-95`; `gitSha` via the CLI's `readGitSha` inlined). The eval
target handed to `runEval` is `reg.agent` as-is — `resolveEvalTarget` handles
Node/AgentLike/PromotedAgent, same as the CLI (`commands/eval.ts:112-115`).
No `toolExecutor` is passed — the CLI passes none either (`:309-311`); parity
first, tool-execution-for-evals is a noted follow-up (Open questions).

### Decision 4 — store parity by construction: extract the recorder

Duplicating the 30-line multi-table persistence block across packages and
hoping a test catches drift is the fragile version. Instead:

- **New `packages/agent-runtime/src/storage/eval-recorder.ts`** —
  `createEvalResultRecorder(store, meta)` returning the `onResult`-shaped
  persistence function, body lifted verbatim from `commands/eval.ts:276-304`.
  Input is structurally typed (`EvalResultLike`, satisfied by
  `eval/types.ts`'s `EvalResult` — the `EvalScoreLike` precedent), so
  `storage/` still never imports `eval/`.
- **`commands/eval.ts` refactors** its `onResult` to
  `printCaseLine(r); recorder?.(r)` — behavior-identical, covered by #135's
  existing tests.
- **The server route uses the same recorder** + its own broadcast.
- **The parity test remains** (Tests §) as the lock against either side
  bypassing the recorder later — belt and suspenders.

Rejected alternative: route-local duplication + parity test only. Works, but
leaves permanent cross-package duplication of the subtlest write path in the
stack (metadata key set, `r.case.split ?? runSplit` precedence, traceId
threading, `derivePass`).

### Decision 5 — held-out guard: 403 + explicit `allowTest` body field

Doc §7: the `test` split "refuses to run without an explicit env/flag". The
POST body carries `allowTest?: boolean`; the route calls
`assertSplitSelectable(split, { allowTest })` **before any store work** (the
CLI's "the refusal must be free" ordering) and maps `HeldOutSplitError` to
**403** `{error: <the case-bank message>, hint: 'retry with "allowTest": true'}`.
403 (policy refusal), not 400 (malformed input) — an invalid split *value*
stays 400 via the existing `parseSplit` message shape. The UI's split picker
shows an explicit "run held-out test split" checkbox when `split=test`, but
the server guard is authoritative.

### POST /eval/runs — request pipeline (ordered guards, then detach)

```
parse body            → 400 on non-JSON / missing setId / missing targetId
validate split value  → 400 (parseSplit message shape)
held-out guard        → 403 (Decision 5 — free, before any store access)
evalStore present?    → 503 notConfigured (existing helper)
evalExecution present?→ 503 "eval execution not configured" (new helper, same shape)
resolve target        → 404 `agent "<id>" not found` + available list (CLI :344 message shape)
resolve set           → 404 `eval set "<id>" not found` (GET :40 message shape)
load + normalize cases; apply filterBySplit when split present
empty selection       → 400 `no cases in split "<s>" of set "<id>"` (CLI :203 shape)
startEvalRun({setId, targetId, variant, split, model, gitSha})   [status 'running']
register live handle {total: cases.length, completed: 0, listeners: ∅}
detach:  runEval({target: reg.agent, cases, scorers: [defaultScorer],
                  onResult: r => { recorder(r); live.completed++; broadcast(case.result) }},
                 {runner: exec.runner, eventBus: config.eventBus, traceId: evalRunId})
         → finishEvalRun ok → broadcast run.finished → deregister
   catch → finishEvalRun error → broadcast run.finished {status:"error"} → deregister + console.error
return 202 {runId, total}
```

`defaultScorer` is the CLI's 3-line expected-gated `exactMatch`
(`commands/eval.ts:264-266`), duplicated route-side (parity test covers score
equality). The route never calls `store.close()` — the server owns the store's
lifecycle (unlike the CLI, which closes in `finally`).

### GET /eval/runs/:id/stream — live registry + SSE

An in-process `Map<evalRunId, LiveEvalRun>` scoped to the `evalRoutes` closure
(the `conversations` registry idiom, `app.ts:26`). Event vocabulary (all
`data` JSON):

| event | data | when |
|---|---|---|
| `run.snapshot` | `{runId, status, completed, total: number\|null}` | once, on attach (store-read after subscribe) |
| `case.result` | `{caseId, pass, succeeded, error, scores, finalAnswer, inputTokens, outputTokens, traceId, completed, total}` | per completed case |
| `run.finished` | `{status: "ok"\|"error"}` | terminal |
| `run.detached` | `{status: "running"}` | attach when store says running but no live handle in this process |
| `done` | `{}` | stream close (conversations.ts:87 convention) |

Attach semantics:
- **Live handle exists:** `streamSSE` → subscribe listener → write
  `run.snapshot` → forward broadcasts (serialize `writeSSE` per listener) →
  on `run.finished` write `done` and close. `stream.onAbort` removes the
  listener; the run continues.
- **No handle, store status terminal:** `run.snapshot` + `run.finished` +
  `done`, close immediately (reload-after-finish case).
- **No handle, store status `running`:** `run.snapshot` + `run.detached`,
  close. Covers (a) a concurrent `ap eval` writing the same DB — there is a
  runner but not in this process — and (b) a server restarted mid-run
  (orphaned row; see Failure modes). The client falls back to 3s polling.
- **Unknown id:** 404. **No store:** 503.

`case.result` mirrors `JoinedEvalResultRow`'s field names
(`eval-store.ts:124-140` / dashboard `api/types.ts`) so the client can merge
streamed rows straight into the fetched results table; `finalAnswer` is the
same `JSON.stringify(r.output)` string the recorder persists.

### Dashboard — launcher + live detail

**Launcher (`pages/eval/RunLauncher.tsx`, mounted on `EvalRunsPage`** in the
header row next to Refresh, expanding a form Card — the `SplitAggregatesPanel`
page-scoped-component idiom):
- Set select ← new `fetchEvalSets()` (`GET /eval/sets`, `EvalFetch<T>` 503
  discrimination like every evalApi call); shows per-split counts from
  `EvalSetSummary.splitCounts`.
- Target select ← the existing agents list fetch (`api/chat-client.ts:22`,
  `GET /agents` — verify export name at impl).
- Variant: free text (optional). Split: (all) / train / dev / test; choosing
  `test` reveals a "run the held-out test split" checkbox → `allowTest`.
- Run → `launchEvalRun(body)` (new evalApi POST) → on 202
  `navigate(/eval/runs/${runId})`; 4xx/5xx render inline in the launcher
  (the runs-page error Card grammar).
- Unconfigured store (503) → hide the form behind the existing
  "persistence not configured" hint.

**Live detail (`EvalRunDetailPage`):** when the fetched run has
`status === "running"`, mount the new **`hooks/useEvalRunStream.ts`**
(EventSource + the `useEventStream` backoff/cleanup idiom, but listening for
the four eval event names; `runId: null` disables — the empty-path
convention). Page behavior:
- progress header: `completed/total` bar (total from snapshot; `null` → count
  only) + the existing running badge;
- merge `case.result` rows into the results table keyed by `caseId`
  (streamed row shape ≈ `JoinedEvalResultRow`; upsert, never duplicate);
- on `run.finished`: refetch `fetchEvalRunDetail` (authoritative joined rows)
  — stream data is a live approximation, the store is truth;
- on `run.detached`: poll `fetchEvalRunDetail` every 3s until terminal
  (cleared on unmount) — this also makes concurrent CLI runs watchable.

## Failure modes

| Scenario | Behavior |
|---|---|
| Unknown `targetId` / `setId` | 404 before `startEvalRun` — **no run row is ever created for a rejected request** |
| Invalid split value / empty split selection / missing body fields | 400, no row |
| `split: "test"` without `allowTest: true` | 403 + `HeldOutSplitError` message + hint (Decision 5) |
| Store absent / execution absent | 503 (`notConfigured` / new `notExecutable`) |
| Case errors mid-suite (node throws) | not a crash — `runEval` scores it errored; run completes `ok` (gate semantics live in scores, matching CLI) |
| **Run crash mid-suite** (recorder/store write throws — `runEval` awaits `onResult`, so it propagates) | detached-promise catch: `finishEvalRun(status:"error")` → broadcast `run.finished {status:"error"}` → deregister → `console.error`. Partial `eval_result` rows are retained; `GET /eval/runs/:id` shows the truncated run with `status:"error"` |
| SSE client disconnects mid-run | listener removed on abort; **run continues** (fire-and-poll invariant) |
| Server process killed mid-run | `eval_run` orphaned as `"running"` forever. **No boot-time sweep** — the DB is shared with concurrent `ap eval` processes whose live runs also read `"running"`; a sweep would clobber them. Stream attach returns `run.detached`; UI polls and shows a stuck-running run honestly. Documented limitation (Open questions) |
| Concurrent POSTs | allowed — independent run ids/handles; better-sqlite3 serializes writes (WAL); runner-level concurrency is the provider's concern (local playground scale) |

## Non-goals (scope fences)

- **No capture-from-session** (`POST /eval/cases/from-session` is #140) and
  **no judge** (#141).
- **No run cancellation endpoint** — kill the playground process; the row
  orphans as `running` (documented above).
- **No file-path sets over HTTP** (Decision 1 — CLI-only; run `ap eval` once
  to mirror a file bank into the store).
- **No boot-time sweep of orphaned `running` rows** (shared-DB hazard).
- **No `toolExecutor` wiring into eval runs** — parity with the CLI's shipped
  behavior; changing both paths is a separate issue.
- **No engine or schema changes** — `run-eval.ts` and the `EvalStore` DDL are
  untouched.

## Open questions

1. **Tool execution in evals** — neither `ap eval` nor this route passes a
   `toolExecutor`, so tool-using LLM-loop targets format tools without
   executing them. Follow-up issue candidate: wire
   `createToolboxExecutor(reg.agent)` into **both** paths together (parity).
2. **Orphaned `running` rows** — acceptable for a local playground; if it
   ever bites, the fix is a per-process owner token on `eval_run`, not a
   sweep.
3. **Run cancellation** — deferred until someone asks; the handle registry is
   the natural seam (`live.abort` flag checked in `onResult`).
