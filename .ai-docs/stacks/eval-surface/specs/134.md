# Spec — Case banks + splits: `EvalCase.split`, jsonl/gold loaders, held-out guard (#134, E3)

## Goal

Make the eval engine's case supply **file-first and split-disciplined** (doc §3 E3, §7,
§16.4): add `split` as a first-class **optional** field on the `EvalCase` envelope
(`eval/types.ts:24-36`) with the **ML-standard names `train` / `dev` / `test`** — the doc
explicitly fixes the consumer's inverted `test`/`validate` naming; consumer aliasing is
out of scope — and ship a NEW module `eval/case-bank.ts` holding:

- **`loadCasesJsonl(path)`** — one JSON case envelope per line → `EvalCase[]`, every
  malformed row failing with a **case-addressed error** (file + line + case id when
  recoverable).
- **`loadGold(casesPath, goldPath)`** — cases file + gold file (id-keyed expected
  outputs) joined by `id` → `EvalCase[]` with `expected` populated. Promotes the idea of
  the consumer's `gold.ts` (id-join, fail-loud on missing sources), not its domain shape.
- **`filterBySplit(cases, split, opts?)` + `assertSplitSelectable(split, opts?)`** — the
  split discipline: selecting the held-out `test` split **throws** unless the caller
  passes the explicit `{ allowTest: true }` opt-in. Promotes the consumer's
  `split-discipline.ts` refusal (with the names un-inverted, and an argument instead of
  an env var — env/flag mapping is #135's CLI policy).

Absent `split` behaves exactly as before — every existing caller compiles and behaves
identically; `runEval` needs **zero changes** (the loaders and filter run *before*
`spec.cases` is handed to the engine, and the engine's existing up-front envelope
validation (`run-eval.ts:170-177`) picks the new optional field up for free because it
validates with the same `EvalCaseSchema`).

Additive only. No storage/ or stores/ edits (the `eval_case` DB mirror is #132's shipped
table, populated later via capture/mirror — file-first authoring stays canonical, §16.4),
no CLI (#135), no engine-loop changes.

### Step 1 — `eval/types.ts`: the split primitive (exact diff in § Interfaces)

`EvalSplitSchema = z.enum(["train", "dev", "test"])` + inferred `EvalSplit` live in
`eval/types.ts` — schema and type stay together, and the engine's existing validation
inherits the field for free (finding 2). `EvalCase` gains `readonly split?: EvalSplit`;
`EvalCaseSchema` gains `split: EvalSplitSchema.optional()`.

Backward-compat note (the one behavioral edge): `EvalCaseSchema` is non-strict, so a
pre-#134 caller passing a stray `split` key with a *non-enum* value (e.g. the consumer's
`"validate"`) previously had it silently stripped; it now fails the up-front validation.
This is fail-loud working as intended — and exactly the migration tripwire the doc wants
the consumer to hit (§7 rename table).

### Step 2 — the `EvalSplit` barrel collision (finding 3)

Decision: **`eval/types.ts` becomes the canonical `EvalSplit`; `storage/eval-store.ts`
keeps its structural twin untouched; the package root disambiguates with one explicit
type re-export.**

- `storage/eval-store.ts` is NOT edited — #132's "zero coupling to `eval/`" is a shipped,
  spec-documented invariant on the branch this forks from; reversing it here would be a
  cross-issue regression. The two declarations are identical string unions, hence
  mutually assignable — TypeScript treats them interchangeably at every seam.
- `src/index.ts` adds `export type { EvalSplit } from "./eval/types.js";` — an explicit
  export **overrides** star-export ambiguity, so the package root keeps exporting
  `EvalSplit` (now the eval-side declaration; identical shape → zero consumer breakage).
  `EvalSplitSchema` is a unique name, no conflict.
- Drift guard: a compile-time test (`expectTypeOf<EvalSplit>().toEqualTypeOf<
  StorageEvalSplit>()`, vitest built-in) in the new test file — if either union ever
  gains a member the other lacks, the suite fails at typecheck (Tests #12).

### Step 3 — `eval/case-bank.ts` (NEW): loaders

**Module name: `case-bank.ts`** (over `loaders.ts`) — the doc's own noun for E3 is "case
banks" (§3), and the module holds more than loaders: the split filter and the held-out
guard are discipline, not loading. `loaders.ts` would under-name a third of the surface.

**jsonl case-file format** (the contract `loadCasesJsonl` enforces):

- UTF-8, one JSON object per **physical line**; blank/whitespace-only lines are skipped
  but still counted (errors always cite the true 1-based line number — improvement over
  the consumer's `filter(Boolean)`, finding 5).
- Each line is a **strict** case envelope:
  `{ "id": string, "input": any, "expected"?: any, "tags"?: string[], "split"?: "train"|"dev"|"test" }`
  — validated with a module-private `CaseRowSchema = EvalCaseSchema.strict()`. Strictness
  is deliberately loader-boundary-only (the engine's schema stays non-strict/unchanged):
  in a hand-authored file, an unknown top-level key is almost certainly a typo — e.g.
  `"spilt": "train"` would otherwise be *silently stripped*, the case would drop out of
  every split filter, and the bank would quietly shrink. Fail loud, case-addressed.
- Duplicate `id`s within a file are load errors. Rationale: everything downstream keys
  per-case results by `case.id` (#132's `eval_result` PK is `(eval_run_id, case_id)`), so
  duplicate ids silently clobber annotations — the loader is the one place to catch it.

**Error shape** — all loader failures throw `CaseBankLoadError extends Error` with
structured fields (`path`, `line?`, `caseId?`) so #135 can render them without regex-
parsing messages. Exact message formats (also the tests' assertions):

| Failure | Message |
|---|---|
| unreadable file | `case-bank: cannot read <path> — <fs error message>` |
| JSON parse | `case-bank: <path>:<line>: invalid JSON — <parse error message>` |
| envelope invalid | `case-bank: <path>:<line> (id=<id>): invalid case — <zod error message>` (the ` (id=…)` segment omitted when `id` itself is missing/non-string) |
| duplicate id | `case-bank: <path>:<line> (id=<id>): duplicate case id (first at line <n>)` |

(`<zod error message>` = `error.message`, the same field the engine already surfaces at
`run-eval.ts:174` — one consistent forensics shape.)

Loaders are **synchronous** (`node:fs` `readFileSync`; precedent finding 6). They run at
harness boot before any async work, and sync keeps the held-out refusal *free* — the
consumer's discipline module names this requirement ("a validate refusal must be free",
i.e. before any client/DB/LLM setup). The "async throughout" convention governs protocol
methods, which these are not.

Generics: `loadCasesJsonl<TIn = unknown, TExpected = unknown>` — the type parameters are
a **caller assertion**, exactly the `types.ts` philosophy ("TIn — caller narrows via
z.infer at their seam", `types.ts:33`); payload validation stays `z.unknown()`
passthrough.

### Step 4 — `loadGold`: the gold-file overlay

**Gold-file format**: jsonl; each line is strictly
`{ "id": string, "expected": any }` — both keys required, no others (a gold row without
`expected` is an authoring error; `z.unknown()` alone can't enforce presence, so the
loader checks `Object.hasOwn(raw, "expected")` on the raw parsed row).

**Join semantics** (`loadGold(casesPath, goldPath)`):

1. Load cases from `casesPath` — identical path/validation to `loadCasesJsonl`.
2. Load gold rows from `goldPath`; duplicate gold `id` → error.
3. **Overlay**: for each gold row, the matching case gets `expected` replaced (gold wins
   over any inline `expected` — the gold file is the authority; regenerating goldens must
   not require touching the cases file). Returns new frozen-shape case objects; inputs
   are never mutated.
4. **Unmatched gold id → error** (`case-bank: <goldPath>:<line> (id=<id>): gold row has
   no matching case in <casesPath>`). Fail-loud is load-bearing: a typo'd id silently
   dropping gold *deflates* the eval — the exact failure mode the consumer's `gold.ts`
   header documents fighting (~23% deflation from skipped substitution).
5. Cases **without** a gold row pass through unchanged (partial gold coverage is normal
   while a bank is being built) — kept `expected` (inline or `undefined`) intact.

### Step 5 — split filter + held-out guard

Two exports, mechanism split from policy:

- **`assertSplitSelectable(split, opts?)`** — throws `HeldOutSplitError` iff
  `split === "test"` and `opts?.allowTest !== true`; no-op for `train`/`dev`. Standalone
  so #135 can refuse **immediately after flag parsing, before loading anything** (the
  free-refusal property). Exact error message (single line, the tests assert it
  verbatim):

  > `case-bank: refusing the held-out "test" split — touch once, pre-ship only. Pass { allowTest: true } to run it deliberately.`

- **`filterBySplit(cases, split, opts?)`** — calls `assertSplitSelectable(split, opts)`
  first, then returns `cases.filter((c) => c.split === split)` (new array, same case
  references). **Untagged cases (absent `split`) are excluded by every split filter** —
  they run only when no filter is applied; explicit tagging is the discipline. The
  opt-in is `{ allowTest: true }` — an explicit *argument*, not an env var: the consumer's
  `EVAL_VALIDATE_OK=1` / `process.exit(1)` behavior is CLI policy, and mapping a
  `--allow-test` flag or env var onto this argument is #135's decision. Throwing (never
  `process.exit`) keeps the primitive embeddable (server routes in #136 catch the same
  error).

Both errors carry stable `name` fields (`"CaseBankLoadError"` / `"HeldOutSplitError"`)
for cross-realm `instanceof`-free detection.

## Interfaces

```ts
// eval/types.ts — MODIFY (additive only; everything else in the file unchanged)

export const EvalSplitSchema = z.enum(["train", "dev", "test"]);
/** ML-standard split names (doc §7). Canonical home; storage/eval-store.ts:48 keeps
 *  a structural twin by design (#132 zero-coupling) — drift-guarded by test. */
export type EvalSplit = z.infer<typeof EvalSplitSchema>; // "train" | "dev" | "test"

export interface EvalCase<TIn, TExpected = unknown> {
  readonly id: string;
  readonly input: TIn;
  readonly expected?: TExpected;
  readonly tags?: readonly string[];
  readonly split?: EvalSplit; // NEW — optional; absent = untagged (pre-#134 behavior)
}

export const EvalCaseSchema = z.object({
  id: z.string(),
  input: z.unknown(),
  expected: z.unknown().optional(),
  tags: z.array(z.string()).readonly().optional(),
  split: EvalSplitSchema.optional(), // NEW
});
```

```ts
// eval/case-bank.ts — all NEW

/** Loader failure, addressed to file + line + case id where recoverable. */
export class CaseBankLoadError extends Error {
  readonly name = "CaseBankLoadError";
  readonly path: string;
  readonly line?: number;   // 1-based physical line; absent for whole-file failures
  readonly caseId?: string; // absent when the row's id itself is unrecoverable
  constructor(message: string, fields: { path: string; line?: number; caseId?: string });
}

/** Thrown when the held-out `test` split is selected without the explicit opt-in. */
export class HeldOutSplitError extends Error {
  readonly name = "HeldOutSplitError";
}

/**
 * Load a jsonl case bank: one strict EvalCase envelope per line
 * ({ id, input, expected?, tags?, split? } — unknown keys are errors).
 * Blank lines skipped; duplicate ids rejected. TIn/TExpected are caller assertions.
 */
export function loadCasesJsonl<TIn = unknown, TExpected = unknown>(
  path: string,
): EvalCase<TIn, TExpected>[];

/**
 * Load cases + overlay a gold file ({ id, expected } per line, both required) by id.
 * Gold wins over inline expected; an unmatched or duplicate gold id is an error;
 * cases without a gold row pass through unchanged.
 */
export function loadGold<TIn = unknown, TExpected = unknown>(
  casesPath: string,
  goldPath: string,
): EvalCase<TIn, TExpected>[];

export interface SplitSelectOptions {
  /** Explicit opt-in for the held-out `test` split. Mapping a CLI flag/env var here is #135's policy. */
  readonly allowTest?: boolean;
}

/** Throws HeldOutSplitError iff split === "test" without { allowTest: true }. Free — call before any loading. */
export function assertSplitSelectable(split: EvalSplit, opts?: SplitSelectOptions): void;

/** assertSplitSelectable, then cases with EXACTLY the given split (untagged cases excluded). */
export function filterBySplit<TIn, TExpected = unknown>(
  cases: readonly EvalCase<TIn, TExpected>[],
  split: EvalSplit,
  opts?: SplitSelectOptions,
): EvalCase<TIn, TExpected>[];
```

## Tests

`packages/agent-runtime/src/eval/__tests__/case-bank.test.ts` — temp files via
`mkdtempSync(join(tmpdir(), "case-bank-"))` (`event-store.test.ts:144-147` idiom);
engine integration via `FunctionStep` + `MockRunner` (`run-eval.test.ts:52-69` idiom).

1. **Round-trip.** A jsonl with one case per split + one untagged (tags, object
   input/expected) → `loadCasesJsonl` returns all four in file order with `split`, `tags`,
   payloads intact.
2. **Blank-line tolerance + true line numbers.** Blank lines between rows are skipped;
   a malformed row *after* blanks reports its physical line number, not its row index.
3. **Malformed JSON.** Message matches `case-bank: <path>:<line>: invalid JSON — …`;
   `err.path`/`err.line` populated; `err instanceof CaseBankLoadError`.
4. **Invalid envelope.** `"split": "validate"` (the consumer's old name) → error carries
   path, line, and `(id=…)`; the message is the doc §7 migration tripwire.
5. **Strict envelope.** An unknown top-level key (`"spilt": "train"`) is an error, not a
   silent strip — case-addressed.
6. **Missing/non-string id.** Error cites path + line and omits the `(id=…)` segment.
7. **Duplicate id.** Error names the id and both line numbers.
8. **Gold overlay.** Gold row overlays `expected` by id; gold **wins** over inline
   expected; a case without a gold row keeps its inline value; returned objects are new
   (inputs not mutated).
9. **Gold failure modes.** Unmatched gold id → error citing goldPath + line + id +
   casesPath; duplicate gold id → error; gold row missing `expected` key → error; gold
   row with extra keys → error (strict).
10. **Split filter.** `filterBySplit(cases, "train")` returns only exact-`train` cases —
    untagged cases excluded; result is a new array; `dev` needs no opt-in.
11. **Held-out guard (the acceptance path).** `filterBySplit(cases, "test")` throws
    `HeldOutSplitError` with the exact § Step-5 message; `{ allowTest: true }` returns the
    test cases; `assertSplitSelectable("test")` standalone throws the same before any file
    I/O (free refusal).
12. **`EvalSplit` drift guard (compile-time).**
    `expectTypeOf<EvalSplit>().toEqualTypeOf<StorageEvalSplit>()` against
    `storage/eval-store.ts` — the structural twin can never drift silently.
13. **Backward compat + engine pass-through (integration).** `runEval` over a mixed bank
    (split-tagged + untagged cases, loaded via `loadCasesJsonl`) with a `FunctionStep` +
    `exactMatch`: report identical in shape to a pre-#134 run; `result.case.split` rides
    through untouched; a split-less inline `cases` array (the pre-#134 calling
    convention) still validates and runs — proving `run-eval.ts` needed zero edits.

Run: `bun run --filter=@agentic-patterns/runtime test` (+ `typecheck`, `lint`).
Existing `eval/__tests__/run-eval.test.ts` and `storage/__tests__/*.test.ts` must stay
green — the only shared edits are `types.ts` (additive optional field) and the two
barrels; test 13 and the drift guard cover both.

## Open questions

None blocking. Three recorded decisions an implementer should not re-litigate:
**gold wins over inline `expected`** (regenerating goldens must not touch the cases
file); **strict envelopes at the loader boundary only** (the engine schema stays lax —
programmatic callers are TS-typed already, files are not); **untagged cases are excluded
by every split filter** (explicit tagging is the discipline; untagged banks run
unfiltered).
