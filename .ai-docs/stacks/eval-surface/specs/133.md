# Spec — Eval trace + run capture fused: `eventBus` on `EvalRunContext`, per-case `traceId`, `RunStoreExporter` (#133, E2)

## Goal

Make every eval case **observable for free** (doc §3 E2, §5): add
`readonly eventBus?: AgentEventBus` to `EvalRunContext` (`eval/run-eval.ts:34-39`), mint a
**per-case traceId** in `runEval`'s loop, deliver bus + traceId to the node execution, and
stamp the traceId onto the `EvalResult` (`eval/types.ts:79-97`). With `RunStoreExporter`
attached to the provided bus, each case then yields an EventStore trace **and** a RunStore
`runs` row with **zero additional engine code** — one lever, both records (the doc's
"Update (2026-07-04)" fusion decision).

This is **THE ONLY engine edit in the whole stack** (doc §13: *"The engine ships as-is;
this stack wires it. The only engine edit is E2's additive `eventBus?` field on
`EvalRunContext`."*). Two files change: `eval/run-eval.ts` and `eval/types.ts`. No
`workflows/`, `runner/`, `exporters/`, or `storage/` edits. No bus → behavior
**byte-identical** to today: every existing `runEval` caller compiles and behaves the same.

## Approach

### Verified against the branch tip (2026-07-05, `dug/133-trace-capture` @ `c390b1a`, forked from `origin/dug/134-case-banks`)

All issue anchors re-read at the tip. The named anchors hold; **one load-bearing drift
found in the LOCKED doc's mechanism** (finding 4) that changes *how* the bus is delivered
— not *what* the feature does:

1. `eval/run-eval.ts:34-39` — `EvalRunContext` is `{ runner; hooks?; toolExecutor?;
   traceId? }`. No `eventBus`. ✓ as the issue describes.
2. `eval/run-eval.ts:184-233` — the per-case loop: `nodeCtx` built at `:185-191`
   (threads `traceId: ctx.traceId` — the *same* id into every case today), `node.run` at
   `:195`, `EvalResult` assembled at `:217-225`. ✓ (the issue cites `:162`, which is the
   `runEval` signature; the loop itself starts at `:184` after #103's up-front envelope
   validation `:170-177`).
3. `eval/types.ts:79-97` — `EvalResult` + `EvalResultSchema`. #134 already touched this
   file on the branch (added `EvalSplit`/`split` at `:23-26`/`:38`/`:46`); the `traceId`
   edit below is a disjoint section (EvalResult block) — no collision, and the branch is
   stacked on #134 so the edits are sequential anyway.
4. **Drift (load-bearing): doc §5 step 2 — "pass the bus + traceId into the
   NodeRunContext" — is not literally implementable.** `NodeRunContext`
   (`workflows/node.ts:28-57`) has **no `eventBus` member**, and `AgentStep.run` — the
   only leaf that reaches a runner — builds its `RunOptions` **explicitly** at
   `workflows/agent-step.ts:114-120` (`toolExecutor`, `maxIterations`, `traceId`,
   `parentSpanId`, `host`) and would silently drop any bus stuffed onto the ctx object.
   The *functional* delivery seam is **`RunOptions.eventBus`**
   (`runner/types.ts:118-119`), which `AgentRunner` honors at the top of all three entry
   points: `run` (`agent-runner.ts:283-285`), `runStructured` (`:774-775`), `stream`
   (`:961-962`). Resolution: deliver the bus via an **eval-local per-case runner
   wrapper** (Step 3 below) — keeps the §13 fence (only `eval/` changes), works for
   every target kind, and makes the LOCKED `EvalRunContext.eventBus` API do its job.
   `traceId` needs no wrapper help for framework nodes — `AgentStep` already forwards
   `ctx.traceId → opts.traceId` (`agent-step.ts:117`) — but the wrapper defaults it
   anyway to harden custom nodes that drop ctx fields.
5. **The fusion contract holds** — verified event-by-event against
   `exporters/run-store.ts` and `runner/agent-runner.ts` (next section).
6. `RunStore` names this exact seam: *"or directly via `startRun`/`finishRun` for manual
   producers (e.g. `runEval`'s …)"* (`storage/run-store.ts:15`) — that manual path stays
   E1/E4 territory (`EvalSpec.onResult`); E2 is the *bus* path.

### The fusion contract (the crux): which events cut a `runs` row, and who emits them

`RunStoreExporter` (`exporters/run-store.ts:80`, `profile = EventProfile.OBSERVABILITY`)
is a per-`runId` state machine:

| Bus event | Handler | Store effect |
|---|---|---|
| `agent.message.start` | `_onMessageStart` (`run-store.ts:109-132`) | **`startRun`** (`:114`) — opens the row (status `running`), keyed `event.runId`, stamps `event.traceId` |
| `agent.llm.end` | `_onLlmEnd` (`:135-146`) | folds tokens / duration / finishReason |
| `agent.tool.end` | `_onToolEnd` (`:149-158`) | folds tool-call counts |
| `agent.iteration.end` | `_onIterationEnd` (`:161-174`) | pushes a step-metrics entry |
| `agent.message.complete` | `_onMessageComplete` (`:177-196`) | **`finishRun`** (`:182`) — status `ok`, first-terminal-wins |
| `agent.error` (recoverable: false) | `_onError` (`:199-220`) | **`finishRun`** (`:205`) — status `error` |

**Does a bare `node.run` emit these? YES — when the runner is `AgentRunner` and the bus
reaches it.** Every LLM leaf in a node tree is an `AgentStep`, which calls
`runner.run`/`runner.runStructured` (`agent-step.ts:127,:137`); `AgentRunner.run`
(`agent-runner.ts:281`) emits the **full lifecycle**: `agent.message.start` at `:308-320`
(the row-opener — with `runId` minted per call at `:287`, `traceId = options?.traceId ??
runId` at `:288`, `agentName`, `agentConfig`, `systemPrompt`), `iteration.start/llm.start/
llm.end/tool.*/iteration.end` through the loop, and a **guaranteed terminal**:
`agent.message.complete` on the normal return (`:476`) *and* on max-iterations (`:633` —
the #117 fix added precisely so "a bus-finish hook like RunStoreExporter … [doesn't stay]
'running' forever"), or `agent.error` on throw (`:389`). `runStructured` mirrors this
(`:789` start, `:928` complete, `:914` error).

**Therefore `runEval` must NOT emit `message.start`/`message.complete` envelope events
itself.** Doing so would double-row every agent-target case (the runner's own lifecycle
+ the synthetic envelope, two distinct `runId`s → two `runs` rows per case) and would
fabricate an "agent run" for cases where nothing ran. `runEval`'s entire job is
**delivery**: get the bus into `RunOptions` and the per-case `traceId` into the ctx.

Three honest boundaries of the contract (documented, not hidden):

- **The fusion is runner-mediated.** `MockRunner.run`/`runStructured`
  (`mock-runner.ts:105-143`) emit **nothing** to any bus (its events exist only in
  `stream()`'s yielded generator, `:214+`). So `runEval` + MockRunner + RunStoreExporter
  = zero rows — correct per contract, and why the tests below use a small
  lifecycle-emitting stub that simulates exactly what `AgentRunner` emits.
- **A pure-`FunctionStep` target produces no `runs` row** (no runner call ⇒ no
  lifecycle events). Per-case persistence for arbitrary targets remains E1's
  `EvalSpec.onResult` → manual `startRun`/`finishRun` seam (`storage/run-store.ts:15`).
- **One case may produce *multiple* `runs` rows** — a composite node with N `AgentStep`
  leaves = N runner calls = N rows, **all sharing the case's `traceId`**. That is by
  design and matches `RunStoreExporter`'s own doc ("nested sub-agent runs … each get
  their own row for free; `traceId` ties a multi-agent trace together",
  `run-store.ts:10-12`). The case→run join key is `trace_id`, not `run_id` — exactly
  what `EvalResult.traceId` records.

**Known hazard (pre-existing, out of scope):** `AgentRunner` *rebinds*
`this._eventBus = options.eventBus` (`agent-runner.ts:283-285`) — a per-call bus
**permanently** redirects a shared runner's future events. In the intended wiring the
bus passed to `runEval` IS the runner's own shared bus (playground precedent:
`agent-cli/src/commands/playground.ts:71` constructs the `AgentEventBus`, `:90-94` hands
it to `createRunner({ eventBus, … })`), making the rebind a no-op. Callers passing a
*different* bus to an eval over a shared runner inherit this pre-existing runner
behavior; fixing it means editing `agent-runner.ts` — fenced out by §13. Noted in the
wrapper's doc comment.

### Step 1 — `eval/run-eval.ts`: `eventBus` on `EvalRunContext` (exact diff in § Interfaces)

Add `readonly eventBus?: AgentEventBus` after `traceId`. Type-only import
`AgentEventBus` from `../events/agent-event-bus.js` (events = layer 5, below eval —
same direction as `exporters/`' imports; precedent `agent-runner.ts:36`).

### Step 2 — per-case `traceId`: format decision

**Format: `` `${base}:${evalCase.id}` `` where `base = ctx.traceId ?? generateId()`,
minted ONCE per `runEval` invocation. Minting is gated on `ctx.eventBus` being present.**

Rationale, mapped to the doc's suggested `${runId}:${case.id}`:

- The doc's "`runId`" is the **suite-invocation id** (E1's `eval_run.id`) — which
  `runEval` does not and should not know (the engine has no store). The pre-existing
  `EvalRunContext.traceId?` field is the caller's seam for exactly this: **E4's CLI will
  pass the `eval_run` id as `ctx.traceId`**, making case traces `<evalRunId>:<caseId>`
  — the doc's formula, with the base caller-owned. When no base is supplied,
  `generateId()` (from `"ai"` — the runtime's established id mint: `agent-runner.ts:287`,
  `as-agent.ts`, `mock-runner.ts`) keeps re-runs of the same suite collision-free.
- **Colon-safety verified:** no code anywhere in runtime/server/dashboard splits or
  parses `traceId` (grep `traceId.split|split(":")` = 0 hits); it is an opaque key in
  `EventStore`, the collector, and the dashboard. `generateId()` output is alphanumeric
  (no colons), so `LIKE '<base>:%'` prefix queries over `runs.trace_id` recover a whole
  suite unambiguously.
- Trace-id convention check: `AgentRunner` treats `options.traceId` as authoritative
  (`effectiveTraceId = options?.traceId ?? runId`, `agent-runner.ts:288`) and stamps it
  on every event — so a per-case id groups the case's *entire* subtree (multi-leaf
  composites included) under one trace, which is precisely what the E5 drill-down
  (existing `EventStream` filtered by traceId) needs.
- Boundary: two cases with the same `id` in one suite collide (the `:170-177` envelope
  validation doesn't dedupe, and E3's loaders don't either). Accepted; see Open
  questions.

**No-bus gate is load-bearing for byte-identity:** `AgentRunner` falls back to the
**global** bus when constructed without one (`getAgentEventBus()`,
`agent-runner.ts:138-143`) — so a real-runner eval *today* already emits events under
`ctx.traceId ?? <per-run runId>`. Unconditionally minting per-case ids would silently
reshape existing callers' traces. Hence: **no `ctx.eventBus` → `nodeCtx.traceId` stays
`ctx.traceId` exactly as today, no wrapper, no stamping.**

### Step 3 — the bus-delivery wrapper (eval-local, per case)

A module-private helper in `run-eval.ts` (NOT exported, NOT in any barrel):

- Wraps `ctx.runner` per case, injecting `{ eventBus, traceId: options?.traceId ??
  caseTraceId }` into the `RunOptions` of `run`, and — **only if present on the
  wrapped runner** — `runStructured` and `stream`. Preserving *absence* matters:
  `AgentStep` fails loud via `StructuredOutputUnsupported` when the resolved runner
  lacks `runStructured` (`agent-step.ts:123-126`); fabricating the method would mask
  that contract.
- Calls through as method calls on the wrapped runner (`runner.run(…)`) so `this`
  binding is preserved (`AgentRunner` uses instance state throughout).
- Per-case construction (closes over `caseTraceId`) — one small object per case,
  negligible.
- Known boundary (documented in its comment): a per-node runner override
  (`AgentStepSpec.runner`, #116 — `agent-step.ts:112` resolves `spec.runner ??
  ctx.runner`) bypasses the wrapper; such a step's events go wherever *that* runner's
  bus points. Same story as everywhere else in the runtime — the override is explicit
  opt-out.

### Step 4 — the loop wiring + `EvalResult` stamping

Sketch of the `runEval` diff (`:184-233`; full signatures in § Interfaces):

```
  const { node, kind } = resolveEvalTarget(spec.target);
+ const bus = ctx.eventBus;
+ const traceBase = bus ? (ctx.traceId ?? generateId()) : undefined;

  for (const evalCase of spec.cases) {
+   const caseTraceId = traceBase === undefined ? undefined : `${traceBase}:${evalCase.id}`;
    const nodeCtx = {
-     runner: ctx.runner,
+     runner: bus && caseTraceId ? withEvalBus(ctx.runner, bus, caseTraceId) : ctx.runner,
      hooks: ctx.hooks,
      toolExecutor: ctx.toolExecutor,
-     traceId: ctx.traceId,
+     traceId: caseTraceId ?? ctx.traceId,
      scratchpad: createScratchpad(),
    };
    …
    const result: EvalResult<TIn, TOut, TExpected> = {
      case: evalCase,
      output: …,
      scores,
      succeeded: …,
      error: …,
+     ...(caseTraceId === undefined ? {} : { traceId: caseTraceId }),
      inputTokens: …,
      outputTokens: …,
    };
```

The **conditional spread** (not `traceId: maybeUndefined`) keeps the no-bus result
object's key set identical to today's — `"traceId" in result === false` — honoring
"byte-identical" literally (`exactOptionalPropertyTypes` is `false` in
`tsconfig.base.json:19`, so either compiles; the spread is chosen for shape fidelity).

`traceId` is stamped on **every** result when a bus is present — including
`succeeded: false` cases (the failing trace is the one E5 most wants to open) — because
the id is minted *before* `node.run`, not derived from its outcome.

### `EvalRunContext` (`eval/run-eval.ts:34-39`) — exact diff

```ts
import { generateId } from "ai";
import type { AgentEventBus } from "../events/agent-event-bus.js";
import type { RunOptions, RunnerProtocol, ToolExecutor } from "../runner/types.js";

export interface EvalRunContext {
  readonly runner: RunnerProtocol; // INJECTED — MockRunner in tests
  readonly hooks?: PatternHooks;
  readonly toolExecutor?: ToolExecutor;
  /** Suite-level trace base. With `eventBus` set, per-case ids are `${traceId}:${case.id}`
   *  (base minted via generateId() when absent); without a bus it threads to every
   *  node.run unchanged, exactly as before #133. E4 passes the eval_run id here. */
  readonly traceId?: string;
  /**
   * NEW (#133, doc §5): observability bus for eval runs. When set, runEval mints a
   * per-case traceId, delivers bus + traceId into each LLM leaf's RunOptions (via a
   * per-case runner wrapper — AgentRunner honors RunOptions.eventBus), and stamps the
   * traceId onto the EvalResult. Attach a RunStoreExporter to this bus and each case
   * also lands RunStore `runs` row(s) — the E2 fusion. Absent → byte-identical to
   * pre-#133 behavior. NOTE: AgentRunner rebinds its instance bus to a per-call
   * RunOptions.eventBus (agent-runner.ts:283) — pass the runner's own shared bus
   * (the playground pattern) unless you intend that redirect.
   */
  readonly eventBus?: AgentEventBus;
}
```

export interface EvalResult<TIn, TOut, TExpected = unknown> {
  readonly case: EvalCase<TIn, TExpected>;

  readonly outputTokens: number;

  case: EvalCaseSchema,
  output: z.unknown().optional(),

### `withEvalBus` (module-private in `run-eval.ts`) — shape

```ts
/** Per-case runner wrapper: injects the eval bus + case traceId into RunOptions.
 *  Preserves absence of optional protocol methods (AgentStep's
 *  StructuredOutputUnsupported check must still fire). Not exported. */
function withEvalBus(
  runner: RunnerProtocol,
  eventBus: AgentEventBus,
  caseTraceId: string,
): RunnerProtocol {
  const opts = (o?: RunOptions): RunOptions => ({
    ...o,
    eventBus,
    traceId: o?.traceId ?? caseTraceId,
  });
  const wrapped: {
    run: RunnerProtocol["run"];
    runStructured?: RunnerProtocol["runStructured"];
    stream?: RunnerProtocol["stream"];
  } = {
    run: (agent, message, o) => runner.run(agent, message, opts(o)),
  };
  if (runner.runStructured) {
    wrapped.runStructured = (agent, message, schema, o) =>
      // biome/TS: non-null is safe — guarded one line up
      runner.runStructured!(agent, message, schema, opts(o));
  }
  if (runner.stream) {
    wrapped.stream = (agent, message, o) => runner.stream!(agent, message, opts(o));
  }
  return wrapped;
}
```

## Non-goals (scope fences)

- **No edits outside `eval/`** — not `workflows/node.ts` (no `eventBus` on
  `NodeRunContext`), not `agent-step.ts`, not `agent-runner.ts` (its bus-rebinding
  mutation at `:283-285` is pre-existing and stays), not `mock-runner.ts` (teaching it
  to emit lifecycle events is a possible follow-up, not E2), not `exporters/` or
  `storage/` (RunStoreExporter and RunStore ship as-is; the fusion is wiring, not code).
- **No synthetic run-lifecycle events from `runEval`** — the runner is the producer;
  see the crux section. A no-LLM (`FunctionStep`-only) case therefore yields no `runs`
  row; E1's `onResult` seam is the universal persistence path for that.
- **No `eval_result` writing, no `EvalStore` wiring** — that is E1's shipped seam
  consumed by E4; E2 only makes `traceId` available to join on.
- **No CLI (#135), no server routes (#136), no dashboard (#137).** The playground's
  shared-bus wiring for eval is E4's step.
- **No concurrency change** — the loop stays sequential (#103 Decisions).

## Open questions

1. **Duplicate case ids** collide traceIds within a suite (`a`,`a` → `base:a`,`base:a`).
   Envelope validation (`run-eval.ts:170-177`) could reject duplicates — but that is a
   behavior change for bus-less callers too, so it is NOT done here. Recommend E4
   dedupe/validate at load time; revisit if E5's per-case drill-down mis-joins.
2. **Should `MockRunner` learn to emit the lifecycle when `options.eventBus` is set?**
   Would let consumers test the fusion without a custom stub. Deferred — engine fence;
   candidate for a post-stack DX issue.
3. **`stream` wrapping is speculative** — no eval path calls `runner.stream` today; it
   is wrapped for protocol completeness only. Drop it if review prefers a two-method
   wrapper.
