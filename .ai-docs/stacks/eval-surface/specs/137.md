# Spec — Eval tab: read-only review UI (#137, E5a — the milestone closer)

## Goal

One new **"Evaluate" nav group** (`AppShell.tsx`) + two client routes (`/eval`,
`/eval/runs/:id`) + a read-only page pair over #136's four GETs. **Run history**
(`EvalRunsPage`): filterable by set / target / variant / split, newest first,
row-click into detail. **Run detail** (`EvalRunDetailPage`): run header +
summary pills (the handler-computed `EvalRunSummary` from `GET /eval/runs/:id`)
+ a per-case `DataTable` with tri-state pass/fail badges and scores; expanding a
row shows **side-by-side actual-vs-expected** (expected joined client-side from
`GET /eval/sets/:id/cases` — the joined result row does not carry it, finding 5)
plus the full score list, and a **lazy trace drill-down** that embeds the
existing presentational `EventStream` fed by a new `fetchTraceEvents(traceId)`
helper (client-side `traceId` filter over `GET /admin/events/recent` — the
cheapest honest option; decision below). Every degraded state renders something
useful: 503-unconfigured, zero runs, empty filter result, missing case bank,
absent/purged trace.

Read-only: **no run-from-UI, no A/B compare, no capture-from-session** (epic 2 —
#138/#139/#140). No server or runtime changes. Dashboard is Vite-built into
agent-cli assets at package build — no runtime dep added.

## Approach

### Verified against the branch tip (2026-07-03, `dug/137-eval-tab` @ `835dba0`, forked from `origin/dug/136-eval-server-api`)

1. **Anchor drift, minor.** `navGroups` at `AppShell.tsx:5` — exact. The route
   table has grown to `App.tsx:21-39` (issue said `:23-35`; the build-door
   routes landed above the RUN block). `EventStream` is at
   `components/organisms/EventStream.tsx` (the issue already noted the doc's
   `components/` path drifted — confirmed). Dashboard test count at tip: **34
   `it()` blocks across 5 files** (issue brief said 35 — count at this tip
   is 34).
2. **`EventStream` is purely presentational** — props are `{ events:
   StreamEvent[] }` (`EventStream.tsx:57-61`), rendering time/badge/summary rows
   with click-to-expand JSON. Embedding it costs nothing; the SSE hook
   (`useEventStream`) is *not* needed for historical traces. Its root div
   hardcodes `height: "calc(100vh - 220px)"` (`:90`) — it gains an optional
   `height` prop (default preserving current callers) so the embedded panel
   sizes to the expanded row.
3. **No trace-by-id query exists anywhere on the read path.**
   `EventStore.recent()` filters `since`/`type`/`limit` only
   (`event-store.ts:303`); `GET /admin/events/recent` exposes exactly those
   params (`agent-server/src/routes/events.ts:49-64`); `useEventStream` is
   live-SSE-only. **But** the response rows carry a top-level `traceId`
   (`rowToPersisted`, `event-store.ts:420`), and #133 stamps every eval case's
   events with `traceId = <evalRunId>:<caseId>` — the same value
   `JoinedEvalResultRow.traceId` returns. So a client-side filter is exact.
4. **`lib/eventApi.ts` is the precedent seam**: `fetchRecentEvents` already does
   REST → `StreamEvent` mapping, DESC→ASC reversal, and 503 → `[]` graceful
   degradation (`eventApi.ts:39-61`, tested in `__tests__/eventApi.test.ts`).
   Its `PersistedEventRow` interface just doesn't surface `traceId` yet — the
   wire has it.
5. **`JoinedEvalResultRow` carries NO `input`/`expected`** (verified,
   `eval-store.ts`) — actual-vs-expected requires joining the case bank:
   fetch `GET /eval/sets/:setId/cases` for `run.setId` and index by `caseId`.
   `finalAnswer` is stored as the raw string `finishRun` received; the #135 CLI
   writes JSON-serialized output (e.g. `"\"42\""` — 136.md example), so the
   actual panel safe-parses before pretty-printing, falling back to the raw
   string.
6. **The dashboard is standalone** (no `@agentic-patterns/runtime` dependency —
   `package.json` deps: react, react-router-dom, xyflow, lucide, markdown).
   Row types are mirrored by hand into `api/types.ts`, the existing convention
   (`ConversationSummary` et al. mirror server shapes). Shapes to mirror,
   verified against `eval-store.ts` + 136.md: `EvalSetSummary`, `EvalCaseRow`,
   `EvalRunRow`, `JoinedEvalResultRow`, `EvalScoreLike`, plus #136's
   handler-computed `EvalRunSummary`.
7. **Page precedents.** List: `ConversationsPage` (DataTable + sort state +
   row-click `navigate` + empty-state Card + loading Spinner + error Card).
   Detail: `ConversationDetailPage` (`useParams` + sequential dependent
   `fetchJSON` calls + back-link header). `DataTable` already supports
   `renderExpanded` / `expandedKey` / `onToggleExpand` (`DataTable.tsx:19-35`)
   — purpose-built for the per-case expansion; no new table organism.
8. **Test idiom**: `@testing-library/react` + jsdom + `vi.stubGlobal("fetch")`
   (`DashboardPage.test.tsx:40-50`) for page-render tests; pure-helper suites
   for lib code (`eventApi.test.ts`). Both apply directly here.
9. **Vite dev proxy** (`vite.config.ts:34-41`): `/eval` needs a proxy entry
   with the existing `htmlNavBypass` (which also makes dev-mode hard-refresh
   on `/eval` serve the SPA). In production (`ap playground`) the SPA and API
   are same-origin and #136 already added `/eval` to `API_PREFIXES`.
10. **Deep-link tradeoff is pre-existing and accepted** (136.md finding 6):
    in production, a hard refresh on `/eval` or `/eval/runs/:id` returns API
    JSON, exactly like `/conversations/:id` and three other tabs today;
    client-side navigation from `/` is how the dashboard reaches every tab.
    `/eval` joins that tradeoff — see Decisions for the `/evaluate` dodge we
    considered and rejected.

### The drill-down decision (the issue's escape hatch, resolved)

Acceptance bar: *"Case row links to its trace view (trace_id-filtered
EventStream renders events)."* Three options, judged against the real plumbing:

- **Link out to an existing view filtered by traceId — REJECTED as dishonest.**
  No existing view accepts a traceId. `LivePage` and `ClaudeCodePage` consume
  `/admin/events/stream` (live SSE); a historical eval trace reviewed after
  `ap eval` finishes would render an empty stream. `GraphPage` replays from
  live events too. A link that lands on "Waiting for events…" fails the
  acceptance in the honest case (review-after-run is THE use case).
- **New server route (`GET /admin/events/trace/:traceId` + an
  `EventStore.traceEvents()` method) — DEFERRED, named follow-up.** Cleanest
  (the `idx_events_trace` index exists for exactly this), but grows #137 across
  runtime + server right after #136 shipped that surface, for precision the
  v1 page doesn't need. If the recent-window caveat below ever bites, this is
  the one-route fix.
- **CHOSEN: embed `EventStream` in the expanded case row, fed lazily by
  `fetchTraceEvents(traceId)`** — a ~20-line addition to `lib/eventApi.ts`:
  `GET /admin/events/recent?limit=10000`, filter rows on the top-level
  `traceId` (finding 3), reuse the existing `StreamEvent` mapping + ASC
  reversal. Zero server change; 503 degrades to `[]` like the precedent.
  Fetch happens on an explicit "Load trace" click, not on row expand — no 10k
  fetch per casual expansion. **Caveat, documented in the UI**: traces older
  than the 10,000 most-recent events (or purged by the store's retention
  caps) return empty → the panel renders "No trace events found — the event
  log may have been purged." Eval review is run-then-review, so the trace is
  near the head of the log in the honest path.

Not embedding the `trace-from-events` → constellation replay: the acceptance
requires the EventStream list, not the graph; the replay embed is exactly the
kind of ballooning the issue told us to shear off (epic-2 polish).

### Data fetching

- **`EvalRunsPage`**: one-shot mount fetch `fetchEvalRuns({ limit: 200 })` + a
  ghost "Refresh" button in the header (the `LivePage` Clear-button idiom).
  **No polling** — the data is CLI-driven and reviewed after the fact, and
  one-shot keeps the 503-unconfigured state cleanly distinguishable (decision
  below). Filters are **client-side** over the fetched window via a pure,
  exported `filterRuns(runs, filters)`; facet options are the distinct values
  across the *unfiltered* window, so selecting one facet never collapses the
  other dropdowns' options.
- **`EvalRunDetailPage`**: `fetchEvalRunDetail(id)` → then, when `run.setId`
  is non-null, `fetchEvalCases(run.setId)` → `Map<caseId, EvalCaseRow>`
  (sequential dependent fetches — the `ConversationDetailPage` precedent).
  404 → "run not found" card with a back link. Missing bank / missing case →
  per-panel fallback, not a page error.
- **Trace**: `fetchTraceEvents(traceId)` on explicit click (above).

All helpers live in `lib/evalApi.ts` (the `lib/eventApi.ts` sibling) and
discriminate 503 explicitly: `type EvalFetch<T> = { kind: "ok"; data: T } |
{ kind: "unconfigured" }` — non-503 failures throw (page renders the standard
error Card). This is why the pages don't use `useAdminData`: its error channel
is a flat string, and "persistence off" must render a different surface than
"server broke".

### Filter UX (`EvalRunsPage`)

A filter bar of four `<select>`s above the table — Set, Target, Variant
(options = distinct non-null values from the fetched runs, each with an "all"
default) and Split (`all | train | dev | test | untagged`; `untagged` matches
`split === null`) — plus a "Clear filters" ghost button shown only when any
filter is active. Filtering is pure client-side (`filterRuns`); an active
filter set that matches nothing renders an inline "No runs match the current
filters" row, not the zero-runs empty state.

History table columns: run id (mono, `shortId`), set, target, variant, split
(Badge), status (Badge: `ok` green / `error` red / `running` emerald), model,
started (`relative()` — lift the `ConversationsPage` local helper as-is into
the new page file; the redesign doc's "pages never share code" rule keeps it
page-local until a third page needs it). Sortable via the `ConversationsPage`
sort-state idiom; row-click → `/eval/runs/:id`. No pass-rate column — the list
endpoint doesn't carry it and N+1 detail fetches are not worth a column.

### Run detail layout (`EvalRunDetailPage`)

- **Header**: back link ("← Eval runs"), run id, status Badge; a meta row of
  Badge/Chip pills — target, variant, split, model, `gitSha` (7-char mono),
  started + duration (`tsStart`/`tsEnd`).
- **Summary pills** (from the response's `summary`): cases, passed, failed,
  ungated, errored, passRate (rendered `—` when `null`), tokens in/out.
  Stat-pill row like `DashboardPage`'s headline cards, one Card.
- **Per-case table** (`DataTable` with `renderExpanded`): caseId (mono), pass
  (tri-state Badge: `pass` green / `fail` red / `ungated` muted — `pass` is
  `boolean | null`), scores summary (compact `passed/total` count + first
  score `name: value`), run status (red `error` Badge when
  `runStatus === "error"`), tokens (in+out), elapsed. Row click toggles
  expansion (`expandedKey`/`onToggleExpand`, single-row-open).

### Expanded case row (`CaseDetail`)

Top-to-bottom inside the expanded block:

1. **Actual vs expected, side-by-side** — a two-column grid (`1fr 1fr`) of
   labeled `<pre>` panels: **Expected** = pretty-printed `case.expected`
   (already-parsed `unknown` from the bank); **Actual** = pretty-printed
   `safeParseAnswer(finalAnswer)` (JSON-parse with raw-string fallback,
   finding 5). On `pass === false` the Actual panel gets a red border tint.
   When `runStatus === "error"`, the Actual panel is replaced by a red error
   panel showing `runError`. When the case is missing from the bank
   (`run.setId` null, bank fetch failed, or `caseId` absent), the Expected
   panel renders "expected unavailable — case not in bank". The case `input`
   renders above the grid as a single collapsed-by-default `<pre>` (context
   for reading the diff).
2. **Scores** — full list: name, value, passed (Badge), `detail`/`error`
   expandable JSON. Renders "no scores recorded" when `scores` is null/empty.
3. **Trace** — when `traceId` is non-null: a "Load trace" ghost Button + the
   mono traceId; on click → spinner → `fetchTraceEvents` →
   `<EventStream events={…} height={360} />`, or the purged-empty message.
   When `traceId` is null: muted "No trace recorded for this case."

## Open questions

None blocking. Recorded decisions an implementer should not re-litigate:

- **Client route is `/eval` (shadowed on prod hard-refresh), not `/evaluate`.**
  #136's `isApiPath` tests guarantee `/evaluate` stays SPA-safe, so a
  deep-link-surviving dodge exists — rejected here for consistency (four tabs
  already accept the tradeoff; the issue and doc both name `/eval`; two URL
  vocabularies for one surface is worse than the caveat).
- **Client-side filtering over one `limit=200` fetch**, not the server's
  filter params — stable facet options, zero extra round-trips at review
  scale; the server params (#136) remain the switch path.
- **One-shot fetch + Refresh button, no polling** — CLI-driven data; keeps
  the 503-unconfigured state a first-class UI state instead of a string-match
  on `useAdminData`'s error channel.
- **Trace drill-down = Option A** (embedded EventStream over client-filtered
  `/admin/events/recent`) with the 10k-window caveat rendered honestly;
  Option B (server route) is the follow-up, not part of this PR.
- **Lazy trace fetch on click**, never on row expand.
