# Spec — A/B compare + split-aware aggregates (#138, E5b — the two views §4 keyed the schema for)

## Goal

Two additive dashboard views over Epic-1's shipped substrate. **A/B compare**:
select two runs on `/eval` → `/eval/compare/:aId/:bId` renders both runs'
provenance side by side (variant free label + `git_sha`/`model` alongside,
§16.2), a six-bucket delta summary (both-passed / both-failed / regressions /
improvements / only-in-A / only-in-B), and a per-case aligned table over the
**union** of case ids — cases present in only one run render as a muted
**not-run** badge, never an error. Expanding a row shows A-vs-B actual answers
side by side with per-side scores and lazy trace drill-down. **Split-aware
aggregates**: a panel on `/eval` (above the runs table, driven by the page's
existing set/target/variant facet filters) renders per-split pass-rate bars
from one new read endpoint, plus the **overfit gap** stat — `train` pass-rate
minus `test` pass-rate — whenever both buckets are present.

Server change is exactly **one additive read GET**
(`GET /eval/aggregates/splits`) exposing the store's shipped `splitAggregates`
query; compare needs **no server change** (decision + evidence below). No
write routes, no run-from-UI (#139), no capture-from-session (#140), no
runtime/store changes.

## Approach

### Verified against the branch tip (2026-07-04, `dug/138-ab-compare` @ `f189b33`, forked from `origin/main` — Epic 1 fully merged)

1. **Both store queries the doc promised already exist, shapes matching §4's
   intent exactly.** `EvalStore.compareEvalRuns(aId, bId): EvalComparison`
   (`agent-runtime/src/storage/eval-store.ts:460-506`) aligns on the sorted
   union of case ids, keeps one-sided rows with the other side `null`, and
   returns the six-bucket summary (`EvalComparison`, `:154-166`: `bothPassed /
   bothFailed / onlyAPassed / onlyBPassed / aOnly / bOnly` — the comment at
   `:161` names `onlyAPassed` as "regressions when A = old, B = new").
   `EvalStore.splitAggregates(opts): SplitAggregate[]` (`:509-528`) is the
   per-split rollup, filterable by `setId / targetId / variant`, with
   `passRate: null` when no result carried a pass verdict. **No anchor drift
   against the doc** — the promised shapes shipped verbatim in #132.
2. **Neither query is exposed over HTTP.** `routes/eval.ts` serves exactly
   four GETs (`/eval/sets` `:20`, `/eval/sets/:id/cases` `:27`, `/eval/runs`
   `:46`, `/eval/runs/:id` `:65`). This issue's central decision is which side
   of the wire each view computes on — resolved per-view below.
3. **The compare payload is *richer* client-side.** The store's
   `EvalComparisonRow` (`eval-store.ts:142-152`) carries only `{pass, scores}`
   per side. The compare UI needs per-side `finalAnswer` (the actual-answer
   diff), `traceId` (drill-down), `runStatus`/`runError` (distinguish errored
   from not-run), tokens and `elapsedMs` — all of which
   `GET /eval/runs/:id` already returns per case as `JoinedEvalResultRow`
   (`eval-store.ts:124-140`, mirrored at `agent-dashboard/src/api/types.ts:177`).
4. **The aggregates rollup is NOT reconstructible client-side without an N+1
   fan-out.** Two independent reasons: (a) it aggregates over *all*
   `eval_result` rows in the DB across runs — reconstruction needs
   `GET /eval/runs?limit=500` then one `GET /eval/runs/:id` per run;
   (b) per-case split truth is `COALESCE(eval_case.split, eval_run.split)` —
   case-level split wins, run label is the fallback
   (`eval-store.ts:303-316`, the `_splitAggregatesStmt` SQL) — and
   `JoinedEvalResultRow` carries **no split field at all**, so even one run's
   rows can't be classified without also fetching its set's case bank.
5. **Issue key-file drift (expected).** The issue names
   `pages/EvalPage.tsx`; #137 shipped the surface as
   `pages/eval/{EvalRunsPage,EvalRunDetailPage,CaseDetail}.tsx` with routes
   `/eval` + `/eval/runs/:id` (`App.tsx:41-43`) and an "Evaluate" nav group
   (`AppShell.tsx:27-30`). This spec extends those.
6. **`~/retrieval-agent-2.0/canvas-workstation/.eval/viz.ts` is not present on
   this machine** — the reference is used as *idea only* via the doc's
   description (§9: "rollup-by-arm/mode, per-run drawer"): rollup keyed by the
   arm label (here: variant/split) with a per-row drill-in, which is exactly
   the panel + expandable-table shapes below.
7. **Existing conventions to reuse, verified:** `EvalFetch<T>` 503
   discrimination (`lib/evalApi.ts:14`), `filterRuns` pure-filter +
   client-side facets (`:90`, `EvalRunsPage.tsx:92-111`), `safeParseAnswer`
   (`:111`), the `Stat` tile (`EvalRunDetailPage.tsx:324`), `CaseDetail`'s
   side-by-side grid + error rendering (`CaseDetail.tsx:67-100`) and its lazy
   `TraceSection` (`:152-193`), `fetchTraceEvents` (`lib/eventApi.ts`),
   `notConfigured`/`parseSplit` route helpers (`routes/eval.ts:86-110`), the
   real-SQLite-seeded route test harness
   (`agent-server/src/__tests__/eval.test.ts:22-50`), and the
   jsdom + testing-library + `vi.stubGlobal("fetch")` page-test idiom
   (`agent-dashboard/src/__tests__/EvalRunsPage.test.tsx`). SPA prefix `/eval`
   is already allowlisted (`agent-cli/src/commands/playground.ts:219`, fixed
   in #136) — **no CLI change**.

### The client-vs-server decision (the issue's explicit fork, resolved per view)

**A/B compare — client-side, zero new endpoints.** Two parallel
`fetchEvalRunDetail` calls (both already served) provide strictly more data
per case than the store's `EvalComparisonRow` (finding 3). Exposing
`compareEvalRuns` over HTTP would return the *poorer* payload and the page
would still need both detail fetches for the drill-down — a third request and
duplicated data for nothing. Alignment + delta summary is a pure O(n) merge
(~40 lines), landed in a new `lib/evalCompare.ts` and unit-tested for **parity
with `compareEvalRuns` semantics**: sorted union of case ids; one-sided rows
keep the other side null; the six summary buckets count exactly as
`eval-store.ts:488-497` does — including the subtlety that a pair where both
sides are present but neither `pass` is `true`/`false` (ungated) increments
**no** bucket. The store method remains the CLI/programmatic compare surface;
it is deliberately not wired to HTTP in this issue.

**Split aggregates — one additive read GET.** Client-side reconstruction is
genuinely insufficient (finding 4: N+1 fan-out + the COALESCE split-precedence
needs data no run-scoped GET carries). The store query already exists and is
tested (#132); the route is ~20 lines following #136's conventions verbatim:

| Method | Path | Query params | Returns |
|---|---|---|---|
| GET | `/eval/aggregates/splits` | `set`, `target`, `variant` (all optional; names match `GET /eval/runs`, `routes/eval.ts:55-60`) | `{ aggregates: SplitAggregate[] }` |

503-unconfigured via the existing `notConfigured` helper; no param → global
rollup; unknown set/target/variant → `{ aggregates: [] }` (200, not 404 —
filters are narrowing, not lookups, same stance as `GET /eval/runs`).
Read-only — the "no write routes" fence holds. Path is namespaced under
`/eval/aggregates/` so future groupings (by variant, by target) slot in
beside it.

### UI — compare entry point (`EvalRunsPage`)

- New leading **checkbox column** on the runs `DataTable`. The cell's
  click handler must `stopPropagation()` — row click already navigates to the
  detail page (`EvalRunsPage.tsx:285`). Selection is capped at 2: with two
  selected, remaining checkboxes render disabled.
- When ≥1 row is selected, a **compare bar** renders between the filter row
  and the table: "`N of 2 selected`" + a `Compare` button (enabled at exactly
  2) + a ghost `Clear` button. Compare navigates to
  `/eval/compare/:aId/:bId` with **A = the older run by `tsStart`** — so the
  default read is A = baseline, B = candidate, and "regressions" means what it
  says (finding 1, `eval-store.ts:161`).
- Selection state is page-local (`useState<Set<string>>`), cleared on
  Refresh; it does not survive navigation (the URL is the durable artifact).

### UI — the compare page (`EvalComparePage`, route `/eval/compare/:aId/:bId`)

Deep-linkable and refresh-safe; the URL is the source of truth for A/B order.
A small `Swap` header button navigates to the swapped URL.

- **Fetch:** `Promise.all([fetchEvalRunDetail(aId), fetchEvalRunDetail(bId)])`.
  States follow the detail-page grammar (`EvalRunDetailPage.tsx:75-80`):
  `loading` / `unconfigured` (either 503) / `not-found` (either 404 — the card
  names which id) / `error` / `ok`.
- **Provenance header:** two side-by-side cards labeled `A · baseline` and
  `B · candidate`, each with the detail page's badge row idiom
  (`EvalRunDetailPage.tsx:227-237`): variant · target · split · model ·
  short `gitSha` (full sha on `title` hover) · started · status badge. This is
  §16.2 rendered: variant stays a free label, provenance sits beside it.
- **Different-set banner** (non-blocking) when `a.run.setId !== b.run.setId`:
  "runs are from different sets — case alignment may be sparse". Compare still
  renders; the store doesn't forbid it either.
- **Delta summary strip:** six `Stat` tiles from `summarizeComparison` —
  Both passed / Both failed / **Regressions** (A ✓ B ✗, red when > 0) /
  **Improvements** (A ✗ B ✓, green when > 0) / Only in A / Only in B.
- **Aligned per-case table** (`DataTable`, rows from `alignResults`, sorted
  union of case ids): Case | A (tri-state pass/fail/ungated badge, or muted
  **`not run`** when the case is absent from A) | B (same) | Δ (a
  `classifyDelta` badge: `regression` red / `improvement` green / `same` and
  `ungated` muted / `not run` muted) | Scores A | Scores B (the
  `scoresSummary` one-liner idiom, `EvalRunDetailPage.tsx:67-73`).
- **Expanded row:** side-by-side A/B "Actual" panels (safe-parsed
  `finalAnswer`; `runStatus === "error"` renders the red-bordered `runError`
  panel exactly as `CaseDetail.tsx:78-98`; an absent side renders the muted
  "not run in this eval run" line); per-side score lists; per-side lazy trace
  drill-down by reusing `TraceSection` — **exported** from `CaseDetail.tsx`
  (same-door reuse inside `pages/eval/`; `CaseDetail` is already the shared
  expanded-row module there). When both runs share a non-null `setId`, the
  page also fetches the case bank once (`fetchEvalCases`, degrading exactly
  as `EvalRunDetailPage.tsx:107-119` — never a page error) and shows the
  collapsed Input + Expected block above the A/B panels for context.

**Graceful-degradation semantics (acceptance bullet 3, made precise):** a case
id present in only one run is a *coverage* fact, not a failure — it renders as
the muted `not run` badge in the missing column, counts only into
`aOnly`/`bOnly` (never into failed/regression buckets), and its Δ is `not
run`. Distinct from an **errored** case (`runStatus === "error"`), which is
present-with-error: red `error` treatment on that side, per `CaseDetail`'s
existing grammar.

### UI — split aggregates panel (`SplitAggregatesPanel`, on `/eval`)

- Placement: between the filter row and the runs table on `EvalRunsPage`,
  inside its own `Card`, heading "Split aggregates".
- Data: `fetchSplitAggregates({ set, target, variant })` wired to the page's
  **existing facet filter state** (the `split` facet is deliberately not
  passed — the panel *groups by* split). Refetches when those three filter
  values change. A caption states the scope ("all results" vs the active
  filter values) — the panel aggregates the whole store, not the 200-run
  table window, and says so.
- Render per bucket (ordered `train`, `dev`, `test`, then `untagged` = null
  split): split `Badge` · `passed/failed/results` counts · a pass-rate
  **meter** (two nested divs, `var(--green)` fill on `var(--bg-inset)` track —
  no chart library) · the percentage (or `—` when `passRate` is `null`).
- **Overfit gap stat:** when both `train` and `test` buckets exist with
  non-null pass rates, a `Stat` tile renders
  `gap = (train.passRate − test.passRate) × 100` as signed percentage points,
  red-tinted when positive (train ≫ test = the overfit signal, §7), muted
  otherwise. Absent either bucket or either rate, the tile is omitted — no
  guess, which is the point.
- Degradation: `unconfigured` → panel renders nothing (the page's existing
  unconfigured card already covers the state); empty `aggregates` → one muted
  line "no scored results yet"; fetch error → muted inline error in the panel,
  **never** blocking the runs table.

## Interfaces

```ts
// packages/agent-dashboard/src/api/types.ts — mirror of eval-store.ts:168-174
export interface SplitAggregate {
  split: EvalSplit | null;        // null = untagged bucket
  results: number;
  passed: number;
  failed: number;
  passRate: number | null;        // null when no result carried a pass verdict
}

// packages/agent-dashboard/src/lib/evalApi.ts
export interface SplitAggregateFilters { set?: string; target?: string; variant?: string }
export async function fetchSplitAggregates(
  filters?: SplitAggregateFilters,
  opts?: { baseUrl?: string },
): Promise<EvalFetch<SplitAggregate[]>>;

// packages/agent-dashboard/src/lib/evalCompare.ts — pure, mirrors compareEvalRuns semantics
export type DeltaKind =
  | "regression" | "improvement" | "same-pass" | "same-fail"
  | "ungated" | "a-only" | "b-only";

export interface ComparisonCaseRow {
  caseId: string;
  a: JoinedEvalResultRow | null;  // null = not run in A (full row kept — richer than the store's pass+scores)
  b: JoinedEvalResultRow | null;
  delta: DeltaKind;
}

export interface ComparisonSummary {   // bucket-for-bucket = EvalComparison["summary"] (eval-store.ts:158-165)
  bothPassed: number; bothFailed: number;
  onlyAPassed: number;                 // regressions when A = older/baseline
  onlyBPassed: number;
  aOnly: number; bOnly: number;        // not-run coverage, never failures
}

export function alignResults(
  a: readonly JoinedEvalResultRow[],
  b: readonly JoinedEvalResultRow[],
): ComparisonCaseRow[];                 // sorted union of caseIds

export function summarizeComparison(rows: readonly ComparisonCaseRow[]): ComparisonSummary;

export function overfitGap(
  aggregates: readonly SplitAggregate[],
): { train: number; test: number; gapPts: number } | null;  // null unless both buckets have non-null passRate

// packages/agent-server/src/routes/eval.ts — the one new handler (inside evalRoutes)
// GET /eval/aggregates/splits?set&target&variant
//   -> 503 notConfigured(c) | 200 { aggregates: evalStore.splitAggregates({ setId, targetId, variant }) }
```

Route components:

```ts
  filters: { set?: string; target?: string; variant?: string };
}): JSX.Element | null;
```

## Non-goals (scope fences)

- **No write routes / run-from-UI** — #139. **No capture-from-session** — #140.
  **No judge** — #141.
- **No runtime/store changes.** Both queries shipped in #132; `compareEvalRuns`
  is deliberately **not** exposed over HTTP (client-side is strictly richer —
  decision above). If a future CLI/API consumer wants wire-level compare,
  that's a one-liner route then, not now.
- **No chart library.** The pass-rate meter is two divs; the gap is a stat
  tile. (`viz.ts` is idea-reference only, and unavailable on this machine.)
- **No 3+-run compare, no cross-set alignment help** — different-set compare
  renders with a warning, nothing more.
- **No per-run split breakdown on `EvalRunDetailPage`** — the aggregates panel
  is store-wide by design; a per-run breakdown would need either the case-bank
  join client-side or an `evalRunId` filter on `splitAggregates` (a store
  change). Deferred until asked for.
- **No nav changes** (`AppShell.tsx` untouched) and **no CLI changes**
  (`/eval` SPA prefix already allowlisted, `playground.ts:219`).
