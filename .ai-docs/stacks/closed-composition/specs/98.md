# Spec — Node dependency injection: a typed user-dep channel on `NodeRunContext`

## Goal

`NodeRunContext` (`workflows/node.ts:27`) carries **framework infra** — `runner`,
`hooks`, `toolExecutor`, `traceId`, `scratchpad` — but has **no channel for
user-supplied dependencies** (API clients, resolvers, loggers, config). So every
consumer builder threads those deps into leaf nodes **by closure**: the
canvas-workstation `escalate.ts` header names this exactly — *"deps arrive by
closure (the framework-gap pattern)."*

This issue adds a **typed deps channel** to `NodeRunContext` that flows through
**every** composition combinator (Sequential / Parallel / FanOut / Loop /
Accumulate / CoordinatorStep) down to every leaf (`FunctionStep` / `AgentStep`),
**and** reaches the two root-context builders that construct a `NodeRunContext`
from scratch (`as-agent.ts`'s `NodeBackedRunner`, `node-tool.ts`'s `nodeTool`).

**Acceptance (from the plan):**
- A dep injected at the `run()` root is readable inside a nested
  `FunctionStep`/`AgentStep` **without closures**.
- Type-safe access pattern documented; **existing `Node` implementations
  unaffected (additive)** — everything compiles unchanged.

Scope is the **deps channel only**. Retry (#100), Loop-accumulator (#101), eval
(#103), and tool-exec bus-threading (#99/#102) are parallel/downstream issues —
do not pull them in. In particular, **cross-tool-boundary deps propagation**
(automatic flow of parent deps through the agent-as-tool / `node-tool` seam) is
scoped to the tool-execution-context work (#99/#102); here `nodeTool` only gains
an *explicit* injection param (see Boundaries).

## Key finding — the channel is one optional field; combinators propagate it for free (read before coding)

Every composite already threads context to its children with an **object-spread**:

| Combinator | ctx-construction site | Shape |
|---|---|---|
| `Sequential` | `sequential.ts:80` | `{ ...ctx, scratchpad: ctx.scratchpad ?? createScratchpad() }` |
| `Loop` | `loop.ts:53` | `{ ...ctx, scratchpad: ... }` |
| `Accumulate` | `accumulate.ts:47` | `{ ...ctx, scratchpad: ... }` |
| `Parallel` | `parallel.ts:88` | `{ ...ctx, scratchpad: parentSlots.fork() }` |
| `FanOut` | `fan-out.ts:80` | `{ ...ctx, scratchpad: parentSlots.fork() }` |
| `CoordinatorStep` | `coordinator-step.ts:133` | `{ ...ctx, toolExecutor }` |

Because each of these **spreads `ctx`**, any *new* field on `NodeRunContext` is
carried to children **automatically, with zero edits to any combinator**. This is
the whole elegance of the change and drives the design: DI is **one optional
field** (`deps`) on the contract plus **one new helper file**, and the six
combinators above need **no change** — they are *verified*, not modified.

The only sites that construct a `NodeRunContext` **fresh** (not by spread), and
therefore must be taught to pass `deps` through, are the **root builders**:
- `node-tool.ts:46–49` — `nodeTool()`'s `execute` builds `{ runner, scratchpad }`.
- `as-agent.ts:167–172` — `NodeBackedRunner.run()` builds `{ runner, hooks?, traceId?, scratchpad }`.
- Any direct top-level `node.run(input, { runner, deps })` caller (the primary
  acceptance path).

## Key decision — typed access via a branded-key registry (mirror `Slot<T>`), NOT a generic on `Node` and NOT an `any`-bag

Three candidate shapes were weighed:

1. **Third generic `Node<TIn, TOut, TDeps>`, threaded through every combinator.**
   *Rejected* — viral: every combinator signature and builder grows a type
   parameter; even defaulted, it ripples through the whole workflow layer and
   breaks "existing implementations compile unchanged." Over-engineered for a
   channel that is read at the leaves, not composed.
2. **Untyped bag — `deps?: Record<string, unknown>` / `deps?: unknown`.**
   *Rejected* — this is exactly the "ADK-style loose shared-dict state" the design
   doc's §5 non-goals forbid. No compile-time safety at the read site.
3. **Branded-key registry mirroring the existing `Slot<T>` / `ScratchpadReader`
   idiom (`slot.ts`).** ✅ **Chosen.** The codebase *already* solves "typed
   ambient value keyed by a handle" for scratchpad: `slot<T>({ key, init })`
   returns a typed handle, and `ScratchpadReader.get<T>(slot): T` reads it
   type-safely with no generic on `Node`. A dependency key is the same move: a
   `DepKey<T>` handle + `ctx.deps.get(key): T`. Type-safe, non-viral, and
   idiomatic — a reader of this codebase already knows the pattern.

**How deps differ from scratchpad (simpler, deliberately):**
- **Read-only.** Deps are injected once at the root and never mutated mid-run —
  so the accessor exposes `get`/`getOptional` only (no `set`/`update`).
- **Run-scoped, never forked.** Deps are a single frozen registry shared *by
  reference* across `FanOut`/`Parallel` branches. The existing `{ ...ctx }`
  spread already aliases the same `deps` object into every branch — exactly the
  desired sharing, with no fork/merge machinery.

## Approach

Introduce a small typed-DI primitive in a new file
`packages/agent-runtime/src/workflows/deps.ts`, add **one optional field** to
`NodeRunContext`, and thread it through the two root builders. Combinators are
untouched.

1. **`DepKey<T>` + `depKey<T>(name)`** — a branded, typed handle (the `Slot<T>`
   analogue). The brand carries `T` phantom-typed so `get(key)` infers the value
   type; `name` is used for identity and error messages. Frozen.

2. **`DepReader` / `DepRegistry`** — the read surface placed on the context:
   - `get<T>(key: DepKey<T>): T` — returns the bound value; **throws
     `MissingDependencyError`** if the key was never provided (fail-loud for a
     required dependency).
   - `getOptional<T>(key: DepKey<T>): T | undefined` — non-throwing lookup for an
     optional dependency.
   - `has(key): boolean`.
   The concrete `DepRegistry` is backed by a `ReadonlyMap<string, unknown>` keyed
   on `DepKey.id`, `Object.freeze()`d per the immutability convention.

3. **`provideDeps(...)` — the root injection helper.** A tiny builder to
   construct a frozen `DepRegistry` at the `run()` root:
   ```ts
   const registry = provideDeps()
     .set(apiClientKey, client)
     .set(loggerKey, logger)
     .build();
   await pipeline.run(input, { runner, deps: registry });
   ```
   (An array form `provideDeps([[apiClientKey, client], ...])` is also accepted
   for a one-shot literal.)

4. **`NodeRunContext.deps?: DepReader`** — the single contract change
   (`node.ts`). Optional, so every existing `{ runner }` / `{ ...ctx }` value
   stays a valid `NodeRunContext` (the same back-compat hinge the `scratchpad`
   field uses). Leaves read it:
   ```ts
   // inside a FunctionStep.fn or AgentStep.prompt-adjacent logic:
   const client = ctx.deps?.get(apiClientKey);   // typed as ApiClient
   ```

5. **Thread `deps` through the two root builders** (they build ctx fresh, so
   spread doesn't help them):
   - `node-tool.ts` — `nodeTool(spec, runner, scratchpad?, deps?)` gains an
     optional `deps` param and sets it on the constructed ctx; `NodeToolbox`
     and `delegateTo` accept and forward an optional `deps`. (Explicit injection
     only — automatic parent→child deps flow across the tool boundary is #102.)
   - `as-agent.ts` — `PromoteOptions` gains `deps?: DepReader`; `NodeBackedRunner`
     sets `deps` on the ctx it builds so a promoted pipeline's nested leaves see
     the injected deps. This is how **`asAgent`/`NodeBackedRunner` exposes the
     channel**: deps are bound at promotion time (`asAgent(node, { role, deps })`)
     and flow into every leaf when the promoted agent is chatted/run.

### `asAgent` / `NodeBackedRunner` exposure (design-doc callout)

The plan asks specifically to *document how `asAgent`/`NodeBackedRunner` exposes
the channel*. Decision: **bind deps at promotion time** via `asAgent(node, {
role, deps })`. `NodeBackedRunner.run()` then injects that registry into the
`NodeRunContext` it constructs, so nested `AgentStep`/`FunctionStep` leaves read
their deps with no closures — even though the promoted pipeline is driven through
the chat/SSE path. **Per-request deps via `RunOptions.deps`** (a different value
per chat turn) is deliberately **deferred**: it would touch `RunOptions`, the
server SSE path, and the CLI attach seam, mirroring #97's decision to leave the
server byte-unchanged. Promotion-time binding satisfies the acceptance; per-turn
deps can layer on later without breaking this surface.

## Interfaces

```typescript
// --- packages/agent-runtime/src/workflows/deps.ts (new) ---

/** A branded, typed dependency handle — the DI analogue of `Slot<T>`. */
export interface DepKey<T> {
  readonly id: string;
  /** phantom — carries T for inference; never read at runtime. */
  readonly __t?: T;
}

/** Mint a typed dependency key. `name` is used for identity + error messages. */
export function depKey<T>(name: string): DepKey<T>;

/** Read-only DI surface placed on `NodeRunContext.deps`. */
export interface DepReader {
  /** Bound value; throws `MissingDependencyError` if the key was never provided. */
  get<T>(key: DepKey<T>): T;
  /** Non-throwing lookup for an optional dependency. */
  getOptional<T>(key: DepKey<T>): T | undefined;
  has(key: DepKey<unknown>): boolean;
}

export class MissingDependencyError extends Error {
  constructor(keyName: string);
}

/** Frozen, ReadonlyMap-backed DepReader. */
export declare class DepRegistry implements DepReader {
  get<T>(key: DepKey<T>): T;
  getOptional<T>(key: DepKey<T>): T | undefined;
  has(key: DepKey<unknown>): boolean;
}

/** Fluent builder for the root injection point. Array form also accepted. */
export function provideDeps(
  entries?: ReadonlyArray<readonly [DepKey<unknown>, unknown]>,
): {
  set<T>(key: DepKey<T>, value: T): /* this */ ReturnType<typeof provideDeps>;
  build(): DepRegistry;
};

// --- added to packages/agent-runtime/src/workflows/node.ts ---
export interface NodeRunContext {
  readonly runner: RunnerProtocol;
  readonly hooks?: PatternHooks;
  readonly toolExecutor?: ToolExecutor;
  readonly traceId?: string;
  readonly scratchpad?: Scratchpad;
  /**
   * User-supplied dependencies (clients, resolvers, loggers), keyed by DepKey<T>.
   * OPTIONAL: injected once at the root and shared by reference across the whole
   * node tree (combinators carry it via `{ ...ctx }`). Existing callers that pass
   * `{ runner }` keep compiling and behave identically (they never read deps).
   */
  readonly deps?: DepReader;
}
```

Usage (the acceptance path, no closures):

```typescript
const apiClientKey = depKey<ApiClient>("apiClient");

const pipeline = Sequential
  .start(fetchStep)                 // FunctionStep: ctx.deps.get(apiClientKey)
  .then(new AgentStep({ /* ... */ }))
  .build();

await pipeline.run(input, {
  runner,
  deps: provideDeps().set(apiClientKey, client).build(),
});
```

## Tests

`workflows/__tests__/deps.test.ts` (vitest; a fake `RunnerProtocol` returning
canned `RunResult`s — no live LLM; mirror `sequential.test.ts` conventions):

1. **Registry semantics.** `provideDeps().set(k, v).build()` → `get(k) === v`;
   `getOptional(missing) === undefined`; `get(missing)` throws
   `MissingDependencyError` naming the key; `has()` correct; two keys with the
   same `T` but different names don't collide; the registry is frozen.
2. **Leaf reads a root-injected dep without closures.** A `FunctionStep` whose
   `fn` calls `ctx.deps!.get(apiClientKey)` returns the injected value; an
   `AgentStep` reads a dep in its `prompt`/logic path.
3. **Propagation through every combinator (the core acceptance).** Inject one dep
   at the root; assert a leaf reads the *same* instance when nested under each of:
   `Sequential`, `Loop`, `Accumulate`, `Parallel` (in a branch), `FanOut` (in a
   branch), and `CoordinatorStep`. Confirms the `{ ...ctx }` spread carries deps
   and that branch forks share deps by reference.
4. **`asAgent` exposure.** `asAgent(pipeline, { role: { name: "P" }, deps })`
   run via `NodeBackedRunner` over a fake inner runner → a nested leaf reads the
   promotion-time dep.
5. **`nodeTool` explicit injection.** `nodeTool(spec, runner, undefined, deps)` →
   the wrapped node's leaf reads the dep when the tool is executed.
6. **Additive / no-regression.** A `node.run(input, { runner })` call with **no**
   `deps` still succeeds; a leaf using `ctx.deps?.getOptional(k)` sees
   `undefined` and does not throw. Existing workflow suites stay green.

## Conventions honored

- **Additive, layer-legal** — new file in runtime layer 9 (workflows); imports
  only within-layer + lower. Core is not touched (deps live in runtime, not the
  core `Node` type — core never learns about DI). One optional field on
  `NodeRunContext`; every existing value stays valid (the `scratchpad` hinge).
- **Immutability** — `DepKey`, `DepRegistry`, and the built registry are
  `Object.freeze()`d, matching `slot()` and the frozen `NodeResult`.
- **Idiomatic** — mirrors the established `Slot<T>` / `ScratchpadReader` typed-key
  pattern; no new mental model for a codebase reader.
- **Barrel exports** — surfaced through `workflows/index.ts` → runtime `index.ts`.
- **§5 non-goal respected** — typed keys, not a loose shared dict; no ADK-style
  string-bag state.

## Decisions (proposed — for Gate 1 review)

1. **Branded-key registry, not a `Node` generic or an `any`-bag.** Mirrors
   `Slot<T>`; non-viral; type-safe. (Rationale above.)
2. **Combinators are verified, not modified.** `{ ...ctx }` spread propagates
   `deps` for free; editing them would be noise. The change surface is `deps.ts`
   + one field on `node.ts` + two root builders.
3. **Deps are read-only + run-scoped** (no `set`/`update`, no fork/merge). Shared
   by reference across branches via the existing spread.
4. **`asAgent` binds deps at promotion time** (`asAgent(node, { deps })`).
   Per-request `RunOptions.deps` is deferred to keep `RunOptions`/server/CLI
   byte-unchanged (mirrors #97).

## Open questions (for Gate 1)

1. **`get` throw-on-missing vs. optional-only.** Proposed: `get` throws
   (fail-loud for required deps), `getOptional` for optional. Alternative: only
   `getOptional` and let callers decide. Recommend the throwing `get` — a missing
   required client should fail at the read site, not surface as a downstream
   `undefined`.
2. **`nodeTool` deps param ordering.** Appending `deps?` as a 4th positional
   arg after `scratchpad?` keeps back-compat but grows a positional list.
   Alternative: fold `runner`/`scratchpad`/`deps` into an options object — larger
   blast radius on existing `nodeTool` callers. Recommend the positional append
   for a tight, additive diff; options-object refactor can be its own cleanup.
3. **Scope confirmation — no automatic tool-boundary propagation.** `nodeTool`
   re-roots the context, so parent deps do **not** auto-flow across the
   agent-as-tool seam here (explicit injection only). Confirm this belongs with
   #99/#102 (tool-execution context) and is correctly out of scope for #98.
