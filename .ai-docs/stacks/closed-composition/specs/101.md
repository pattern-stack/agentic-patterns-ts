# Spec — #101 Loop-with-accumulator (fold state between iterations)

## Goal

Give `Loop` a first-class **accumulator seam**: a typed value seeded once from the
loop input, folded once per iteration from that iteration's body output, visible to
both the continuation predicate and the loop body, and returned on exit. This is to
`Loop` what `Slot.merge` (the `Scratchpad` reducer) already is to `FanOut`/`Parallel`
fan-in — a deterministic, typed way to build up cross-iteration state instead of
hand-rolling it.

The acceptance bar from the issue:

1. Loop supports `initial` + `fold(acc, iterationResult)` and exposes `acc` to the
   condition **and** the body.
2. The consumer's `escalate.ts` merge pattern (navigate → gap-check → merge pool →
   re-check once, bounded at 2) is reproducible with the primitive, and a unit test
   mirrors it.

Scope is **Loop only**. No retry (#100), no Node DI (#98). The accumulator arrives by
the spec, not by a new `NodeRunContext` channel.

## Context / evidence

`escalate.ts` (260 lines) is a hand-rolled Loop-with-merge. Read against it, the seam
is unmistakable:

| escalate.ts concept | primitive seam |
|---|---|
| `pool` (EvidencePool) built up across iterations, returned at the end | **the accumulator** (`TAcc`) |
| `gapCheck(...) → GapCheckDecision` each iteration | **the body output** (`TState`, folded in) |
| `EvidencePool.parse({ items: mergePoolItems(...), coverage: [...] })` | **`fold(acc, output, i)`** — immutable replacement, not mutation |
| `decision.done \|\| supplements.length === 0` → stop | **`until(acc, state, i)`** predicate |
| `MAX_GAP_CHECKS = 2` | **`maxIterations`** |
| `exitReason: 'done' \| 'max_iterations'` | reuse **`LoopExitReason`** |
| gap-check reads the *current pool* to render its input | **body reads `acc`** (the load-bearing requirement) |

The tell that today's `Loop<TState>` cannot express this: its body is `Node<TState, TState>`
— the iteration output **is** the next state, so there is exactly one threaded channel.
`escalate` needs **two**: a decision that drives continuation (`TState`) *and* a pool that
accumulates and is itself the return value (`TAcc`). One channel can't carry both.

## Approach

### Decision: add a sibling combinator, do **not** overload `Loop<TState>`

The mission asks to prefer extending the existing Loop *if additive*. It is **not**
cleanly additive, for three concrete reasons:

1. **The body signature must change.** The issue requires the body to *read* `acc`. Today
   the body is `Node<TState, TState>`; giving it `acc` means its input becomes
   `{ state, acc, iteration }` — a different `TIn`. That is a breaking change to every
   existing `Loop` body, not an addition.
2. **A second type parameter appears.** `Loop<TState>` becomes `Loop<TState, TAcc>`.
   Bolting on `TAcc` with a `= never`/`= TState` default to keep old call sites inferring
   makes `until`/`fold`/result types conditional on whether the accumulator is present —
   the kind of optional-field discriminant the codebase deliberately avoids (see
   `Accumulate` sitting *beside* `Loop` rather than as a flag on it).
3. **The return contract changes.** The point of the primitive is that the **accumulator**
   is the output (`Node<TState, TAcc>`), whereas `Loop` returns `TState`
   (`Node<TState, TState>`). Different output type ⇒ different Node.

So: introduce **`AccumulatingLoop<TState, TAcc> implements Node<TState, TAcc>`**,
co-located in `loop.ts` to reuse the loop family's vocabulary (`LoopExitReason`,
iteration semantics) and keep `Loop<TState>` byte-for-byte unchanged (zero risk to the
"replaces the four deleted loop classes" consolidation). This mirrors how `Accumulate`
(static-list fold) already lives as its own primitive next to `Loop` (predicate-driven).

`Accumulate` is explicitly **not** the answer: it folds over a *statically-known list*
with no continuation predicate and no safety cap. `escalate` iterates an *unknown* number
of times gated by an LLM decision, bounded by `maxIterations` — that is `Loop`, plus a
fold. Hence: `Loop` + accumulator, not `Accumulate`.

### Seam shape

```
acc₀ = initial(input)                       // seed once
loop i = 0 … maxIterations-1:
  res = body.run({ state, acc, iteration: i })   // body sees BOTH channels
  if !res.succeeded: exitReason = "error"; break // acc/state stay LAST-GOOD (Loop parity)
  state = res.output
  acc   = freeze(fold(acc, state, i))            // fold AFTER body; frozen between iters
  if until(acc, state, i): exitReason = "predicate_met"; break
exit: exitReason = "max_iterations" (default)
output = acc                                       // the accumulator is the result
```

Design points, each justified against evidence:

- **`acc` visible to body via `{ state, acc, iteration }` input** — the load-bearing
  requirement; `escalate`'s gap-check renders the *current pool* to decide supplements.
- **`fold` runs after a successful body, folding this iteration's `state` output** —
  matches `escalate` merging `supPool` into `pool` only after a successful navigate.
- **`until` sees the folded `acc`** (not just `state`) — `escalate` exits on
  `decision.done`, a property of the merged pool view, not of the raw decision.
- **`acc` is `Object.freeze`-d between iterations** — project immutability discipline;
  `fold` must return a *new* value (immutable replacement), exactly as `escalate` does
  `pool = EvidencePool.parse({...})` rather than mutating the pool. Freeze is **shallow**
  (parity with how `NodeResult` is shallow-frozen); deep immutability of `TAcc`'s interior
  is the caller's contract — documented, not enforced.
- **`error` exit keeps last-good `acc` and `state`** — direct parity with `Loop`'s
  documented "do NOT thread the failed output forward" behavior (`loop.ts:82-95`).
- **Cap-hit stays `succeeded: true`** — parity with `Loop`; the caller branches on
  `exitReason`. `escalate` treats `max_iterations` as a normal, usable exit.
- **`maxIterations` REQUIRED positive integer** — reuse `Loop`'s constructor guard verbatim.
- **Token + hook accounting** — sum `totalInputTokens`/`totalOutputTokens` across
  iterations and fire `onPatternStart` / `onIterationStart` / `onIterationComplete` /
  `onPatternComplete`, identical cadence to `Loop`.

## Interfaces

```typescript
export interface AccumulatingLoopStepInput<TState, TAcc> {
  readonly state: TState;
  readonly acc: TAcc;
  readonly iteration: number;
}

export interface AccumulatingLoopSpec<TState, TAcc> {
  readonly name?: string;
  /** Body reads BOTH the threaded state and the current accumulator. */
  readonly body: Node<AccumulatingLoopStepInput<TState, TAcc>, TState>;
  /** Seed the accumulator once from the loop input. */
  readonly initial: (input: TState) => TAcc;
  /** Fold this iteration's body output into the accumulator. MUST return a new value. */
  readonly fold: (acc: TAcc, output: TState, iteration: number) => TAcc;
  /** Continue-predicate — sees the folded accumulator, latest state, and iteration index. */
  readonly until: (acc: TAcc, state: TState, iteration: number) => boolean;
  /** REQUIRED safety cap (positive integer). */
  readonly maxIterations: number;
}

export interface AccumulatingLoopResult<TState, TAcc> extends NodeResult<TAcc> {
  /** `output` is the accumulator; `state` is the last body output, for callers who want it. */
  readonly state: TState;
  readonly iterations: number;
  readonly exitReason: LoopExitReason; // reused from Loop
}

export class AccumulatingLoop<TState, TAcc> implements Node<TState, TAcc> {
  constructor(spec: AccumulatingLoopSpec<TState, TAcc>);
  run(input: TState, ctx: NodeRunContext): Promise<AccumulatingLoopResult<TState, TAcc>>;
}
```

## Test plan

Harness mirrors `loop.test.ts` exactly (`MockRunner`, `FunctionStep`, `ctx = { runner }`).

**Core semantics (parity with `Loop`):**
1. **predicate_met** — `until` on the folded acc first holds → `exitReason: "predicate_met"`,
   `output` = final acc, `succeeded: true`.
2. **max_iterations** — `until` never holds → `exitReason: "max_iterations"`, `iterations === maxIterations`,
   `output` = acc after the last fold, `succeeded: true`.
3. **error** — body throws / returns `succeeded:false` on iteration N → `exitReason: "error"`,
   `succeeded:false`, `error` propagated, `acc` + `state` are **last-good** (the failing
   iteration is NOT folded), `iterations === N`.
4. **acc visible to body** — body reads `acc` from its input and branches on it (e.g. stops
   emitting once `acc.items.length >= k`); assert the body actually saw the growing acc.
5. **fold cadence** — `fold` called once per successful iteration, receiving the correct
   `(acc, output, iteration)`; assert the iteration indices and acc progression.
6. **immutability** — attempting to mutate `acc` inside `fold`/`body` does not leak across
   iterations; assert each iteration receives the frozen result of the previous `fold`
   (mutation attempt throws in strict mode / is not observed next iteration).
7. **maxIterations guard** — `new AccumulatingLoop({ maxIterations: 0 })` throws (reused guard).
8. **token/hook accounting** — totals summed across iterations; pattern + iteration hooks
   fire in the same cadence as `Loop` (spy on `ctx.hooks`).

**escalate.ts mirror (the acceptance test):**
9. Model `acc` as a pool-like `{ items: readonly number[] }`, body as a decision emitter
   `{ done: boolean; supplements: number[] }`, `fold` = concat/merge `supplements` into
   `items`, `until = (acc, dec) => dec.done`, `maxIterations: 2`. Assert three arms that
   reproduce `escalate`'s exact behavior:
   - **done on iteration 1** → `predicate_met`, one body run, acc = first merge.
   - **not-done → escalate → re-check → cap at 2** → `max_iterations`; acc reflects the
     iteration-1 merge; assert the capped iteration's supplements are handled the way
     `escalate` handles the bound (folded-then-capped vs. not — pin the exact contract in
     the test so the primitive's cap semantics are locked).
   - **body failure mid-loop** → `error`, acc = last-good pool.

Run: `bun run --filter=@agentic-patterns/runtime test` (vitest) + `typecheck` + `lint` (biome) green.

## Open questions (for Gate 1 review)

1. **Co-locate in `loop.ts` vs. new `accumulating-loop.ts`?** Spec co-locates (reuses
   `LoopExitReason`, keeps the loop family cohesive, least churn). A separate file matches
   one-file-per-combinator (`accumulate.ts`, `fan-out.ts`). Reviewer's call — trivial to flip.
2. **Ergonomic factory?** Optionally add `Loop.accumulating(spec)` / `accumulatingLoop(spec)`
   so the primitive is discoverable under the `Loop` name without overloading its type.
   Nice-to-have; omitted from the core plan to keep surface minimal. Want it in scope?
3. **Cap-hit fold semantics** (open-Q surfaced by escalate arm 2): when the loop hits
   `maxIterations`, is the final iteration's output folded before exit (my default: yes —
   fold runs on every successful body, the cap is checked at loop top) or withheld
   (escalate's "supplements NOT executed" at the bound)? These differ because escalate's
   bound short-circuits *before* executing supplements, whereas the primitive folds *body
   output*, not supplement execution. My reading: the primitive folds every successful
   iteration; escalate's "not executed" is a *body-internal* concern (its body would simply
   not run supplements on the final pass). Please confirm this is the intended contract.
4. **`fold` purity enforcement** — spec shallow-freezes `acc`; deep immutability of `TAcc`'s
   interior is a documented caller contract, not enforced (parity with `NodeResult`). OK?

## Out of scope

- Node DI / `NodeRunContext` user-dep channel (#98) — the accumulator arrives via the spec.
- Node-native retry (#100) — a failed body exits with `error`, it does not retry.
- Concurrency over the accumulator — folds are strictly sequential by construction (as with
  `Accumulate`); no `maxConcurrency` knob, so nobody can corrupt the fold.
- Rewriting `escalate.ts` itself — the consumer refactor lands downstream; this issue only
  proves the merge pattern is reproducible (test #9).
