# Spec — core: optional `ToolExecutionContext` on `ToolDefinition.execute`

## Goal

Give a tool's `execute` an **optional** second parameter — a
`ToolExecutionContext` `{ emit, runId, traceId, parentToolCallId }` — and thread
it through `Toolbox.execute(name, args, ctx?)`. This is the **core, vendor-neutral
half** of the "agent-as-tool + shared bus" unlock (design doc §4 item 3): once a
tool can `emit`, a nested sub-agent invoked *as a tool* (pipeline, CoordinatorStep,
agent-as-tool) can publish its own tool calls onto the parent run's event bus, so
they surface in chat / Live / Tools / Graph instead of vanishing.

**This issue is core only.** It defines the *type* and *forwards* the context; it
emits nothing itself. The runtime wiring — building the context from the run's
`AgentEventBus` in `agent-runner.ts` and passing it down through
`toolbox-executor.ts` — is **#102**, which depends on this. The seam designed here
**is** #102's contract; §"Designed-for consumer" makes that binding explicit
without implementing it.

Hard constraints (from the plan's acceptance + the design doc):
- **Strictly backward compatible.** Every existing `execute(args)` implementation
  and every existing 2-arg `toolbox.execute(name, args)` call compiles and passes
  **untouched**. No existing test changes.
- **Zero runtime import.** The sink type lives in `@agentic-patterns/core`. `emit`
  is a **minimal event sink**, *not* runtime's `AgentEventBus`. Core layer 2
  (molecules) must not reach up into runtime — ever (CLAUDE.md import rules).

## Key finding — the sink must be minimal, so the trace fields ride on the *context*, not the *event* (read before coding)

The design doc says `emit` is "a minimal event-sink interface, not runtime's
`AgentEventBus`." The tension to resolve: runtime's bus consumes a **`BaseEvent`**
(`events/types.ts:30`) that *requires* `type`, `traceId`, `runId`, `spanId`,
`timestamp`. If core's `emit` demanded that shape, core would either duplicate
runtime's event schema (coupling by copy) or force every tool author to hand-stamp
`spanId`/`timestamp` — neither is "minimal."

**Resolution:** core's `ToolEvent` carries only `{ type, data? }`. The correlation
fields (`runId`, `traceId`, `parentToolCallId`) live on the **`ToolExecutionContext`
alongside `emit`, not inside each event.** The tool author emits a bare
`{ type: "progress", data: { statusText } }`; the **runtime adapter in #102** owns
stamping `traceId`/`runId`/`spanId`/`timestamp` (all of which it already holds at
the dispatch site) before `publish()`-ing to the real bus. This keeps core
genuinely decoupled — core never names an `AgentEventBus`, a `BaseEvent`, or a
`spanId` — while making #102 a mechanical bridge, not a translation layer with
guesswork.

Second finding — **`emit` is fire-and-forget `void`, not `Promise`.** Runtime's
`AgentEventBus.publish` is `async` (returns `Promise<unknown[]>`, runs the gate
chain). A minimal *sink* should not drag tool authors into awaiting bus/gate
plumbing on a progress ping. So core types `emit(event): void`; #102's adapter
wraps the async publish fire-and-forget (`void bus.publish(stamp(event))`). See
Decisions for the (rejected) `Promise`-returning alternative.

## Approach

One file changes in earnest — `packages/agent-core/src/molecules/toolbox.ts` — plus
a barrel re-export. Three additive edits, all backward compatible:

1. **Define the context types in `toolbox.ts`** (co-located with `ToolDefinition`,
   the only consumer of them), as **plain `interface`s — no zod** (see Decisions §1
   for the rationale):

   - `ToolEvent` — the minimal event a tool may emit: `{ type: string; data?:
     Record<string, unknown> }`. No trace fields; those are on the context.
   - `ToolExecutionContext` — `{ emit?, runId?, traceId?, parentToolCallId? }`,
     **every field optional** so that omitting the context entirely, or passing
     `{}`, is valid. `emit?: (event: ToolEvent) => void`.

2. **Widen `ToolDefinition.execute`** to accept the optional context as a second
   parameter:
   ```ts
   execute: (args: Record<string, unknown>, ctx?: ToolExecutionContext) => Promise<unknown>;
   ```
   Adding a trailing optional parameter is **assignment-compatible** with every
   existing `(args) => Promise<unknown>` implementation: in TypeScript a function
   that ignores parameters is assignable to a type that declares more. So all
   current tool definitions (`ManualToolbox`, test toolboxes, userland tools)
   compile with **no edit**.

3. **Forward the context in `Toolbox.execute`**:
   ```ts
   async execute(name: string, args: unknown, ctx?: ToolExecutionContext): Promise<unknown> {
     const tool = this.tools[name];
     if (!tool) throw new Error(`Unknown tool: ${name}`);
     const parsed = tool.parameters.parse(args) as Record<string, unknown>;
     return tool.execute(parsed, ctx);   // was: tool.execute(parsed)
   }
   ```
   Zod validation of `args` is unchanged and still runs before `execute`. `ctx` is
   pass-through only — never validated, never inspected by core. When a 2-arg caller
   omits `ctx`, `tool.execute(parsed, undefined)` is passed, which every existing
   implementation ignores.

That is the whole core change. No behavior executes differently until #102 supplies
a context; this issue only *opens the channel*.

### Playbook symmetry — explicitly scoped OUT (recommended)

`Playbook.execute` (`molecules/playbook.ts:70`) has the same 2-arg shape and the
runtime `toolbox-executor.ts` routes plays through it. Threading `ctx` through
`Playbook` too would be trivially symmetric — but #102's consumer is the
**agent-as-tool / `node-tool.ts`** path, which is a *toolbox tool*, not a play. Per
the issue title ("on `ToolDefinition.execute`") and YAGNI, **do not touch
`Playbook` in this issue.** It is a clean, additive follow-on if a play ever needs
to emit. Tracked as an open decision, not silently dropped.

## Designed-for consumer — #102 (do NOT implement here; this is the contract)

The seam is designed so #102 is mechanical. At each dispatch site in
`agent-runner.ts` (`:468`, `:614`, `:1209`) the runner already holds everything the
context needs — verified this session:
- `runId` and `effectiveTraceId` (`agent-runner.ts:222–223`),
- the per-call `tc.toolCallId` and `tcSpanId` (`:460,:464`),
- `this.eventBus` (an `AgentEventBus`).

So #102 will:
1. Widen the runtime `ToolExecutor` interface (`runner/types.ts:74`) from
   `execute(name, args)` → `execute(name, args, ctx?: ToolExecutionContext)`, and
   have `createToolboxExecutor` forward `ctx` into `toolbox.execute(name, args, ctx)`
   (`toolbox-executor.ts`). The runtime `ToolboxLike` structural type there gains
   the optional 3rd param — compatible with core's widened class.
2. Build the context at the dispatch site:
   ```ts
   const ctx: ToolExecutionContext = {
     runId, traceId: effectiveTraceId, parentToolCallId: tc.toolCallId,
     emit: (e) => void this.eventBus.publish({           // adapter lives in runtime
       type: e.type, data: e.data,
       traceId: effectiveTraceId, runId, spanId: `${tcSpanId}-child`,
       timestamp: new Date(),
     }),
   };
   ```
3. Fix child→parent propagation in `node-tool.ts` / `coordinator-step.ts` using that
   `emit` (the general-case fix the design doc §4.3 calls for).

**Nothing above is in scope for #99** — it is reproduced only to prove the core type
is sufficient and correctly shaped for its sole consumer. Core imports `type
ToolExecutionContext` is what runtime references; the mapping to `BaseEvent` stays
entirely in runtime.

## Interfaces

```typescript
// packages/agent-core/src/molecules/toolbox.ts

/**
 * A minimal, vendor-neutral event a tool may emit during execution.
 * Deliberately NOT runtime's BaseEvent: no traceId/runId/spanId/timestamp —
 * those correlation fields live on ToolExecutionContext and are stamped by the
 * host (runtime) when it bridges to a real event bus. Keeps core decoupled.
 */
export interface ToolEvent {
  readonly type: string;
  readonly data?: Record<string, unknown>;
}

/**
 * Optional execution context handed to a tool's `execute`. Every field is
 * optional: a tool that ignores it, or a caller that omits it, is fully valid
 * (backward compatible). `emit` is a minimal fire-and-forget sink — NOT an
 * AgentEventBus. The host wires it to whatever bus/exporter it runs.
 */
export interface ToolExecutionContext {
  /** Fire-and-forget event sink. Host bridges to its bus; core never awaits it. */
  readonly emit?: (event: ToolEvent) => void;
  /** Correlates emitted events to the enclosing run. */
  readonly runId?: string;
  readonly traceId?: string;
  /** The tool-call id of the invoking tool, so children nest under their parent. */
  readonly parentToolCallId?: string;
}

export interface ToolDefinition {
  description: string;
  parameters: ZodTypeAny;
  returns?: ZodTypeAny;
  // CHANGED — trailing optional param; assignable from every existing (args)=>… impl.
  execute: (args: Record<string, unknown>, ctx?: ToolExecutionContext) => Promise<unknown>;
}

export abstract class Toolbox {
  // ...unchanged members...
  // CHANGED — optional trailing ctx, forwarded to tool.execute.
  execute(name: string, args: unknown, ctx?: ToolExecutionContext): Promise<unknown>;
}
```

## Tests

`Toolbox` subclass + zod params):

1. **Backward compat — no context.** Existing `toolbox.execute("add", {a,b})` (no
   3rd arg) still returns the result. (Already covered; assert it stays green as the
   regression guard.)
2. **Context is forwarded verbatim.** A tool whose `execute(args, ctx)` records the
   received `ctx`; call `toolbox.execute("probe", args, ctx)` with a context whose
   `emit` pushes to a local array; assert the tool saw the **same** `runId`,
   `traceId`, `parentToolCallId`, and that calling `ctx.emit({type:"progress"})`

3. **Omitted context → `undefined`.** A tool asserting its 2nd param is `undefined`
   when `toolbox.execute("probe", args)` is called with no ctx.
4. **Legacy 1-arg tool + context supplied.** A tool defined as `execute: (args) =>

   context.

   empty) — context does not bypass validation.
6. **Type-level (compile-time) guard.** A `ToolDefinition` literal using the legacy
   `execute: async (args) => …` assigns without error, and one using `(args, ctx) =>
   …` also assigns — a `// @ts-expect-error`-free block in the test file doubles as

## Conventions honored

- **Layer-legal, additive** — change confined to core layer 2 (molecules). Core
  imports **nothing** from runtime; the context type is defined in core and consumed
  *upward* by runtime (#102), never the reverse (CLAUDE.md import rules).
- **Plain interface, not zod** — matches `ToolDefinition` itself (a plain interface)
  and runtime's `NodeRunContext`; zod is reserved for model-produced *data* boundaries
  (`parameters`/`returns`), not framework plumbing (see Decisions §1).
- **Immutability** — context/event fields are `readonly`; no `Object.freeze` needed
  (they are transient per-call values, not frozen atom data).
- **Barrel exports** — new types surfaced through `molecules/index.ts` → core
  `index.ts`, per the public-API convention.
- **Backward compatibility as the primary acceptance** — trailing-optional-param
  widening is the least-invasive shape that satisfies the design doc's field set.

## Decisions (resolved at authoring; open items flagged for Gate 1)

1. **Plain `interface`, no zod — recommended.** CLAUDE.md says "zod for all data
   models," but `ToolExecutionContext` is **framework plumbing**, not a
   model/trust-boundary payload: it is built by the runtime, not the LLM, and its
   `emit` is a live **function** that `z.function()` cannot meaningfully validate
   (and would add cost for zero safety). Precedent: `ToolDefinition` and
   `NodeRunContext` are both plain interfaces. If event validation is ever needed at
   a boundary, a `ToolEventSchema` can be added additively — not now.
2. **Trace fields on the context, event stays minimal — recommended.** Keeps core
   free of runtime's `BaseEvent` schema; the host stamps `spanId`/`timestamp` (which
   only it holds). Alternative (put full event shape in core) rejected as coupling.
3. **`emit` is `void`, fire-and-forget — recommended.** A minimal sink should not
   force tool authors to await bus/gate plumbing. #102's adapter wraps the async
   `publish` (`void bus.publish(...)`). Alternative — `emit(e): void | Promise<void>`
   — is deferred; add it only if a consumer needs backpressure on emitted events.
4. **All context fields optional — recommended.** Makes both "no context" and
   "partial context" valid, which is what backward compat + a gradually-wired host
   require. `emit?` being optional means a tool must guard `ctx?.emit?.(…)`.

**Open questions for the human (Gate 1):**
- **Playbook symmetry.** Confirm scoping `Playbook.execute`'s context threading OUT
  of #99 (recommend: yes — defer to a follow-on if/when a *play* must emit; #102
  targets the toolbox/agent-as-tool path).
- **`AbortSignal` on the context.** The design doc names exactly four fields; a
  `signal?: AbortSignal` for cancellable long-running tools is a plausible future
  addition but is **out of scope** here. Confirm we hold to the four-field set for
  now (recommend: yes).
- **`ToolEvent` payload shape.** `{ type, data? }` vs an open index signature
  (`{ type; [k: string]: unknown }`). Recommend the explicit `data?` bag — it keeps
  `type` unambiguous and maps cleanly onto runtime's `ToolProgressEvent`
  (`toolCallId`/`progress`/`statusText`) in #102.
