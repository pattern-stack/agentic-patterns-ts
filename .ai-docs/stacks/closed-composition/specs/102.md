# Spec — runtime: thread `eventBus` into tool execution; child→parent bus propagation

> **BLOCKED ON #99.** This is the runtime half of the "agent-as-tool + shared
> bus" unlock. It consumes the `ToolExecutionContext` type that #99 adds to
> `@agentic-patterns/core`. #99 is **approved but not yet merged** (branch
> `dug/99-tool-exec-context`). Implementation of #102 **must not start until #99
> lands on `main`** — the core import (`ToolExecutionContext`, `ToolEvent`) does
> not exist on `origin/main` yet. The strategy below is written against #99's
> approved contract (its § "Designed-for consumer — #102"), which is binding: do
> **not** redesign the core seam here.

## Goal

Make nested sub-agents' tool activity **visible on the parent run's event bus**.
Two coupled pieces:

1. **The mechanical bridge (m.a).** Thread a `ToolExecutionContext` from the
   runner's dispatch sites in `agent-runner.ts` → the runtime `ToolExecutor`
   interface → `toolbox-executor.ts` → core's `toolbox.execute(name, args, ctx)`.
   The context's `emit` is bound to the parent run's `AgentEventBus`; its
   `runId`/`traceId`/`parentToolCallId` correlate anything a tool emits to the
   enclosing call. This is a pass-through widening — no behavior changes for
   tools that ignore `ctx`.

2. **The general-case propagation fix (m.b).** `node-tool.ts` and
   `coordinator-step.ts` (and `as-agent.ts`'s `NodeBackedRunner`) currently run a
   **whole sub-agent** whose events form an **orphan trace** — they land on the
   bus (the sub-run shares the coordinator's runner, whose `_eventBus` is sticky
   from the parent run) but under a **freshly-minted `traceId` and no
   `parentSpanId`**, so the playground's Live/Tools/Graph views — which group by
   `traceId` and nest by `parentSpanId` — can't attach them to the invoking tool
   call. They vanish from the nested view. The fix threads the parent's
   `traceId` + `parentToolCallId` (as `parentSpanId`) into the sub-run so its
   real, structured `agent.tool.*` events **nest under the call that spawned
   them**.

Acceptance (from the issue):
- A sub-agent invoked via agent-as-tool or `CoordinatorStep` emits events visible
  on the **parent run's** bus.
- Playground shows nested tool calls for a promoted pipeline (manual verify +
  event-level unit test).

## Key finding — full-fidelity nesting comes from *trace/span correlation*, not from `emit` (read before coding)

It is tempting to read "nested sub-agents emit onto the parent bus" as "make the
sub-agent call `ctx.emit`." That is **wrong for the acceptance criterion.**
`ctx.emit` (from #99) carries only a minimal `ToolEvent { type, data? }` — a
coarse progress ping. If child tool calls were forwarded through `emit`, they'd be
flattened into generic `agent.tool.progress` events and **lose** the structured
`agent.tool.start`/`agent.tool.end` shape the Tools/Graph views render. The
playground would show "something happened," not the actual nested call tree.

**Resolution — two distinct channels, by design:**

- **Channel A — correlation (the load-bearing fix for m.b).** A sub-agent run via
  `AgentStep`/`CoordinatorStep` already emits real, typed `agent.tool.*` events
  through its runner's bus. Because `NodeToolbox` is constructed with the **same
  runner** as the coordinator (the documented norm — see `node-tool.ts` class
  docstring: *"Typically constructed with the SAME runner that runs the
  coordinator, so the sub-workflows execute on the same model/gate/event
  plumbing"*), those events are already on the parent bus. The **only** missing
  wire is correlation: pass the parent `traceId` + `parentToolCallId` down so they
  carry the parent trace and nest under the invoking call's span. Full fidelity,
  zero flattening. This is exactly why #99 put `traceId` and `parentToolCallId` on
  the context.

- **Channel B — `emit` (secondary, for plain tools).** A **non-agent** tool (a
  leaf that does I/O, not a sub-agent) has no runner and no events of its own; its
  only way to report progress is `ctx.emit({ type: "progress", data: {...} })`.
  The runtime bridge maps that to a real `agent.tool.progress` event correlated to
  the invoking `toolCallId`. This is the mechanical part (m.a) and is what makes
  the channel *exist*, but it is **not** how nested sub-agent calls surface.

The distinction matters because it scopes the work: m.a is a mechanical widening;
m.b is a small correlation-threading change in three workflow files. Neither
requires re-plumbing the event system.

### Second finding — the sticky-bus assumption is real, and it is the one fragility

Channel A works **only** if the sub-run publishes to the *parent's* bus. It does
so today because the coordinator's runner instance holds `_eventBus` from the
parent `run()` call and the sub-run reuses that same instance. If a `NodeToolbox`
is ever constructed with a *different* runner than the one executing the
coordinator, the child events go to that other runner's bus and never reach the
parent — correlation ids alone won't save them. #99's context deliberately does
**not** carry an `AgentEventBus` (core stays vendor-neutral), so #102 cannot
thread the bus through the core seam to fix the cross-runner case. **We accept the
shared-runner invariant** (document it, assert it in the manual-verify path) and
flag cross-runner full-fidelity propagation as an explicit follow-on / open
question — not a silent gap. See Decisions §4.

## Approach

Five files change; all edits are additive/pass-through. Ordered from the core
boundary outward.

### m.a — the mechanical bridge

1. **Widen the runtime `ToolExecutor` interface** (`runner/types.ts:74`):
   ```ts
   import type { ToolExecutionContext } from "@agentic-patterns/core";
   export interface ToolExecutor {
     execute(name: string, args: Record<string, unknown>, ctx?: ToolExecutionContext): Promise<unknown>;
   }
   ```
   Trailing optional param — every existing `execute(name, args)` impl and caller
   stays assignment-compatible.

2. **Forward `ctx` in `toolbox-executor.ts`.** Widen the local `ToolboxLike`
   structural type's `execute` to the 3-arg shape (matches core's widened
   `Toolbox.execute`), and pass `ctx` through in the returned executor:
   ```ts
   interface ToolboxLike {
     readonly name: string;
     execute(name: string, args: unknown, ctx?: ToolExecutionContext): Promise<unknown>;
     readonly tools: Record<string, { execute: (args: Record<string, unknown>, ctx?: ToolExecutionContext) => Promise<unknown> }>;
   }
   // ...
   async execute(name, args, ctx?) {
     const tb = toolLookup.get(name);
     if (tb) return tb.execute(stripPrefix(name), args, ctx);   // was: (…, args)
     const pb = playLookup.get(name);
     if (pb) return pb.execute(stripPrefix(name), args);        // plays unchanged — see Decisions §2
     // …unchanged not-found path…
   }
   ```
   Plays are **not** threaded (they route through `Playbook.execute`, which #99
   explicitly scoped OUT). Tool path only.

3. **Build the context at the three dispatch sites in `agent-runner.ts`** and pass
   it as the 3rd arg to `toolExecutor.execute(...)`. Factor a private helper to
   avoid triplicating the adapter:
   ```ts
   private buildToolCtx(a: {
     traceId: string; runId: string; parentToolCallId: string; parentSpanId: string;
   }): ToolExecutionContext {
     return {
       runId: a.runId,
       traceId: a.traceId,
       parentToolCallId: a.parentToolCallId,
       // Channel B: fire-and-forget sink → a real, correlated progress event.
       emit: (e) =>
         void this.eventBus.publish(
           createEvent("agent.tool.progress", {
             traceId: a.traceId,
             runId: a.runId,
             parentSpanId: a.parentSpanId,
             toolCallId: a.parentToolCallId,
             statusText: typeof e.data?.statusText === "string" ? e.data.statusText : e.type,
             progress: typeof e.data?.progress === "number" ? e.data.progress : undefined,
           }),
         ),
     };
   }
   ```
   Then at each site:
   - **`:468`** (streaming `run()` loop): `traceId: effectiveTraceId, runId,
     parentToolCallId: tc.toolCallId, parentSpanId: tcSpanId`.
   - **`:614`** (`convertExecutableTools`, SDK-driven loop): `traceId:
     ctx.traceId, runId: ctx.runId, parentToolCallId: intent.toolCallId,
     parentSpanId: tcSpanId`. (Uses the local `ctx: { traceId, runId,
     parentSpanId }` already in scope — rename the new var to avoid shadowing,
     e.g. `toolCtx`.)
   - **`:1209`** (generator loop): `traceId: effectiveTraceId, runId,
     parentToolCallId: tc.toolCallId, parentSpanId: tcSpanId`.

   All four inputs are already in scope at each site (verified against
   `agent-runner.ts` this session). The map to `agent.tool.progress` is the safe
   choice over passing `e.type` through verbatim — see Decisions §3.

### m.b — child→parent correlation

4. **`node.ts` — add `parentSpanId?` to `NodeRunContext`.** One optional field,
   engine-defaulted (absent → today's behavior), preserving the back-compat hinge:
   ```ts
   export interface NodeRunContext {
     readonly runner: RunnerProtocol;
     readonly hooks?: PatternHooks;
     readonly toolExecutor?: ToolExecutor;
     readonly traceId?: string;
     readonly parentSpanId?: string;   // NEW — nests this node's events under the invoking span
     readonly scratchpad?: Scratchpad;
   }
   ```

5. **`agent-step.ts` — forward `parentSpanId` into `RunOptions`.** `RunOptions`
   already has `parentSpanId?` (`runner/types.ts:116`) and `traceId?` is already
   forwarded; add the one line:
   ```ts
   const opts: RunOptions = {
     toolExecutor: ctx.toolExecutor,
     maxIterations: this.spec.maxIterations,
     traceId: ctx.traceId,
     parentSpanId: ctx.parentSpanId,   // NEW
   };
   ```
   Now a sub-agent's `agent.tool.*` events carry the parent trace **and** nest
   under the parent tool-call span.

6. **`node-tool.ts` — widen `nodeTool`'s `execute` and thread correlation down.**
   The `ToolDefinition.execute` type is already widened by #99; realize the second
   param and forward it into the sub-node run:
   ```ts
   execute: async (args: Record<string, unknown>, ctx?: ToolExecutionContext) => {
     const input = spec.parameters.parse(args);
     const result = await spec.node.run(input, {
       runner,
       scratchpad: scratchpad ?? createScratchpad(),
       traceId: ctx?.traceId,                 // NEW — join the parent trace
       parentSpanId: ctx?.parentToolCallId,   // NEW — nest under the invoking call
     });
     if (!result.succeeded) return { error: result.error?.message ?? "sub-workflow failed" };
     return result.output;
   },
   ```
   `CoordinatorStep` needs **no change**: it already delegates via `leaf.run(input,
   { ...ctx, toolExecutor })`, which spreads the (now-correlated) `traceId` +
   `parentSpanId` into `AgentStep`. So when a coordinator is invoked as a
   node-tool, correlation flows through transitively. (Confirm with a test; do not
   edit the file unless the test proves a gap.)

7. **`as-agent.ts` — `NodeBackedRunner.run` forwards `parentSpanId`.** It builds a
   `NodeRunContext` from `options` and already forwards `traceId`/`toolExecutor`;
   add the symmetric line so a promoted pipeline run (the playground path for the
   acceptance criterion) roots its nested spans correctly:
   ```ts
   const ctx: NodeRunContext = {
     runner: this.inner,
     toolExecutor: options?.toolExecutor,
     traceId: options?.traceId,
     parentSpanId: options?.parentSpanId,   // NEW
     scratchpad: createScratchpad(),
   };
   ```

## Tests

Event-level unit tests (vitest), using an in-memory `AgentEventBus` and a
`MockRunner`/recording subscriber — mirroring `events/__tests__/agent-event-bus.test.ts`
and `runner/__tests__/toolbox-executor.test.ts`.

1. **Executor forwards `ctx` (m.a).** `createToolboxExecutor` over a toolbox whose
   tool records its received `ctx`; call `executor.execute(name, args, ctx)` and
   assert the tool saw the same `runId`/`traceId`/`parentToolCallId`, and that
   `ctx.emit({type:"progress", data:{statusText:"x"}})` publishes exactly one
   `agent.tool.progress` on the bus with `toolCallId === parentToolCallId` and
   `statusText === "x"`. Extend `toolbox-executor.test.ts`.
2. **Backward compat (m.a).** `executor.execute(name, args)` (no 3rd arg) still
   dispatches and returns the tool's result — a legacy 2-arg tool ignores the
   absent context. Regression guard.
3. **`agent-runner` builds a correlated ctx (m.a).** Drive `AgentRunner.run` with
   a bus subscriber and a `toolExecutor` that captures its `ctx`; assert the
   captured `traceId`/`runId` equal the run's, and `parentToolCallId` equals the
   dispatched `tc.toolCallId`. Extend `agent-runner.test.ts`.
4. **Child tool calls nest under the parent (m.b) — the headline test.** Build a
   `CoordinatorStep` (or `delegateTo`) whose sub-agent makes a tool call, run it on
   a shared bus, and assert the child's `agent.tool.start`/`agent.tool.end` events
   carry the **parent run's `traceId`** and a `parentSpanId` equal to the invoking
   call's span — i.e. they are attributable to the parent tool call, not an orphan
   trace. This is the event-level proof of the acceptance criterion.
5. **Promoted-pipeline nesting (m.b, as-agent).** Run a `asAgent(Sequential(...))`

## Conventions honored

- **Layer-legal** — runtime imports a *type* from core (`ToolExecutionContext`);
  core imports nothing from runtime. The `emit` → `agent.tool.progress` mapping
  (the `BaseEvent` stamping) lives entirely in runtime, per #99's split.
- **Backward-compatible widening** — trailing-optional params on `ToolExecutor`,
  `ToolboxLike`, and one new optional `NodeRunContext` field; no existing caller,
  test, or tool changes.
- **Single adapter** — `buildToolCtx` centralizes the core→bus mapping so the
  three dispatch sites don't drift.
- **Fire-and-forget `emit`** — `void this.eventBus.publish(...)`, honoring #99's
  contract that the sink never makes a tool author await bus/gate plumbing.
- **Additive `NodeRunContext`** — preserves the `PatternRunOptions` back-compat
  hinge (`node.ts` §9); `{ runner }`-only callers behave identically.

## Decisions (resolved at authoring; open items flagged for Gate 1)

1. **Correlation, not `emit`, is the mechanism for nested sub-agent calls —
   recommended.** Forwarding structured child `agent.tool.*` events onto the shared
   bus with parent `traceId`/`parentSpanId` preserves full Tools/Graph fidelity;
   routing them through `emit` would flatten them to progress pings. See Key
   finding. Rejected: an `emit`-only bridge.
2. **Plays are not threaded — recommended.** #99 scoped `Playbook.execute` OUT;
   `toolbox-executor.ts` keeps the play path 2-arg. Symmetric follow-on if a *play*
   ever needs to emit. Matches the issue title ("tool execution").
3. **`emit` maps to `agent.tool.progress`, not a verbatim `e.type` — recommended.**
   The bus's `publish` consumes a typed `BaseEvent` union; a freeform `e.type`
   string wouldn't be a known `AgentEventType` and would be dropped/ignored by
   view consumers keyed on the union. Mapping to the real `ToolProgressEvent`
   (`toolCallId`/`statusText`/`progress`) is the safe, useful shape. Rejected:
   `publish({ type: e.type, ... })` passthrough.
4. **Accept the shared-runner invariant for Channel A — recommended, with a flagged
   follow-on.** Full-fidelity nesting relies on the sub-run using the coordinator's
   runner (whose bus is the parent bus). This is the documented `NodeToolbox`
   norm. #99's context intentionally omits the `AgentEventBus` (core
   vendor-neutrality), so #102 cannot fix the cross-runner case through the core
   seam. Documented + asserted in manual verify; cross-runner propagation is an
   explicit non-goal here.

**Open questions for the human (Gate 1):**
- **Cross-runner propagation.** Do we want a runtime-only escape hatch — e.g. an
  optional `eventBus?` on `NodeRunContext` that `node-tool`/`coordinator-step` set
  so the child provably publishes to a specific bus regardless of runner identity —
  or is the shared-runner invariant (Decision §4) sufficient for now? (Recommend:
  ship the invariant now; add the escape hatch only if a real cross-runner
  topology appears. Note: `node-tool` has no bus handle today, so this would need
  the dispatch bridge to stash it — a larger change than #102's mechanical scope.)
- **`emit` payload contract.** Is mapping `emit` to `agent.tool.progress` with
  `statusText`/`progress` the shape we want plain tools to target, or should we
  define a richer `ToolEvent` → event mapping table (e.g. custom `type`s → a
  namespaced event)? (Recommend: `agent.tool.progress` only for now; expand when a
  concrete tool needs more.)
- **`parentSpanId` vs a dedicated `parentToolCallId` field on `NodeRunContext`.**
  We reuse `parentSpanId` (already on `RunOptions`) to nest child spans. Confirm
  we're comfortable overloading the span-id channel with the invoking tool-call id
  (they coincide: the tool-call *is* the parent span). (Recommend: yes — a
  tool call's span id and its `toolCallId`-derived span are the same nesting
  anchor; a separate field would be redundant.)
