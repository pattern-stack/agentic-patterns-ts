## Goal

The HITL **wire layer** — R2's first half. Everything #350's prompt state machine will
consume, nothing it will render:

1. **Typed `input.request`**: a new `ChunkInputRequest` chunk carrying the prompt (in
   `Content`), the resolved correlation id, `kind`, `options`, the tool fields, `Meta`, and
   the two forward-compat seam fields (`AvailableDecisions`, raw `InputPayload`). Today the
   frame silently rides through as `ChunkUnknown` (no-allowlist flip) — interactive events
   belong in the typed vocabulary, not the passthrough.
2. **Unanswerable prompts drop**: no correlation id (neither `correlation_id` nor the
   `requestId` alias) → `nil`; the server's timeout/teardown auto-deny keeps the run from
   hanging (`pending-input-registry.ts:47,81-85`; `conversations.ts:563-568`).
3. **Optional `InputResponder` capability** in `internal/types/client.go` — the
   `TurnCanceller` mold from #347, dossier decision D1 (locked): NOT a `Client` widening.
   Only `HTTPClient` implements it; `StubClient` and the CLI-spawn transports deliberately
   don't, which gives #350 the read-only degradation branch for free.
4. **`RespondInput` fail-closed**: always sends an explicit `decision` (empty → `"deny"`),
   `value` only when set; `404 → ErrInputOrphaned` (already settled — caller treats as
   auto-deny), `501 →` registry-missing error, other non-200 → plain HTTP error. Endpoint
   override `EndpointConfig.RespondInput`, default `/conversations/{id}/input`. Always
   POSTs to the stream's **own `:id`** — never a global key (B3 turns the global-key
   shortcut into a 404; plan §4, locked).
5. **Forward-compat seam vs harness-runners #328/B3 declared, not implemented**:
   `requestId` alias wins when present; `availableDecisions`/`payload` pass through
   untouched on the chunk; the decision string is forwarded unvalidated (the server is the
   validator). When B3 lands, the cockpit needs new decision-kind *strings*, not a wire
   release.

NOT in this PR: prompt state machine, key routing, rendering, app-shell guards — dossier
§3.D/§3.F, all #350 (`hitl-ux`).

## Approach

**State verified at spec time (differs from the dossier's pre-R1 snapshot):** the R1
prerequisites are DONE on chat-patterns main — send-path posts `{content}`
(`httpclient/client_test.go:14-66`), the no-allowlist flip forwards unknown events as
`ChunkUnknown` (`sse/parse.go:197-202`), the `tool.rejected` alias with canonical
`{tool_name, reason, gate_name}` payload is parsed (`parse.go:141-163`) — so this PR does
**not** carry the alias (dossier §3.C's "iff R1 hasn't landed it" resolved: it landed).
`SSEBase`/`Meta` uniformity exists (`sse/types.go:10-13`), so the new payload struct embeds
`SSEBase` — a post-dossier addition. Server side is done and tested; nothing to build there
(dossier §1; `approval-round-trip.test.ts:187-223`).

### 1. Parser — `input.request` becomes a typed, interactive chunk

New payload struct in `internal/sse/types.go` (authoritative wire source today:
`sse-formatter.ts:189-199` — snake_case, optional keys omitted when unset; seam fields per
plan §4):

- `correlation_id`, `kind`, `prompt` always present today; `options`, `tool_name`,
  `tool_call_id`, `arguments` conditional.
- Seam fields: `requestId` (B3 alias), `availableDecisions` (B3 decision list),
  `payload` as `json.RawMessage` (uninterpreted passthrough).

New case in `ChunkFromSSE` inserted before `default:` (`sse/parse.go:197`), following the
named-event discipline (malformed JSON → `nil` drop — same rule as tool/thinking cases,
NOT the best-effort `iteration.*`/`message.cancel` style, because an undecodable prompt is
unanswerable):

- **Alias resolution happens here, once**: effective id = `RequestID` if non-empty, else
  `CorrelationID`; both empty → `nil` (drop — the server denies on timeout/teardown, so a
  dropped prompt degrades to auto-deny, never a hang). Downstream sees a single
  `StreamChunk.CorrelationID`, already resolved (Open question Q1).
- `Prompt` → `Content`; tool fields reuse the existing `ToolCallID`/`ToolName`/`Arguments`
  chunk fields; `Meta` from `SSEBase`.
- `Done` stays false — the stream idles parked after this frame (runner blocked inside
  `bus.publish`; server invariant at `conversations.ts:407-411`), and the terminal frames
  arrive later on the same channel.

The typed case supersedes the `ChunkUnknown` passthrough for this event name — exactly the
carve-out the passthrough's own doc comment anticipates (`types.go:78-79` names
`input.request` as future typed handling).

### 2. Chunk vocabulary + DTO — `internal/types/types.go`

- `ChunkInputRequest ChunkType = "input_request"` in the const block (after `:36`; #347
  adds `ChunkCancelled` in the same block — textual conflict, trivial).
- `StreamChunk` grows a human-input field group (after the tool fields, `:65-74`):
  `CorrelationID`, `InputKind`, `Options`, `AvailableDecisions`, `InputPayload
  json.RawMessage`. The seam fields ride the chunk so #350 renders from
  `AvailableDecisions` when present without re-parsing raw data (plan §4: render-only
  change later).
- `InputResponse` DTO next to `SendMessageRequest` (`:123-125`): `CorrelationID`,
  `Decision` (client sends explicitly, always), `Value` (empty = omitted on the wire).
- `EndpointConfig.RespondInput string` override field (`:186-193`; #347 adds `CancelTurn`
  to the same struct — same trivial conflict).

### 3. Optional capability, not a `Client` widening — `internal/types/client.go`

`types.Client` (`client.go:6-25`) has six implementations (http, cli, exec, stdio, demo,
stub). Only HTTP has an input route. `InputResponder` is appended as a standalone
interface, mirroring #347's `TurnCanceller` (dossier D1, locked): the chat model
type-asserts in #350; the other five backends get the read-only branch with zero churn.
`StubClient` **deliberately does not implement it** — pinned by a negative test so the
gallery/demo path keeps exercising read-only degradation.

### 4. `HTTPClient.RespondInput` — `internal/httpclient/client.go`

Endpoint plumbing follows the existing pattern exactly: `endpointConfig.respondInput`
default `"/conversations/{id}/input"` + `respondInputPath()` helper (`client.go:19-66`) +
`types.EndpointConfig.RespondInput` override wiring in `newEndpointConfig`.

Method semantics (server contract verified at `conversations.ts:612-649`):

- Empty `Decision` → `"deny"` **client-side** (fail-closed; also matches the server's
  bare-call default, `:636-637`) — the wire body always carries an explicit decision.
- Body `{"correlation_id": ..., "decision": ...}`; `"value"` key only when `Value != ""`
  (server: `value` present would imply approve, `:636-637` — irrelevant here since we're
  always explicit, but keeps the body minimal and the tests exact).
- The decision string is **forwarded, not validated** — today's server accepts
  approve/deny; B3's richer decisions (sourced from `availableDecisions`) must not require
  a client release (Open question Q3).
- Uses the JSON client `c.HTTPClient` (30s timeout, `client.go:111`) with the caller's ctx
  — NOT the timeout-free `streamClient` (`:252`); `inputRegistry.resolve` is synchronous
  server-side (`:639-643`), the response is immediate.
- Response grammar: `200 → nil` · `404 → ErrInputOrphaned` (exported sentinel — the
  request was already settled: answered/timed out/torn down; #350 stamps "auto-denied
  (expired)" on `errors.Is`) · `501 →` error naming the missing registry (server hint:
  `AP_APPROVAL_TOOLS`, `:613-620`) · other → `respond input: HTTP %d`.
- `var _ types.InputResponder = (*HTTPClient)(nil)` next to the existing assertion
  (`:100`).

### 6. Trap 1 encoded at the wire layer — deny is `error {ToolCallBlocked}`, never `tool.rejected`

On the per-turn POST stream a deny/timeout arrives as
`error {error_type:"ToolCallBlocked"}` → already typed by the existing error case into
`StreamChunk{Error: &APIError{Type:"ToolCallBlocked"}, Done:true}` (`parse.go:185-195`).
`tool.rejected` is bus-only — it never rides this stream (runner yields the error and
returns, `agent-runner.ts`; proven by `approval-round-trip.test.ts:214-223`); the
`tool.rejected` alias already on main serves the admin firehose. **No new deny-path code in
this PR** — but the contract gets a dedicated wire-fixture test pinning
`APIError.Type == "ToolCallBlocked"` + `Done:true`, so #350's deny-render path has a
named, tested chunk shape to key on and nobody "fixes" the parser to wait for a
`tool.rejected` that will never come.

## Interfaces

```go
// internal/types/types.go

ChunkInputRequest ChunkType = "input_request" // HITL prompt — stream parks until answered

// StreamChunk additions (populated for ChunkInputRequest):
CorrelationID      string          // resolved id to echo back (requestId alias already applied)
InputKind          string          // "approval" | "select" | "text"; unknown → approval (#350)
Options            []string        // for InputKind "select"
AvailableDecisions []string        // harness-runners B3 seam: render decisions from this when present
InputPayload       json.RawMessage // B3 seam: raw passthrough, uninterpreted

// InputResponse answers a ChunkInputRequest (HITL return leg).
type InputResponse struct {
	CorrelationID string
	Decision      string // always sent explicitly; empty → "deny" (fail-closed) at the client
	Value         string // select/text answer; empty = omitted on the wire
}

// EndpointConfig addition:
RespondInput string // default: "/conversations/{id}/input"
```

```go
// internal/types/client.go

// InputResponder is an optional backend capability: answering a human-input
// request (ChunkInputRequest). Backends that cannot (stdio, cli, exec, demo,
// stub) simply don't implement it; the chat layer renders a read-only waiting
// state and the server's timeout/teardown auto-deny keeps the run from
// hanging. Deliberately NOT part of Client — callers type-assert.
type InputResponder interface {
	RespondInput(ctx context.Context, conversationID string, resp InputResponse) error
}
```

## Open questions

1. **Alias resolution location** (Approach §1): resolve `requestId` → one
   `StreamChunk.CorrelationID` in the parser (recommended — single field downstream, the
   seam collapses at the edge) vs carrying both raw fields on the chunk and letting #350
   pick. Note: the alias **key spelling** (`requestId` camelCase) comes from the locked
   plan-§4 wording, not shipped B3 code; if B3 ships `request_id`, it's a one-line
   struct-tag fix + test update. Gate call.
2. **`payload` passthrough type**: `json.RawMessage` on both structs (recommended — zero
   interpretation, byte-faithful, `encoding/json` import into `internal/types` is the only
   cost) vs `map[string]any` (decoded, friendlier, but lossy on non-object payloads and
   pretends we understand a shape that's still in B3 review). Gate call.
3. **Decision validation**: forward any non-empty decision string unvalidated
   (recommended — server is the validator; B3 decisions from `availableDecisions` then
   need no client release) vs restrict to `approve|deny` until B3 lands (stricter today,
   guaranteed client release later). Gate call.
4. **Keyless conformance probe now?** `contracttest` could cheaply assert
   `POST /conversations/{id}/input {correlation_id:"nonexistent"}` ⇒ 404 JSON against a
   live server without an LLM key (dossier §5). Recommended: leave to #350/Gate C — this
   PR stays offline-only and `contracttest` runs against live servers. Gate call.
