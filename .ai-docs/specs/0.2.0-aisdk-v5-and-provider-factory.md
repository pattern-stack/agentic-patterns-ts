# 0.2.0 — AI SDK v5 migration + config-driven provider factory

**Date:** 2026-06-13 · **Type:** breaking framework release (`@agentic-patterns/*@0.2.0`)
**Land together:** the AI SDK v5 port and the YAML provider factory ship as one `0.2.0`.
**Scope:** `packages/agent-runtime` (runner, providers, transport, exporters, message-utils, mocks) + dep bumps. **`packages/agent-core` is `ai`-free — do not touch it for v5.** Server/dashboard follow only where they bridge AI-SDK SSE. Consumers (retrieval-agent, dugs-agents, swe-brain) bump *after* publish.

**Why now:** unlock Gemini 3.x (thought-signatures are v5-provider-only), gain tool-call repair + `prepareStep`, and stop pinning old provider lines. Pairs with the deferred `remove-role-default-model` 0.2.0 break — fold that in if convenient.

## Part A — AI SDK v5 migration

Primary reference: the official v5 migration guide (https://ai-sdk.dev/docs/migration-guides/migration-guide-5-0). Below is the actionable, file-mapped delta. Most renames are covered by `npx @ai-sdk/codemod upgrade` — run it first, then fix the rest by hand.

**Order (per Dug, 2026-06-13): land v5 (Part A) first as `0.2.0`; the YAML provider factory (Part B) is a separate follow-up — order doesn't matter, so don't block v5 on it.**

### A0. Dependency bumps (MUST)
- `ai@^4 → ^5`, `@ai-sdk/provider@^2`, `@ai-sdk/provider-utils@^3`, `@ai-sdk/{anthropic,openai,google,…}@^2`, `zod@^3.25 || ^4.1.8`.
- **`ollama-ai-provider@1.x` is V1-only → REJECTED by v5.** Swap to a V2 fork: `ollama-ai-provider-v2` (preferred) or `ai-sdk-ollama@^2`. Update `providers/ollama.ts` `createOllama` import + `simulateStreaming`/`numCtx` settings against the fork's API.
- `@ai-sdk/*` are runtime peer/optional deps that consumers install — update the install-hint strings and `package.json` `peerDependenciesMeta`.

### A1. `runner/agent-runner.ts` (the core — most work here)
- **Delete `maxSteps: 1`** from both `generateText` and `streamText`. Single-step is now the v5 default; the gate-chain interception is preserved **iff tools stay `execute`-less** (they are — dispatch goes through `createToolboxExecutor`, not the SDK). Add a code comment locking this invariant.
- **Tool conversion (`convertTools`)**: the v5 tool shape is `{ description, inputSchema }` (was `{ description, parameters }`). Remap `parameters → inputSchema`. (Core's `ToolSchema.toVercelAI()` can keep returning `{description, parameters}`; do the rename at the runner boundary.)
- **Tool-call reads**: `toolCall.args → toolCall.input` (line ~332, ~349, ~385, ~406 — the `tc.args` sites).
- **Input params**: `maxTokens → maxOutputTokens`; any `providerMetadata` (input) → `providerOptions`.
- **Usage remap** (everywhere usage is read/emitted): `result.usage.promptTokens → inputTokens`, `completionTokens → outputTokens`; `result.usage` is now **final-step only** → use `result.totalUsage` for the run total the events report. Add `reasoningTokens`/`cachedInputTokens` to the emitted usage if cheap.
- **Reasoning**: `result.reasoning` (string) → `result.reasoningText`; the `agent.reasoning` event content reads `reasoningText`.
- **Messages**: `CoreMessage` type → `ModelMessage` (rename in the `messages: CoreMessage[]` array + `ToolCallPart`/`ToolResultPart` imports). Multimodal `mimeType → mediaType` if present.
- **★ JUDGMENT — thought-signature / reasoning round-trip:** when the runner reconstructs the assistant message after a tool-call step (the `assistantContent.push(...tool-call...)` block ~line 402+), it currently builds the message from scratch and **drops `providerMetadata`**. v5 carries the Gemini `thoughtSignature` (and Anthropic thinking blocks) in the assistant message's `providerMetadata`. **You must preserve and re-attach `result.response.messages` (or the assistant message's `providerMetadata`) unchanged into the next iteration's `messages`**, or Gemini 3.x multi-turn tool loops fail with "function call is missing a thought_signature." Prefer appending `result.response.messages` verbatim over hand-rebuilding the assistant turn.
- **Error handling**: `InvalidToolArgumentsError → InvalidToolInputError` (use `InvalidToolInputError.isInstance(e)`). `ToolExecutionError` is gone (execute-errors now surface as `tool-error` content parts — N/A to us since we don't give tools `execute`). Keep `NoSuchToolError`.

## Part B — config-driven (YAML) provider factory

> **SUPERSEDED — gateway re-added as a different shape.** The per-id
> `openai-compatible` *profile kind* described below was removed; gateway support
> was instead re-added as a resolver-level `GatewayConfig` (one endpoint routes
> many ids; the agent's id passes through, optionally prefixed/qualified; profiles
> are the per-id escape to go direct). Set it in code (`createRunner({ gateway })`)
> or via env (`AP_GATEWAY_BASE_URL`). See `providers/model-resolver.ts`
> (`GatewayConfig`). `ModelProfile` itself only aliases/pins to a named provider.
> Cross-provider retry/failover (which a gateway also provides) is still a separate
> future workstream. Below is retained as historical design context.

**Problem (today):** two unrelated provider systems — the framework's `ProviderProtocol` registry (env-detect + tier only; no per-instance config; no gateways) and consumers' hand-rolled `buildModel` if-else cascades (Bifrost/Ollama/Gemini with `numCtx`, Basic-auth, baseURL). Consumers bypass the registry because it can't express what they need.

**Goal:** one declarative model-profile schema + a factory that builds the adapter from data, evolving (not replacing) `ProviderProtocol`.

### B1. The `ModelProfile` schema (Zod)
```ts
type ModelProfile = {
  provider: 'anthropic'|'openai'|'google'|'groq'|'mistral'|'xai'|'deepseek'|'openrouter'|'ollama'|'openai-compatible';
  model: string;                       // tag or gateway-prefixed id
  tier?: ProviderTier;                 // optional; model wins over tier
  baseURL?: string;                    // gateways / local (env-interpolated: ${VAR})
  auth?: { type: 'bearer'|'basic'|'apiKey'|'env'; env?: string[] };  // how to build the auth header/key
  options?: Record<string, unknown>;   // per-provider passthrough (numCtx, headers, simulateStreaming, providerOptions…)
};
```

### B2. The factory + loader
- `buildModelFromProfile(profile): LanguageModelV2` — dispatch on `provider`; apply `baseURL`/`auth`/`options`. **`openai-compatible`** is a first-class kind (covers Bifrost, vLLM, any OpenAI-shaped gateway: `createOpenAI({ baseURL, apiKey, headers })`).
- `loadModelConfig(path): { default: string; profiles: Record<string, ModelProfile> }` — read a `models.yaml`, validate against the schema, interpolate `${ENV}`.
- **Evolve `ProviderProtocol.load`**: `load(modelId, opts?: { baseURL?; auth?; options? }) → LanguageModelV2`. The existing 9 providers keep working (opts optional); add the `openai-compatible` builder.
- **`createRunner` gains profile resolution** (additive): `createRunner({ profile?: string, modelsPath?: string, ... })`. Resolution order becomes: explicit runner → explicit model → **named profile** → explicit provider → **default profile** → env-detect (unchanged fallback) → claude CLI → mock. Env-detect stays as the zero-config path.

### B3. Migrate the consumer pattern (proves the design)
- The retrieval-agent's `config.ts` `buildModel` (Bifrost/Ollama/Gemini if-else) becomes **data**: a `models.yaml` with `bifrost-claude` (openai-compatible), `local-oss` (ollama + numCtx), `gemini-flash` (google) profiles + a `default`. `buildModel` shrinks to `buildModelFromProfile(resolveProfile())`. (Do this in the retrieval-agent's own follow-up PR, not in 0.2.0 — but ship a worked `models.yaml` example in the framework docs.)

## Phasing & verification

1. **Branch + worktree**, off `main`. One branch carries both Part A and Part B (land together).
2. **Part A first** (it's the foundation; Part B's builders return `LanguageModelV2`): codemod → manual fixes → `bun run build` green → `bun run typecheck` green → fix `bun run test` (505 suites; the mocks + the T0-1 regression are the canaries) → biome.
3. **Part B** on top: schema + factory + loader + the `openai-compatible` kind + `createRunner` profile path + tests.
4. **Smoke**: a hermetic in-memory agent (like `pm-memory`) run on v5 via a profile; plus a Gemini-3.x multi-turn tool-loop smoke (proves the thought-signature round-trip — the whole point).
5. **Release**: lockstep `just bump minor` → `0.2.0` → PR → merge → CI publish. Update READMEs with the v5 + `models.yaml` story.

## Acceptance
- `bun run check` green on v5 across core+runtime+server.
- The T0-1 gate-allow regression test passes under v5.
- A Gemini-3.x agent completes a **multi-turn** tool loop (no thought-signature error).
- A `models.yaml`-driven `createRunner({ profile })` builds anthropic / ollama(+numCtx) / gemini / openai-compatible(Bifrost) models.
- Core untouched (still `ai`-free).

## The four judgment points (don't let a mechanical pass skip these)
1. **Thought-signature round-trip** in `agent-runner.ts` (A1 ★) — append `result.response.messages` verbatim; don't hand-rebuild the assistant turn dropping `providerMetadata`.
2. **`ollama-ai-provider` V2 fork** swap (A0) — the original is V1-only.
3. **Gate-chain invariant** — tools stay `execute`-less; `maxSteps` deletion must not let the SDK auto-run/loop tools.
4. **`ClaudeCodeLanguageModel` → V2** (A3) — the hand-written provider needs a real spec port.
