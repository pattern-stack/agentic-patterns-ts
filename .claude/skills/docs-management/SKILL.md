# Docs Management

Documentation governance for agentic-patterns-ts. Established with #457/#458
(PR #459). The prime directive: **docs are code** — they build in CI, break
loudly, and never silently rot. The 2026 failure mode this system exists to
prevent: a hand-deployed site freezing for five months and documenting a dead
framework.

## Architecture (do not re-derive)

- **`docs/` is the single source of truth**, read IN PLACE by the site.
  Never move content under `docs-site/` — code comments and ADR cross-refs
  depend on `docs/...` paths.
- **`docs-site/`** is a private workspace member (Astro + Starlight). Its
  content collection is a glob loader based at `../docs`
  (`docs-site/src/content.config.ts`). Its build rides the workspace Build
  step, so the docs site is part of the required CI `check` status.
- **Deployment**: Cloudflare Pages git integration — `main` is production at
  agentic-patterns.pattern-stack.com, PRs get preview URLs. There is NO
  manual deploy step, by design. Never introduce one.

## Frontmatter contract (every docs/ page)

```yaml
---
title: "Page Title"                    # expected — falls back to the first h1
description: "One sentence, <=160ch."  # required by convention — search/SEO/llms
sidebar:
  label: "Short Label"                 # only when the title is unwieldy (ADRs)
---
```

- The body has NO h1 — the title renders as the h1. (The 2026-08 migration
  moved every doc's first h1 into frontmatter.)
- **`title` is not hard-required.** A doc with no `title` takes its first h1
  instead of failing the build (`docs-site/src/content.config.ts`). This exists
  because a strict schema turned every doc merged to `main` into a build break
  for branches cut before it — a merge-order hazard, not a docs-accuracy one.
  Write the frontmatter anyway: the fallback leaves the h1 in the body, so the
  page renders its heading twice, and you lose `description` and `sidebar.label`.
  The gates that carry real signal — link validation and manifest drift — are
  untouched by this.
- Descriptions state design-preview vs shipped status explicitly when it
  applies ("Status: design/mockup", "Phase B not built"). A cold reader must
  be able to tell shipped API from aspiration without opening the page.

## Linking rules

- **Between docs**: relative `*.md` paths (`../adr/0007-memory-store.md`) —
  they work in GitHub's file view, and an inline remark plugin in
  `docs-site/astro.config.mjs` rewrites them to site routes at build.
- **To files outside docs/** (e.g. `.ai-docs/` specs): absolute GitHub blob
  URLs — those targets don't exist on the site.
- Every internal href in the FINAL built HTML is validated by
  `tools/check-docs-links.ts` (chained into the docs-site build script). A
  broken link fails CI. If the build reds on links, fix the link — do not
  weaken the checker.

## Sidebar placement policy

Wired explicitly in `docs-site/astro.config.mjs`. Adding a root-level guide
requires adding its slug there (slugs are lowercased paths without extension).

| Group | What belongs | Bar |
|---|---|---|
| **Guides** | Shipped-API learning path only | A visitor following it must never hit an unshipped API |
| **Memory** | The memory guide + evolution cookbook | Phase status flagged in prose |
| **Reference** | Generated catalogs + operational reference | Generated pages preferred over hand-written |
| **Architecture Decisions** | `docs/adr/` (autogenerated) | ADRs are public; keep sidebar labels short ("ADR NNNN — Name") |
| **Design notes** (collapsed) | Dated design/plan documents, internal playbooks | Honest quarantine — never let these leak into Guides |

When a design doc's feature ships, promote the doc out of Design notes only
after rewriting it as a guide (present tense, shipped surface only).

## Truth gates (the point of the whole system)

1. **Link gate** — `tools/check-docs-links.ts`, runs inside every docs-site
   build. Covers sidebar/hero/generated links, not just markdown.
2. **Events drift gate** — `docs/reference/events.md` is GENERATED from
   `packages/agent-runtime/src/transport/sse-event-manifest.json` by
   `tools/gen-docs-event-reference.ts`. `bun run check:docs-events` (in the
   root `check` chain and CI) fails when stale. If you change the SSE wire
   vocabulary: regenerate with `bun run docs:events` and commit both files.
3. **Verified code samples** — any executable code block added to a doc must
   be proven against the built packages before commit: write an executable
   twin script, run it, THEN commit (the getting-started precedent — its twin
   exercises compose/render/run for both the prose and capability stages).
   This is manual discipline until #457 slice 3 automates fence checking.
4. **Prose/source agreement** — landing page, README, and CLAUDE.md must
   agree with each other and with source. When a doc states an architecture
   fact, verify it against code, not against another doc (the fact-check that
   built this system found CLAUDE.md itself stale).

## The generated-page pattern (house style)

For any reference derivable from a source-of-truth artifact (manifests,
schemas, export maps): **generate + commit + drift-check** — never build-time
magic, never hand-written.

1. Generator at `tools/gen-docs-<thing>.ts` with a `--check` mode (exit 1 on
   stale), following `tools/gen-docs-event-reference.ts`.
2. Output committed under `docs/reference/` with a GENERATED header naming
   the generator and the regen command.
3. `check:docs-<thing>` script in root package.json, appended to the `check`
   chain, plus a CI step in `.github/workflows/ci.yml`.

## Commands

```sh
bun run docs:dev            # live-reload authoring server
bun run --filter=@pattern-stack/agentic-docs-site build   # build + link gate
bun run docs:events         # regenerate the events reference
bun run check:docs-events   # drift gate (what CI runs)
cd docs-site && bunx astro preview        # serve the built site (daemonized)
```

## Anti-patterns

- Hand-editing `docs/reference/events.md` (regenerate instead)
- Moving docs under `docs-site/` (breaks every path reference)
- Adding a doc without frontmatter description (invisible to search/llms)
- Putting a design doc in Guides "temporarily"
- Weakening a truth gate to make a build pass
- Any deploy path that isn't the CF Pages git integration
